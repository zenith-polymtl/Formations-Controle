# Annexe 5.4, pour les leads : créer et faire évoluer l'environnement

Cette annexe n'est pas un exercice : la recrue la parcourt une fois, seulement pour savoir que l'annexe existe. L'annexe donne aux leads les gestes pour créer un repo de mission et le faire évoluer, avec les commandes exactes du repo. Les six recettes sont indépendantes ; lisez celle dont vous avez besoin.

---

## 1 - Créer un repo de mission à partir de `mission-template`

`mission-template` (le repo public `zenith-polymtl/mission-template`) est la base des repos de compétition. Il contient le Makefile, les conteneurs, la configuration, `gcs_ws`, `vision_ws`, `packages/sim_mocks`, les cinq submodules de `packages/` et les liens déjà posés dans les workspaces. Il ne contient aucune mission. Ses fichiers sont ceux d'`aeac-2027`, sauf le `README.md`. Quand l'architecture change dans un repo de compétition, reportez le changement dans le template, pour deux raisons : les recrues lisent le template, et les prochains repos (`suas-2027`, `aeac-2028`) partiront de lui.

La recette compte quatre étapes, à faire une fois par repo. Ce sont les étapes de la section « Créer un repo de mission à partir de ce template » du `README.md` du template.

D'abord, créez le repo distant. Sur GitHub, ouvrez `zenith-polymtl/mission-template`. Cliquez **Use this template → Create a new repository** et créez le repo dans l'organisation `zenith-polymtl`. Dans **Settings → Collaborators and teams** du nouveau repo, donnez l'accès en écriture à l'équipe contrôle.

Ensuite, clonez le repo dans WSL :

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/<nouveau-repo>
```

```bash
cd <nouveau-repo>
```

```bash
make init
```

```bash
make check
```

Sur un clone neuf, `make check` répond `check : rien à signaler`.

Puis vérifiez `.gitmodules`. Un submodule pointe vers un commit, pas vers une branche. La ligne `branch =` indique seulement la branche où `make bump` ira chercher le commit suivant ; si la ligne manque, c'est `main`. Dans le template, `tools` et `custom_interfaces` suivent la branche `aeac-2027`. C'est la branche qui contient `topics.py` et `MissionState.msg`, et elle n'est pas encore mergée dans le `main` de ces deux repos. Un nouveau repo hérite de ces lignes. Une fois la branche `aeac-2027` mergée, retirez les deux lignes `branch = aeac-2027` dans un commit.

Enfin, protégez `main` avant que quiconque clone le repo. Dans **Settings → Branches → Add branch ruleset**, créez une règle sur `main` : pull request obligatoire, et c'est un lead qui merge. La règle « `main` = ce qui vole » est respectée seulement si GitHub l'impose.

**Le template et la formation.** Les recrues de la formation 5 clonent `mission-template` lui-même. Elles y copient la démo, puis y poussent leur branche en 5.3. Donnez donc à l'équipe contrôle le droit d'écriture sur le template, pour qu'elle puisse pousser des branches ; `main` reste protégée. Un lead relit chaque PR avec la grille de [`5.3-projet/solution/CHECKLIST.md`](5.3-projet/solution/CHECKLIST.md). Ensuite, il ferme la PR sans merge et supprime la branche, parce que le template ne contient jamais de mission. Avant de pousser un nouveau pointeur de submodule dans le template, poussez le submodule lui-même (`git push --recurse-submodules=on-demand`, que `make init` règle par défaut). Si le pointeur vise un commit absent de GitHub, le clone de la recrue suivante échoue.

## 2 - Ajouter une mission

Une mission se compose de trois choses (`ARCHITECTURE.md`, section « Une mission ») : un workspace, un fichier de configuration et un launch file pour le sol. Tapez les commandes dans WSL, à la racine du repo. Remplacez `<nom>` par le nom de la mission.

Créez d'abord le workspace. `make link` a besoin que le dossier `src/` du workspace existe :

```bash
mkdir -p workspaces/<nom>_ws/src
```

Ensuite, créez un lien par package partagé :

```bash
make link C=<nom> PKG=tools
```

```bash
make link C=<nom> PKG=custom_interfaces
```

```bash
make link C=<nom> PKG=sim_mocks
```

`sim_mocks` permet à `make rc` et `make takeoff` de trouver les mocks en simulation. Créez les liens depuis WSL, parce que sous Windows, git enregistre un symlink comme un fichier texte. Les liens font partie du commit : celui qui clone ou copie le workspace le reçoit donc déjà lié, comme `demo_ws` en 5.2.

Ensuite, créez le package `<nom>_bringup` dans `workspaces/<nom>_ws/src/`, avec `launch/mission.launch.py`. Partez de `demo_bringup`, dans `5-env_compétition/demo_ws/src/`. Copiez-le, puis remplacez `demo` par `<nom>` dans le nom du dossier, dans `package.xml`, `setup.py`, `setup.cfg`, le fichier de `resource/` et le launch file. Supprimez aussi le dossier `config/` de la copie, parce qu'il ne sert qu'à la formation. Le launch file de `demo_bringup` a déjà la forme attendue : deux arguments, `sim` et `site`, et une node qui reçoit `/aeac/config/<nom>.yaml` puis `/aeac/config/sites/<site>.yaml`.

Puis écrivez `config/<nom>.yaml` sur le modèle de l'exemple de `config/README.md` : une section par node, au format des paramètres ROS 2.

Enfin, pour le sol, créez `workspaces/gcs_ws/src/gcs_bringup/launch/<nom>.launch.py`. Ce launch file inclut `base.launch.py` (la docstring de `base.launch.py` donne les lignes à copier) et ajoute les nodes sol de la mission. `make gcs C=<nom> DRONE=<drone>` le lance.

Construisez, puis vérifiez les `package.xml` et les liens :

```bash
make build C=<nom>
```

```bash
make check
```

Si la mission a son propre terrain, ajoutez `config/sites/<terrain>.yaml` sur le modèle de `cimetiere.yaml`. Ce fichier donne la cible en mètres depuis le home, c'est-à-dire le point où le pilote arme. `make sim C=<nom> SITE=<terrain>` charge ce terrain. Sur la Jetson, le terrain de vol est la variable `SITE` du `.env` du repo. `make drone` et `mission.service` la passent en `site:=`, et refusent de lancer la mission si elle manque (`systemd/install.md`).

**Un launch file de simulation.** Aucun launch file de mission n'inclut de mock : c'est ce qui garantit qu'un mock ne vole jamais. En revanche, vous pouvez écrire un `sim.launch.py` réservé à la simulation, qui inclut `mission.launch.py` et démarre les mocks. Lancez-le par une cible make dont le nom indique qu'elle ne sert qu'au sol.

## 3 - Ajouter un package partagé

La règle est dans `packages/README.md` : un package reste local à sa mission, sauf s'il sert ailleurs. S'il sert à deux workspaces du même repo, il va dans `packages/` sous forme de dossier ordinaire, comme `sim_mocks`. S'il sert à deux repos, ou d'une année à l'autre, il devient un submodule.

Pour un submodule, créez un repo GitHub dans `zenith-polymtl` avec le `package.xml` à sa racine (pas dans un sous-dossier), puis :

```bash
git submodule add https://github.com/zenith-polymtl/<nom> packages/<nom>
```

Ajoutez ensuite une ligne pour ce package au tableau de `packages/README.md`. Liez-le aux workspaces qui l'utilisent avec `make link` (recette 2). Faites un commit du tout. L'opération inverse, sortir un package du partage, est décrite dans `ARCHITECTURE.md`, section « Pour les leads ».

## 4 - Ajouter un conteneur

Un conteneur demande deux fichiers, chacun avec un en-tête. Le Dockerfile va dans `docker/dockerfile.<rôle>`. Son en-tête indique où l'image tourne et ce qui la distingue des autres images, comme celui de `docker/dockerfile.gcs`. Il explique aussi pourquoi une dépendance est épinglée, comme le numpy de `docker/dockerfile.vision`. Le fichier compose va dans `compose/<nom>.yml`, avec un fichier par chose à lancer. Son en-tête indique qui le lance, à la main et au boot, comme celui de `compose/mavros.yml`. `make check` signale tout Dockerfile qu'aucun compose ne construit.

Ajoutez la cible dans la section 2 du `Makefile`, avec son commentaire `##`. `make help` affiche ce commentaire :

```makefile
<nom>: ## Description courte (Jetson)
	docker compose -f compose/<nom>.yml up
```

Si le conteneur doit démarrer au boot, passez à la recette 5.

Les cibles de confort de la section 1 (`make shell`, `make takeoff`, `make rc`, `make echo`) font seulement ce qu'un `docker exec` ferait : elles évitent de retaper la commande. Vous pouvez en ajouter librement, chacune avec un nom explicite et sa ligne `##`.

## 5 - Ajouter un service au boot

Créez un fichier `systemd/<nom>.service` sur le modèle des services existants. Écrivez `__REPO__` partout où le chemin du repo apparaît : `make deploy` remplace `__REPO__` par le vrai chemin, puis copie le fichier dans `/etc/systemd/system/`. Ajoutez ensuite le nom du service à la variable `SERVICES` du Makefile ; sinon, `make deploy` l'ignore.

Déclarez l'ordre au boot avec `After=`. Si un service a besoin d'un matériel, il doit attendre ce matériel explicitement au lieu de compter sur un délai. Par exemple, le `ExecStartPre=` de `mavros.service` attend le port série. Vérifiez le service avec `make <nom>-status` et `make <nom>-logs`. La formation 6 couvre les services en détail.

## 6 - Faire évoluer

**Avancer un package partagé.** Quand une PR est mergée dans le repo d'un submodule, les repos de mission ne se mettent pas à jour tout seuls. Pour avancer le submodule, lancez dans le repo de mission :

```bash
make bump PKG=tools
```

`make bump` lit la branche suivie dans `.gitmodules` (`main` si aucune n'est indiquée). Ensuite, la cible affiche les nouveaux commits, place le submodule sur cette branche, pose un tag daté et stage le pointeur. Si le commit actuel du submodule n'est pas dans cette branche, `make bump` refuse, parce que le pointeur reculerait ; un lead doit alors décider. La PR du submodule doit donc viser la branche suivie. Il reste à faire le commit et le push :

```bash
git commit -m "bump tools"
```

```bash
git push --recurse-submodules=on-demand
```

**Déployer sur la Jetson.** `make deploy C=<mission>` installe les services et choisit la mission lancée au boot. Pour changer de mission, lancez `make deploy C=<autre>`, puis `make mission-restart`. `make undeploy` arrête et désactive les services, pour que vous puissiez tester à la main. La marche à suivre est dans `systemd/install.md`.

**Après la compétition.** Posez un tag `<compétition>-<année>` sur `main`. Ensuite, supprimez les workspaces et les packages de mission qui ne serviront plus. Le tag conserve le repo dans l'état où il a volé.

La section « Pour les leads » d'`ARCHITECTURE.md` résume ces gestes en une liste courte. Tenez-la à jour quand l'un d'eux change.
