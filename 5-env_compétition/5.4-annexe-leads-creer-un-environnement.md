# Annexe 5.4, pour les leads : créer et faire évoluer l'environnement

Cette annexe n'est pas un exercice et la recrue n'a rien à y faire : elle sait qu'elle existe, elle la parcourt une fois, elle reste l'utilisateur de l'environnement plutôt que son constructeur. Ce qui suit répond à la question que personne ne documente et qui se repose chaque année : comment on fabrique un repo de mission, et pas seulement comment on l'habite. C'est écrit en gestes, avec les commandes exactes du repo, pour qu'un lead de 2028 s'en serve sans nous.

Vingt minutes de lecture. Les six recettes sont indépendantes ; lisez celle dont vous avez besoin.

---

## 1 - Créer un repo de mission à partir de `mission-template`

`mission-template` est le squelette dont `aeac-2027` est issu : le `Makefile`, `.env.example`, `docker/`, `compose/`, `config/`, `systemd/`, `scripts/check.py`, `ARCHITECTURE.md`, `procédure.md`, `NOTES.md`, `workspaces/gcs_ws`, `workspaces/vision_ws`, `packages/sim_mocks`, les cinq submodules de `packages/` (`custom_interfaces`, `tools`, `nav_stack`, `vision`, `zed-ros2-wrapper`) et les liens des packages partagés vers les workspaces, exactement comme dans `aeac-2027`. Il ne contient aucun code de mission. C'est le repo public `zenith-polymtl/mission-template`. Un nouveau repo de compétition (`suas-2027`, `aeac-2028`) en part.

Deux détails du contenu à connaître avant de partir de là. `config/sites/` arrive avec `sim.yaml` (la position de départ du SITL) et `cimetiere.yaml` (le terrain de vol habituel) ; les deux sont au format paramètres ROS 2, sous le joker `/**`, pour être passés tels quels au launch file. Et `.env.example` est le modèle du `.env` local de chaque poste : on le copie en `.env`, qui reste hors de git, et on y met `SITL_HOST=` quand le calcul automatique du Makefile ne convient pas (WSL en mode mirrored, Linux natif, Mac).

La recette est celle du `README.md` du template, section « Créer un repo de mission à partir de ce template ». Elle tient en trois gestes, une fois par repo.

D'abord le repo distant. Sur GitHub, ouvrez `zenith-polymtl/mission-template` et cliquez **Use this template → Create a new repository** : le nouveau repo naît avec tout le contenu du template, dans l'organisation `zenith-polymtl`, sans l'historique du template. Ne cochez rien qui ajoute un fichier ; le template les apporte. Dans **Settings → Collaborators and teams**, donnez l'accès en écriture à l'équipe contrôle.

Ensuite le contenu, en local :

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/<nouveau-repo>
cd <nouveau-repo>
make init
make check
```

`--recurse-submodules` est ce qui remplit `packages/` ; `make init` pose les réglages git et les dossiers ignorés, et `make check` dit tout de suite si un lien de package partagé est cassé.

Enfin protéger `main`, tout de suite, avant que quiconque clone. Dans **Settings → Branches → Add branch ruleset**, sur `main` : interdire le push direct et exiger une pull request, qu'un lead fusionne. La règle du repo (« `main` = ce qui vole ») ne tient que si GitHub la fait tenir.

Chaque mission se crée ensuite selon la recette 2.

### Le template et la formation

La formation 5 ne se fait pas dans un repo à part : les recrues clonent le repo template lui-même, y posent la démo, y écrivent leur node et y poussent leur branche. La PR de 5.3 s'ouvre donc sur `mission-template` ; un lead la relit avec la grille de [`5.3-projet/solution/CHECKLIST.md`](5.3-projet/solution/CHECKLIST.md), la ferme sans fusionner et supprime la branche. Le template ne contient jamais de mission, pas même celle d'un exercice. Le repo de compétition, lui, n'est jamais touché par la formation. Pour que les recrues puissent pousser leur branche, donnez à l'équipe contrôle le droit d'écriture sur `mission-template` : les branches, pas `main`, qui reste protégée.

Trois conséquences pour le lead qui s'occupe du template. `main` y est protégée comme dans un repo de compétition, sinon une branche de recrue finirait par y entrer. Les pointeurs de submodules doivent viser des commits réellement poussés, faute de quoi le `git clone --recurse-submodules` de la première recrue échoue : poussez avec `git push --recurse-submodules=on-demand`, que `make init` règle une fois pour toutes dans un clone (`git config push.recurseSubmodules on-demand`), mais vérifiez-le sur la machine d'où vous travaillez. Et le template se met à jour quand l'architecture change, puisque c'est lui que les recrues lisent et que les prochains repos de compétition en partiront.

## 2 - Ajouter une mission

Une mission, c'est trois choses, dit `ARCHITECTURE.md` : un workspace, une configuration, un launch file pour le sol.

1. `workspaces/<nom>_ws/src/<nom>_bringup/`, avec `launch/mission.launch.py` : c'est ce que `make drone C=<nom>` lance sur la Jetson et ce que `make sim C=<nom>` lance en simulation. Le même launch file sert aux deux ; `sim:=true` passe un paramètre `sim` aux nodes qui touchent au matériel, et `site:=<nom>` choisit `config/sites/<nom>.yaml`.
2. `config/<nom>.yaml` : tout ce qui se règle, au format paramètres ROS 2, une section par node. Le launch file le charge et le passe aux nodes. (La distinction entre un fichier de référence dans `<nom>_bringup/config/` et une copie de travail dans `config/` à la racine est la convention de `demo_ws`, pas une règle du repo de mission.)
3. `gcs_ws/src/gcs_bringup/launch/<nom>.launch.py` : ce que le portable lance pour cette mission, `make gcs C=<nom> DRONE=<drone>`.

`gcs_ws` est le workspace du sol, et rien d'autre. Ce n'est pas le workspace dans lequel on développe : rien de spécifique à un drone ou à une mission n'y entre, même temporairement. Le conteneur `dev` monte tout le repo dans `/aeac` et construit n'importe quel workspace, donc il n'y a jamais de raison de squatter celui du sol.

Les packages partagés se lient au nouveau workspace, un par un, et les liens se commettent :

```bash
make link C=<nom> PKG=tools && make link C=<nom> PKG=custom_interfaces && make link C=<nom> PKG=sim_mocks
```

`make link` est un geste de lead, et c'est voulu. Quand vous préparez un workspace pour des recrues, posez les liens vous-même et commettez-les : celui qui copie le workspace le trouve déjà lié et n'a rien à faire. C'est ainsi que `demo_ws` est livré à la formation 5.2.

Pensez à `sim_mocks` : c'est ce qui permet à `make rc` et `make takeoff` de trouver les mocks dans le conteneur `dev`, où tourne la simulation.

Puis la vérification, qui voit les `package.xml` incomplets et les liens cassés :

```bash
make check
```

Si la mission a un terrain à elle, ajoutez `config/sites/<terrain>.yaml`, sur le modèle de `cimetiere.yaml` ; `make sim C=<nom> SITE=<terrain>` le charge.

**Un launch file de simulation.** Aucun launch file de mission n'inclut un mock : c'est ce qui garantit qu'un mock ne peut pas se retrouver dans les airs. Rien n'interdit en revanche d'écrire un second launch file réservé à la simulation, un `sim.launch.py` qui inclut le launch file de mission et démarre les mocks avec, avec une cible make dont le nom dit clairement qu'elle ne sert qu'au sol. Ce qui est interdit, c'est de mélanger les deux dans le fichier qui vole.

## 3 - Ajouter un package partagé

La règle est dans `packages/README.md` et elle se lit dans ce sens : un package est **local** à sa mission sauf s'il sert ailleurs. S'il sert à deux workspaces du même repo, il vit dans `packages/` comme dossier simple, comme `sim_mocks`. S'il sert à deux repos, ou d'une année à l'autre, il devient un submodule, et c'est un lead qui le décide.

Pour le submodule : créez un repo GitHub avec le `package.xml` à la racine du repo, et non dans un sous-dossier, puis

```bash
git submodule add https://github.com/zenith-polymtl/<nom> packages/<nom>
```

Ajoutez une ligne dans le tableau de `packages/README.md` (package, type, rôle), liez-le aux workspaces qui l'utilisent avec `make link`, et commettez le tout.

Prévenez ensuite les autres repos qui suivent ce package : chez eux, `make bump PKG=<nom>` avance le pointeur sur `origin/main`, pose un tag daté et stage le pointeur. Un repo qui ne fait pas ce `bump` reste sur l'ancienne version, ce qui est le comportement voulu : un submodule ne bouge que quand quelqu'un le décide.

L'opération inverse est dans `ARCHITECTURE.md`, section « Pour les leads » : `git submodule deinit packages/<nom>`, copier le dossier dans le workspace concerné, `git rm packages/<nom>`.

## 4 - Ajouter un conteneur

Deux fichiers, et un en-tête dans chacun.

Le Dockerfile va dans `docker/`, nommé `dockerfile.<rôle>`. Son en-tête dit où l'image tourne et **ce qui diffère** des autres images, parce que c'est la seule question que se pose le suivant. Celui de `docker/dockerfile.gcs` le fait en quelques lignes : image du portable et du poste de développement, rviz2, rqt et X11 en plus par rapport à `dockerfile.drone`, tout le reste identique volontairement. Quand une dépendance est épinglée, l'en-tête dit pourquoi : `dockerfile.vision` explique que numpy est tenu à 1.26.4 parce que torch et ultralytics sur Jetson ne supportent pas numpy 2.

Le compose va dans `compose/`, nommé `<nom>.yml`, un fichier par chose à lancer. Son en-tête dit qui le lance, à la main et au boot : `compose/mavros.yml` commence par « mavros vers le Pixhawk, sur la Jetson. `make mavros` à la main, `mavros.service` au boot. »

Ajoutez ensuite la cible dans le `Makefile`, dans la bonne section (`##@ 2. Test sur véhicule` pour ce qui se lance à la main sur le drone), avec son commentaire `##` : c'est lui que `make help` affiche.

```makefile
<nom>: ## Description courte (Jetson)
	docker compose -f compose/<nom>.yml up
```

Si le conteneur doit aussi démarrer au boot, ajoutez son nom à la variable `SERVICES` en haut du Makefile, et passez à la recette 5.

**Les cibles de confort.** La section 1 du Makefile en contient déjà : `make shell` entre dans le conteneur en cours sans qu'on ait à le nommer, `make down` arrête tous les conteneurs `aeac-*` du poste, `make takeoff` et `make rc` lancent les deux nodes de test de `sim_mocks`, `make echo T=/un/topic` regarde un topic. Elles ne font rien qu'un `docker exec` ne ferait, elles évitent de le retaper. Ajoutez-en librement : une commande que l'équipe tape dix fois par soirée mérite une cible, un nom explicite et sa ligne `##` pour `make help`.

## 5 - Ajouter un service au boot

Un fichier `systemd/<nom>.service`, calqué sur ceux qui existent. `make deploy` remplace `__REPO__` par le chemin du repo et copie le fichier dans `/etc/systemd/system/`, donc écrivez `__REPO__` partout où le chemin du repo apparaît. Le nom du service doit figurer dans la variable `SERVICES` du Makefile, sinon `make deploy` l'ignore.

L'ordre au boot se déclare avec `After=` et se lit dans `systemd/install.md` : `lo-multicast`, puis `mavros` (qui attend `/dev/ttyTHS1`), `zed` (qui attend la caméra), `zenoh-air`, `vision`, `mission`. Un service qui a besoin d'un autre le nomme ; un service qui attend du matériel l'attend explicitement plutôt que de compter sur un délai.

Vérifiez avec `make <nom>-status` et `make <nom>-logs`, et rappelez-vous que systemd n'est qu'un emballage : `make undeploy` puis la cible `make` correspondante relance exactement la même chose en avant-plan. Le détail des services et du réseau est le sujet de la formation 6 ; ici il s'agit seulement de savoir où le fichier se met.

## 6 - Faire évoluer

**Avancer un package partagé.** Quand une PR est fusionnée dans le repo d'un submodule, les repos qui le suivent ne bougent pas tout seuls :

```bash
make bump PKG=tools
```

La cible fetch `origin`, affiche les commits gagnés, se place sur `origin/main`, pose un tag daté du nom du repo, et stage le pointeur. Il reste à commettre et à pousser :

```bash
git commit -m "bump tools" && git push --recurse-submodules=on-demand
```

**Déployer sur la Jetson.** `make deploy C=<mission>` installe les services depuis `systemd/`, écrit la mission dans `/etc/aeac/mission` et les active. `make deploy C=<autre>` change la mission au boot. `make undeploy` rend la main pour un test manuel. La marche à suivre complète est dans `systemd/install.md`.

**Le reste.** La section « Pour les leads » d'`ARCHITECTURE.md` est la liste courte de ces gestes, et c'est elle qu'il faut tenir à jour : contribuer à un package partagé, en créer un, en sortir un du partage, déployer, les modèles de vision.

**Après la compétition.** Un tag `<compétition>-<année>` sur `main`, puis la suppression des workspaces et des packages de mission qui ne serviront plus. Le tag est ce qui permet de revenir au repo tel qu'il a volé, une fois qu'on l'a vidé pour l'année suivante.

Reste, pour boucler avec la formation 5 : les PR de la formation 5.3 se relisent avec la grille de [`5.3-projet/solution/CHECKLIST.md`](5.3-projet/solution/CHECKLIST.md).
