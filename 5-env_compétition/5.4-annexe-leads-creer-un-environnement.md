# Annexe 5.4, pour les leads : créer et faire évoluer l'environnement

Cette annexe n'est pas un exercice et la recrue n'a rien à y faire : elle sait qu'elle existe, elle la parcourt une fois, elle reste l'utilisateur de l'environnement plutôt que son constructeur. Ce qui suit répond à la question que personne ne documente et qui se repose chaque année : comment on fabrique un dépôt de mission, et pas seulement comment on l'habite. C'est écrit en gestes, avec les commandes exactes du dépôt, pour qu'un lead de 2028 s'en serve sans nous.

Vingt minutes de lecture. Les six recettes sont indépendantes ; lisez celle dont vous avez besoin.

---

## 1 - Créer un dépôt de mission à partir de `mission-template`

`mission-template/` est le squelette dont `aeac-2027` est issu : le `Makefile`, `docker/`, `compose/`, `config/`, `systemd/`, `scripts/check.py`, `ARCHITECTURE.md`, `procédure.md`, `NOTES.md`, `workspaces/gcs_ws`, `workspaces/vision_ws`, `packages/sim_mocks`, et aucun code de mission. Un nouveau dépôt de compétition (`suas-2027`, `aeac-2028`) en part.

D'abord le dépôt distant : sur GitHub, dans l'organisation `zenith-polymtl`, **New repository**, nom du dépôt, privé, et surtout rien de coché qui ajoute un fichier (pas de README, pas de `.gitignore`, pas de licence) : le template les apporte. Dans **Settings → Collaborators and teams**, donner l'accès en écriture à l'équipe contrôle.

Ensuite le contenu, en local. Le squelette est `5-env_compétition/mission-template/` du dépôt Formations-Controle ; placez-vous dans son dossier parent, ou donnez le chemin complet. C'est la recette du `README.md` d'aeac-2027, section « Créer un dépôt de mission à partir de ce template » :

```bash
cp -r mission-template/ <nouveau-dépôt> && cd <nouveau-dépôt>
git init
for p in custom_interfaces tools nav_stack vision; do git submodule add https://github.com/zenith-polymtl/$p packages/$p; done
git submodule add -b zenith https://github.com/zenith-polymtl/zed-ros2-wrapper packages/zed-ros2-wrapper
make link C=gcs PKG=custom_interfaces && make link C=gcs PKG=tools && make link C=gcs PKG=sim_mocks
make link C=vision PKG=vision && make link C=vision PKG=custom_interfaces
make init && make check
git add -A && git commit -m "init from mission-template"
```

Puis le premier `push`, que le README ne dit pas :

```bash
git branch -M main
git remote add origin https://github.com/zenith-polymtl/<nouveau-dépôt>
git push -u origin main
```

Enfin protéger `main`, tout de suite, avant que quiconque clone. Dans **Settings → Branches → Add branch ruleset**, sur `main` : interdire le push direct et exiger une pull request. La règle du dépôt (« `main` = ce qui vole ») ne tient que si GitHub la fait tenir.

Chaque mission se crée ensuite selon la recette 2.

### Variante : un dépôt de cohorte pour la formation 5

La formation 5 ne se fait jamais dans le dépôt de compétition. Chaque cohorte reçoit une copie jetable, `formation-5-<cohorte>` (par exemple `formation-5-automne-2026`), et elle part d'`aeac-2027` plutôt que du template : les recrues doivent voir un dépôt habité, avec ses sous-modules, ses conteneurs et ses paquets partagés.

Créez le dépôt GitHub comme ci-dessus, puis :

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/aeac-2027 formation-5-<cohorte>
cd formation-5-<cohorte>
git remote set-url origin https://github.com/zenith-polymtl/formation-5-<cohorte>
```

Retirez ce qui ne sert pas à la formation : les workspaces de mission de la saison en cours (`workspaces/<mission>_ws/`) et leurs `config/<mission>.yaml`. Gardez `gcs_ws` (la formation 5.1 le construit et écoute son heartbeat), `vision_ws`, `packages/` au complet, `docker/`, `compose/`, `config/`, `systemd/`, `scripts/` et les quatre documents de la racine. Ne mettez pas `demo_ws` : c'est la recrue qui le copie depuis le dossier de la formation en 5.2, et `demo_monitor` en 5.3. Retirer un `workspaces/<mission>_ws/` sans retirer `gcs_ws/src/gcs_bringup/launch/<mission>.launch.py` laisse un launch orphelin que `make check` ne voit pas.

```bash
make init && make check
git add -A && git commit -m "Trim competition missions for the cohort repository"
git push -u --recurse-submodules=on-demand origin main
```

`--recurse-submodules=on-demand` est ce qui garantit que les pointeurs de sous-modules visent des commits réellement poussés ; sans lui, un pointeur peut désigner un commit qui n'existe que sur votre machine, et le `git clone --recurse-submodules` de la première recrue échoue. `make init` le règle une fois pour toutes dans un clone (`git config push.recurseSubmodules on-demand`), mais vérifiez-le sur la machine d'où vous créez le dépôt.

Côté GitHub, deux réglages : `main` protégée comme ci-dessus, et les recrues en écriture sur le dépôt, ce qui leur donne le droit de pousser leurs branches et d'ouvrir des PR sans pouvoir toucher à `main`.

## 2 - Ajouter une mission

Une mission, c'est trois choses, dit `ARCHITECTURE.md` : un workspace, une configuration, un launch sol.

1. `workspaces/<nom>_ws/src/<nom>_bringup/`, avec `launch/mission.launch.py` : c'est ce que `make drone C=<nom>` lance sur la Jetson et ce que `make sim C=<nom>` lance en simulation. Le même launch sert aux deux ; `sim:=true` passe un paramètre `sim` aux nœuds qui touchent au matériel, et `site:=<nom>` choisit `config/sites/<nom>.yaml`.
2. `config/<nom>.yaml` : tout ce qui se règle, au format paramètres ROS 2, une section par nœud. Le launch le charge et le passe aux nœuds. (La distinction entre un fichier de référence dans `<nom>_bringup/config/` et une copie de travail dans `config/` à la racine est la convention de `demo_ws`, pas une règle du dépôt de mission.)
3. `gcs_ws/src/gcs_bringup/launch/<nom>.launch.py` : ce que le portable lance pour cette mission, `make gcs C=<nom> DRONE=<drone>`.

Les paquets partagés se lient au nouveau workspace, un par un, et les liens se commettent :

```bash
make link C=<nom> PKG=tools && make link C=<nom> PKG=custom_interfaces && make link C=<nom> PKG=sim_mocks
```

Pensez à `sim_mocks` : c'est ce qui permet à `make shell IMG=sim` de trouver les mocks.

Puis la vérification, qui voit les `package.xml` incomplets et les liens cassés :

```bash
make check
```

Si la mission a un terrain à elle, ajoutez `config/sites/<terrain>.yaml` ; `make sim C=<nom> SITE=<terrain>` le charge.

## 3 - Ajouter un paquet partagé

La règle est dans `packages/README.md` et elle se lit dans ce sens : un paquet est **local** à sa mission sauf s'il sert ailleurs. S'il sert à deux workspaces du même dépôt, il vit dans `packages/` comme dossier simple, comme `sim_mocks`. S'il sert à deux dépôts, ou d'une année à l'autre, il devient un sous-module, et c'est un lead qui le décide.

Pour le sous-module : créez un dépôt GitHub avec le `package.xml` à la racine du dépôt, et non dans un sous-dossier, puis

```bash
git submodule add https://github.com/zenith-polymtl/<nom> packages/<nom>
```

Ajoutez une ligne dans le tableau de `packages/README.md` (paquet, type, rôle), liez-le aux workspaces qui l'utilisent avec `make link`, et commettez le tout.

Prévenez ensuite les autres dépôts qui suivent ce paquet : chez eux, `make bump PKG=<nom>` avance le pointeur sur `origin/main`, pose un tag daté et stage le pointeur. Un dépôt qui ne fait pas ce `bump` reste sur l'ancienne version, ce qui est le comportement voulu : un sous-module ne bouge que quand quelqu'un le décide.

L'opération inverse est dans `ARCHITECTURE.md`, section « Pour les leads » : `git submodule deinit packages/<nom>`, copier le dossier dans le workspace concerné, `git rm packages/<nom>`.

## 4 - Ajouter un conteneur

Deux fichiers, et un en-tête dans chacun.

Le Dockerfile va dans `docker/`, nommé `dockerfile.<rôle>`. Son en-tête dit où l'image tourne et **ce qui diffère** des autres images, parce que c'est la seule question que se pose le suivant. Celui de `docker/dockerfile.gcs` le fait en quelques lignes : image du portable et du poste de développement, rviz2, rqt et X11 en plus par rapport à `dockerfile.drone`, tout le reste identique volontairement. Quand une dépendance est épinglée, l'en-tête dit pourquoi : `dockerfile.vision` explique que numpy est tenu à 1.26.4 parce que torch et ultralytics sur Jetson ne supportent pas numpy 2.

Le compose va dans `compose/`, nommé `<nom>.yml`, un fichier par chose à lancer. Son en-tête dit qui le lance, à la main et au boot : `compose/mavros.yml` commence par « mavros vers le Pixhawk, sur la Jetson. `make mavros` à la main, `mavros.service` au boot. »

Ajoutez ensuite la cible dans le `Makefile`, dans la bonne section (`##@ 2. Test sur véhicule` pour ce qui se lance à la main sur le drone), avec son commentaire `##` : c'est lui que `make help` affiche.

```makefile
<nom>: ## Description courte (Jetson)
	docker compose -f compose/<nom>.yml up
```

Si le conteneur doit aussi démarrer au boot, ajoutez son nom à la variable `SERVICES` en haut du Makefile, et passez à la recette 5.

## 5 - Ajouter un service au boot

Un fichier `systemd/<nom>.service`, calqué sur ceux qui existent. `make deploy` remplace `__REPO__` par le chemin du dépôt et copie le fichier dans `/etc/systemd/system/`, donc écrivez `__REPO__` partout où le chemin du dépôt apparaît. Le nom du service doit figurer dans la variable `SERVICES` du Makefile, sinon `make deploy` l'ignore.

L'ordre au boot se déclare avec `After=` et se lit dans `systemd/install.md` : `lo-multicast`, puis `mavros` (qui attend `/dev/ttyTHS1`), `zed` (qui attend la caméra), `zenoh-air`, `vision`, `mission`. Un service qui a besoin d'un autre le nomme ; un service qui attend du matériel l'attend explicitement plutôt que de compter sur un délai.

Vérifiez avec `make <nom>-status` et `make <nom>-logs`, et rappelez-vous que systemd n'est qu'un emballage : `make undeploy` puis la cible `make` correspondante relance exactement la même chose en avant-plan. Le détail des services et du réseau est le sujet de la formation 6 ; ici il s'agit seulement de savoir où le fichier se met.

## 6 - Faire évoluer

**Avancer un paquet partagé.** Quand une PR est fusionnée dans le dépôt d'un sous-module, les dépôts qui le suivent ne bougent pas tout seuls :

```bash
make bump PKG=tools
```

La cible fetch `origin`, affiche les commits gagnés, se place sur `origin/main`, pose un tag daté du nom du dépôt, et stage le pointeur. Il reste à commettre et à pousser :

```bash
git commit -m "bump tools" && git push --recurse-submodules=on-demand
```

**Déployer sur la Jetson.** `make deploy C=<mission>` installe les services depuis `systemd/`, écrit la mission dans `/etc/aeac/mission` et les active. `make deploy C=<autre>` change la mission au boot. `make undeploy` rend la main pour un test manuel. La marche à suivre complète est dans `systemd/install.md`.

**Le reste.** La section « Pour les leads » d'`ARCHITECTURE.md` est la liste courte de ces gestes, et c'est elle qu'il faut tenir à jour : contribuer à un paquet partagé, en créer un, en sortir un du partage, déployer, les modèles de vision.

**Après la compétition.** Un tag `<compétition>-<année>` sur `main`, puis la suppression des workspaces et des paquets de mission qui ne serviront plus. Le tag est ce qui permet de revenir au dépôt tel qu'il a volé, une fois qu'on l'a vidé pour l'année suivante.
