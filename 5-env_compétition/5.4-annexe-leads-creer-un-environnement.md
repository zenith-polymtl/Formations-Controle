# Annexe 5.4, pour les leads : créer et faire évoluer l'environnement

Cette annexe n'est pas un exercice : la recrue la parcourt une fois pour savoir qu'elle existe. Elle donne aux leads les gestes pour fabriquer un repo de mission et le faire évoluer, avec les commandes exactes du repo. Les six recettes sont indépendantes ; lisez celle dont vous avez besoin.

---

## 1 - Créer un repo de mission à partir de `mission-template`

`mission-template`, le repo public `zenith-polymtl/mission-template`, est le squelette des repos de compétition : le Makefile, les conteneurs, la configuration, `gcs_ws`, `vision_ws`, `packages/sim_mocks`, les cinq submodules de `packages/` et les liens déjà posés dans les workspaces. Il ne contient aucune mission. Ses fichiers sont ceux d'`aeac-2027`, sauf le `README.md`. Quand l'architecture change dans un repo de compétition, reportez le changement dans le template : c'est lui que les recrues lisent, et c'est de lui que partiront les prochains repos (`suas-2027`, `aeac-2028`).

La recette tient en quatre gestes, une fois par repo. Ce sont ceux de la section « Créer un repo de mission à partir de ce template » du `README.md` du template.

D'abord le repo distant. Sur GitHub, ouvrez `zenith-polymtl/mission-template` et cliquez **Use this template → Create a new repository**, dans l'organisation `zenith-polymtl`. Dans **Settings → Collaborators and teams**, donnez l'accès en écriture à l'équipe contrôle.

Ensuite le clone, dans WSL :

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/<nouveau-repo>
```

```bash
cd <nouveau-repo>
```

```bash
make init
```

```bash
make check
```

Sur un clone neuf, `make check` répond `check : rien à signaler`.

Puis vérifiez `.gitmodules`. Un submodule pointe un commit, pas une branche : la ligne `branch =` dit seulement où `make bump` ira chercher le commit suivant, et c'est `main` quand la ligne manque. Dans le template, `tools` et `custom_interfaces` suivent `aeac-2027`, la branche où vivent `topics.py` et `MissionState.msg`, pas encore mergée dans leur `main`. Un nouveau repo hérite de ces lignes. Une fois cette branche mergée, retirez les deux lignes `branch = aeac-2027` dans un commit.

Enfin, protégez `main` avant que quiconque clone : **Settings → Branches → Add branch ruleset**, sur `main`, pull request obligatoire, un lead merge. La règle « `main` = ce qui vole » ne tient que si GitHub la fait tenir.

**Le template et la formation.** Les recrues de la formation 5 clonent `mission-template` lui-même, y copient la démo et y poussent leur branche en 5.3. Donnez donc à l'équipe contrôle le droit d'écriture sur le template, pour les branches ; `main` reste protégée. Un lead relit chaque PR avec la grille de [`5.3-projet/solution/CHECKLIST.md`](5.3-projet/solution/CHECKLIST.md), la ferme sans merge et supprime la branche : le template ne contient jamais de mission. Avant de pousser un nouveau pointeur de submodule dans le template, poussez le submodule lui-même (`git push --recurse-submodules=on-demand`, que `make init` règle par défaut) : un pointeur vers un commit absent de GitHub fait échouer le clone de la recrue suivante.

## 2 - Ajouter une mission

Une mission, c'est trois choses (`ARCHITECTURE.md`, section « Une mission ») : un workspace, un fichier de configuration et un launch file pour le sol. Les commandes se tapent dans WSL, à la racine du repo ; remplacez `<nom>` par le nom de la mission.

Le workspace d'abord. `make link` a besoin que son dossier `src/` existe :

```bash
mkdir -p workspaces/<nom>_ws/src
```

Puis un lien par package partagé :

```bash
make link C=<nom> PKG=tools
```

```bash
make link C=<nom> PKG=custom_interfaces
```

```bash
make link C=<nom> PKG=sim_mocks
```

`sim_mocks` est ce qui permet à `make rc` et `make takeoff` de trouver les mocks en simulation. Posez les liens depuis WSL : sous Windows, git enregistre un symlink comme un fichier texte. Les liens entrent dans un commit ; celui qui clone ou copie le workspace le reçoit déjà lié, comme `demo_ws` en 5.2.

Ensuite le package `<nom>_bringup`, dans `workspaces/<nom>_ws/src/`, avec `launch/mission.launch.py`. Le modèle est `demo_bringup`, dans `5-env_compétition/demo_ws/src/` : copiez-le, remplacez `demo` par `<nom>` dans le nom du dossier, dans `package.xml`, `setup.py`, `setup.cfg`, le fichier de `resource/` et le launch file, et supprimez son dossier `config/`, qui ne sert qu'à la formation. Son launch file a la forme attendue : deux arguments, `sim` et `site`, et une node qui reçoit `/aeac/config/<nom>.yaml` puis `/aeac/config/sites/<site>.yaml`.

Puis `config/<nom>.yaml`, sur le modèle de l'exemple de `config/README.md` : une section par node, au format paramètres ROS 2.

Enfin, pour le sol, `workspaces/gcs_ws/src/gcs_bringup/launch/<nom>.launch.py`. Il inclut `base.launch.py` (la docstring de ce fichier donne les lignes à copier) et ajoute les nodes sol de la mission ; `make gcs C=<nom> DRONE=<drone>` le lance.

Construisez, puis vérifiez les `package.xml` et les liens :

```bash
make build C=<nom>
```

```bash
make check
```

Si la mission a un terrain à elle, ajoutez `config/sites/<terrain>.yaml` sur le modèle de `cimetiere.yaml` (la cible en mètres depuis le home, là où le pilote arme) ; `make sim C=<nom> SITE=<terrain>` le charge. Sur la Jetson, le terrain de vol est `SITE` dans le `.env` du repo : `make drone` et `mission.service` le passent en `site:=`, et refusent de lancer la mission s'il manque (`systemd/install.md`).

**Un launch file de simulation.** Aucun launch file de mission n'inclut un mock : c'est ce qui garantit qu'un mock ne vole jamais. Rien n'interdit en revanche un `sim.launch.py` réservé à la simulation, qui inclut `mission.launch.py` et démarre les mocks, derrière une cible make dont le nom dit qu'elle ne sert qu'au sol.

## 3 - Ajouter un package partagé

La règle est dans `packages/README.md` : un package est local à sa mission sauf s'il sert ailleurs. S'il sert à deux workspaces du même repo, il vit dans `packages/` comme dossier ordinaire, comme `sim_mocks`. S'il sert à deux repos, ou d'une année à l'autre, il devient un submodule.

Pour un submodule, créez un repo GitHub dans `zenith-polymtl` avec le `package.xml` à sa racine (pas dans un sous-dossier), puis :

```bash
git submodule add https://github.com/zenith-polymtl/<nom> packages/<nom>
```

Ajoutez sa ligne au tableau de `packages/README.md`, liez-le aux workspaces qui l'utilisent avec `make link` (recette 2), et faites un commit du tout. L'opération inverse, sortir un package du partage, est dans `ARCHITECTURE.md`, section « Pour les leads ».

## 4 - Ajouter un conteneur

Deux fichiers, chacun avec un en-tête. Le Dockerfile va dans `docker/dockerfile.<rôle>`. Son en-tête dit où l'image tourne et ce qui diffère des autres images, comme celui de `docker/dockerfile.gcs`, et pourquoi une dépendance est épinglée, comme le numpy de `docker/dockerfile.vision`. Le compose va dans `compose/<nom>.yml`, un fichier par chose à lancer ; son en-tête dit qui le lance, à la main et au boot, comme celui de `compose/mavros.yml`. `make check` signale un Dockerfile qu'aucun compose ne construit.

Ajoutez la cible dans la section 2 du `Makefile`, avec son commentaire `##`, que `make help` affiche :

```makefile
<nom>: ## Description courte (Jetson)
	docker compose -f compose/<nom>.yml up
```

Si le conteneur doit démarrer au boot, passez à la recette 5.

Les cibles de confort de la section 1 (`make shell`, `make takeoff`, `make rc`, `make echo`) ne font rien qu'un `docker exec` ne ferait : elles évitent de le retaper. Ajoutez-en librement, avec un nom explicite et sa ligne `##`.

## 5 - Ajouter un service au boot

Un fichier `systemd/<nom>.service`, calqué sur ceux qui existent, avec `__REPO__` partout où le chemin du repo apparaît : `make deploy` le remplace par le vrai chemin et copie le fichier dans `/etc/systemd/system/`. Ajoutez le nom du service à la variable `SERVICES` du Makefile, sinon `make deploy` l'ignore.

L'ordre au boot se déclare avec `After=`. Un service qui attend du matériel l'attend explicitement, comme le `ExecStartPre=` de `mavros.service` qui attend le port série, plutôt que de compter sur un délai. Vérifiez avec `make <nom>-status` et `make <nom>-logs`. Le détail des services est le sujet de la formation 6.

## 6 - Faire évoluer

**Avancer un package partagé.** Quand une PR est mergée dans le repo d'un submodule, les repos de mission ne bougent pas tout seuls :

```bash
make bump PKG=tools
```

La cible lit la branche suivie dans `.gitmodules` (`main` sinon), affiche les commits gagnés, place le submodule sur cette branche, pose un tag daté et stage le pointeur. Si le commit actuel du submodule n'est pas dans cette branche, elle refuse, parce que le pointeur reculerait : c'est à un lead de trancher. La PR du submodule doit donc viser la branche suivie. Restent le commit et le push :

```bash
git commit -m "bump tools"
```

```bash
git push --recurse-submodules=on-demand
```

**Déployer sur la Jetson.** `make deploy C=<mission>` installe les services et fixe la mission au boot. Pour changer de mission, `make deploy C=<autre>` puis `make mission-restart`. `make undeploy` rend la main pour un test manuel. La marche à suivre est dans `systemd/install.md`.

**Après la compétition.** Un tag `<compétition>-<année>` sur `main`, puis la suppression des workspaces et des packages de mission qui ne serviront plus. Le tag garde le repo tel qu'il a volé.

La section « Pour les leads » d'`ARCHITECTURE.md` est la liste courte de ces gestes : tenez-la à jour quand un geste change.
