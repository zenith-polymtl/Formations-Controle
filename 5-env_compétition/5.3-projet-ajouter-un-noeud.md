# Formation 5.3 : projet, ajouter un nœud à la démo

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Ajouter un nœud à un workspace de mission en respectant les règles de code du dépôt
- Déclarer un nouveau topic au bon endroit, et le rendre externe ou interne en le nommant
- Donner des réglages à votre nœud sans écrire une valeur dans le code
- Passer `make check`, ouvrir une PR et la faire relire

Prérequis : la [formation 5.2](5.2-une-mission-en-simulation.md) terminée (la démo tourne en simulation, la machine à états passe par ses quatre états, le waypoint vient d'un YAML que vous avez modifié).

Jusqu'ici vous avez habité le dépôt. Ici vous y ajoutez quelque chose. Le nœud demandé est petit et volontairement inoffensif, parce que ce n'est pas lui qui est difficile : ce qui compte est qu'il oblige à toucher aux cinq points de contact d'un nœud avec le dépôt : un paquet, un `package.xml`, une constante dans `topics.py`, un launch, la config.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 2 h, dont un quart d'heure de rappel git.
> - **Prérequis** : 5.2 faite, et la démo qui tourne avec `make sim C=demo`.
> - **À la fin** : une PR ouverte sur le dépôt de cohorte, et `make check` qui ne dit plus rien sur votre paquet.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : le lien de votre PR, et une capture du nouveau topic vu depuis un second terminal.

Rappel de 5.1 et 5.2, parce qu'il va servir dix fois : le shell ouvert par `make shell` ne source rien tout seul, donc `source /opt/ros/humble/setup.bash && source install/setup.bash` dans chaque terminal que vous ouvrez dans un conteneur.

## 1 - Le cahier des charges

Un nœud `mission_monitor`, dans un paquet `demo_monitor`, qui s'abonne à l'état de la mission et à `/mavros/battery`, et publie un résumé sur un topic externe à 1 Hz : l'état courant, la tension, le temps passé dans l'état. Il n'arme rien, ne commande rien, il regarde. C'est le nœud le plus simple qui oblige à toucher à tout : un paquet, un `package.xml`, une constante dans `topics.py`, un launch, la config.

Le résumé est un `std_msgs/String` qui contient du JSON sur une ligne :

```json
{"state": "GOTO", "voltage": 15.8, "time_in_state": 12.4}
```

L'énoncé complet, la liste des fichiers à toucher et la grille que le lead utilisera pour relire votre PR sont dans [`5.3-projet/README.md`](5.3-projet/README.md). Lisez-le en entier avant d'écrire une ligne : il est votre cahier des charges, ce document est votre mode d'emploi.

## 2 - Le squelette et les règles

### 2.1 - Copier le squelette

Le squelette est fourni, comme la node de téléop de la formation 3.4. Depuis la racine de votre clone de `formation-5-automne-2026`, en remplaçant `<dossier de la formation>` par le chemin où vous avez le dépôt Formations-Controle :

```bash
cp -r <dossier de la formation>/5-env_compétition/5.3-projet/squelette/demo_monitor workspaces/demo_ws/src/
```

Le paquet se pose à côté de `demo_bringup` et `demo_mission`, dans le même `src/` : la règle de `packages/README.md` dit qu'un paquet est local à sa mission sauf s'il sert ailleurs, et celui-ci ne sert qu'ici.

```bash
make build C=demo
```

`make build C=demo` réussit : le paquet compile tel quel. Il n'y a rien à observer de plus pour l'instant, le nœud n'est pas encore dans le launch et `topics.DEMO_SUMMARY` n'existe pas encore. Il reste six `# TODO n :`, tous dans `demo_monitor/demo_monitor/monitor.py`.

### 2.2 - Les six TODO

Ouvrez `workspaces/demo_ws/src/demo_monitor/demo_monitor/monitor.py`. Les imports, la classe, le paramètre, les deux abonnements, le publisher et le timer sont écrits. Les six trous sont à quatre endroits :

| TODO | Où | Ce qui manque |
|---|---|---|
| 1 | `format_summary` | Le dictionnaire des trois champs, rendu en JSON |
| 2 et 3 | `state_callback` | Loguer la transition, retenir l'état et le temps reçu |
| 4 et 5 | `battery_callback` | Retenir la tension, avertir une fois sous le seuil |
| 6 | `tick` | Publier le résumé |

Deux callbacks qui ne font que retenir, un timer qui publie, une fonction de mise en forme qui ne connaît pas ROS. Cette dernière, `format_summary`, est une fonction de module et pas une méthode : elle n'appelle rien de ROS, donc elle se vérifie dans un `python3` nu, sans conteneur et sans simulation.

### 2.3 - Les six règles, et la ligne qui les respecte

**Six règles de code**, celles que ce nœud rencontre, chacune avec l'endroit du squelette ou de la solution où elle se voit. Elles viennent d'`ARCHITECTURE.md`, section « Règles de code ».

**1. Le nom du topic vient de `topics.py`**, jamais d'une chaîne écrite dans le nœud : ligne 64 du squelette, `self.create_publisher(String, topics.DEMO_SUMMARY, 10)`, et la ligne à ajouter dans `topics.py` est `DEMO_SUMMARY = f'{EXTERNAL}/demo/summary'`. `/mavros/battery` reste une constante de module du nœud, ligne 25 : `topics.py` ne décrit que les topics `/aeac` écrits par l'équipe.

**2. L'état se compare à une constante de `MissionState`**, jamais à `'IDLE'` ni à `0` : le dict `LABELS` est indexé par `MissionState.IDLE`, `.GOTO`, `.ACT` et `.RETURN`, lignes 27 et 28 du squelette, et c'est le seul endroit du fichier où les noms d'états apparaissent en texte. Dans `state_callback`, la transition se repère en comparant `msg.state` à l'état retenu, jamais à une chaîne.

**3. Pas de `time.sleep` dans un callback**, parce qu'un `sleep` bloque l'exécuteur et donc tous les autres callbacks du nœud : ligne 66 du squelette, `self.timer = self.create_timer(1.0, self.tick)`.

**4. `package.xml` déclare ce qui est importé**, sinon le nœud marche chez celui qui l'a écrit et casse au premier clone propre : les cinq `<depend>` du squelette, `rclpy`, `std_msgs`, `sensor_msgs`, `tools` et `custom_interfaces`. Notez `sensor_msgs` et non `mavros_msgs` pour `BatteryState` ; vérifiez-le avec `ros2 interface show sensor_msgs/msg/BatteryState`.

**5. Le résumé est externe parce que le sol veut le voir**, et le préfixe suffit : `DEMO_SUMMARY` est construit à partir de `EXTERNAL`, donc le topic traverse la radio, alors qu'un topic sous `INTERNAL` reste sur la machine. La formation 6 montre ce qui se passe derrière, du côté de Zenoh.

**6. Logs en français, `INFO` pour les événements, jamais du périodique**, parce qu'un log à chaque tour de timer rend le journal inutilisable le soir d'un vol raté : lignes 81 et 98 de la solution, un `INFO` par transition d'état et un `WARN` au passage sous `battery_warn_v`, une seule fois, rien dans `tick()`. Le TODO 5 vous demande une marge pour réarmer ce `WARN` (`BATTERY_REARM_MARGIN_V = 0.3` dans la solution, ligne 34).

### 2.4 - `topics.py` est dans un sous-module

`packages/tools` n'est pas un dossier du dépôt de mission : c'est un autre dépôt, attaché ici comme sous-module. Dans la vraie vie, ajouter `DEMO_SUMMARY` veut donc dire ouvrir une PR dans le dépôt `tools`, la faire relire, puis avancer le pointeur du dépôt de mission avec `make bump PKG=tools`. C'est lent exprès : un nom de topic est une frontière entre les équipes.

Pour la formation, vous ne faites pas cette PR. Ouvrez `packages/tools/tools/topics.py` et ajoutez, sous `DEMO_STATE` :

```python
DEMO_SUMMARY = f'{EXTERNAL}/demo/summary'
```

`make status` dira alors que `tools` est modifié localement :

```bash
make status
```

```
Branche : main
 9ab2274ab96d2e2f4829baa2691c71466bf526b1 packages/tools (heads/aeac-2027)
 M packages/tools
```

La ligne des sous-modules reste à jour : le commit pointé n'a pas bougé, seul son contenu a changé. C'est le `git status` du bas de `make status` qui le dit, avec ` M packages/tools`.

C'est attendu, et c'est la seule fois de la formation où on l'accepte. La règle de 5.1 reste la règle : un sous-module modifié localement se signale à un lead avant d'aller plus loin. Ici le lead, c'est nous, et la réponse est écrite d'avance : gardez la modification locale, ne la commettez pas, et décrivez la ligne dans votre PR pour que le lead la porte dans `tools`. La section 4 dit comment la tenir hors de votre commit.

## 3 - Brancher et vérifier

### 3.1 - Le launch

Le moniteur doit démarrer et s'arrêter avec la mission : personne ne doit avoir à penser à le lancer. Il devient donc un second `Node` dans le launch de la démo. Ouvrez `workspaces/demo_ws/src/demo_bringup/launch/mission.launch.py` et ajoutez ce bloc dans `launch_setup`, après le `Node` de `demo_mission` :

```python
        Node(
            package='demo_monitor',
            executable='monitor',
            name='mission_monitor',
            output='screen',
            parameters=[
                f'{CONFIG_DIR}/demo.yaml',
            ],
        ),
```

Le moniteur reçoit `config/demo.yaml` tel quel, le même fichier que le nœud de mission. Il ne reçoit pas les paramètres du site : il ne vole pas, il regarde.

### 3.2 - La config, et le piège du fichier de paramètres

Un fichier de paramètres ROS 2 est indexé par nom de nœud : le premier niveau du YAML est le nom du nœud qui recevra les clés qui suivent. `config/demo.yaml` commence par `demo_mission:`, donc un nœud nommé `mission_monitor` n'y lit rien, et il n'y lit rien silencieusement, sans erreur ni avertissement, en gardant les défauts écrits dans son code.

Le moniteur a donc sa propre section dans le même fichier. Ouvrez `config/demo.yaml` à la racine du clone, et ajoutez à la fin :

```yaml
mission_monitor:
  ros__parameters:
    battery_warn_v: 14.0     # tension sous laquelle le moniteur avertit une fois, volts
```

C'est le cinquième point de contact du projet, « la config », et le seul qui ne se voit pas dans le code. Le seuil n'est écrit nulle part dans le nœud autrement que comme valeur par défaut de déclaration, ligne 50 du squelette : ce qui fait foi est dans `config/`.

Attention à l'endroit : `config/demo.yaml` à la racine du clone est celui que le launch lit, sous le nom `/aeac/config/demo.yaml`. Le fichier de même nom dans `workspaces/demo_ws/src/demo_bringup/config/` est la copie d'origine du workspace, et modifier celui-là ne change rien à ce qui se lance. Vous avez déjà rencontré ce piège en 5.2 avec le YAML de site.

### 3.3 - Construire et lancer

```bash
make build C=demo
```

```bash
make sim C=demo
```

Au milieu des lignes de mavros et de la mission, la ligne du moniteur :

```
[monitor-2] [INFO] [mission_monitor]: Surveillance de la mission démarrée : résumé sur /aeac/external/demo/summary, alerte sous 14.0 V.
```

Le SITL de Mission Planner doit tourner, comme en 5.2 : sans lui, mavros n'a personne à qui parler et vous n'aurez jamais de tension.

### 3.4 - Le topic dans un second terminal

```bash
make shell C=demo IMG=sim
```

```bash
source /opt/ros/humble/setup.bash && source install/setup.bash
```

Le nœud et son topic n'existent que maintenant, une fois le launch modifié et `DEMO_SUMMARY` ajouté dans `topics.py` :

```bash
ros2 node list | grep monitor          # /mission_monitor
```

```bash
ros2 topic list | grep summary         # /aeac/external/demo/summary
```

```bash
ros2 topic echo --once /aeac/external/demo/summary
```

```
data: '{"state": "IDLE", "voltage": 12.59, "time_in_state": 3.4}'
---
```

Et la preuve que le seuil vient du YAML et pas du code :

```bash
ros2 param get /mission_monitor battery_warn_v
```

```
Double value is: 14.0
```

Ce `14.0` ne prouve rien tout seul, puisque c'est aussi le défaut écrit dans le code. Changez la valeur du YAML pour `13.1`, relancez `make sim C=demo`, redemandez le paramètre : si le nœud suit, votre section est bien lue ; s'il reste à `14.0`, relisez la section 3.2.

### 3.5 - `make check`

`make check` lit le dépôt et sort une ligne par problème, au format `chemin: message`. Lancez-le depuis la racine du clone, dans WSL, hors conteneur :

```bash
make check
```

```
packages/vision/vision/package.xml: licence à remplir (Apache-2.0)
packages/vision/vision/package.xml: description à remplir
packages/vision/vision/test: dossier test/ généré par ros2 pkg create : à supprimer (pas de tests dans ce dépôt)
packages/nav_stack/nav_stack/package.xml: mainteneur à remplir
packages/nav_stack/nav_stack/package.xml: licence à remplir (Apache-2.0)
packages/nav_stack/nav_stack/package.xml: description à remplir
packages/nav_stack/nav_stack/test: dossier test/ généré par ros2 pkg create : à supprimer (pas de tests dans ce dépôt)
workspaces/demo_ws/src/demo_monitor/package.xml: mainteneur à remplir
workspaces/demo_ws/src/demo_monitor/package.xml: licence à remplir (Apache-2.0)
workspaces/demo_ws/src/demo_monitor/package.xml: description à remplir
```

Dix lignes, et elles ne sont pas toutes à vous. Les sept premières portent sur `vision` et `nav_stack` : elles étaient là avant vous et elles y seront encore après votre PR. Ne les corrigez pas, ce sont des sous-modules, et les toucher vous mettrait dans la situation que la section 2.4 vous demande d'éviter. L'ordre des lignes peut différer chez vous.

Les trois dernières sont les vôtres, et elles sont l'exercice. Le squelette est livré avec les trois champs que `ros2 pkg create` laisse en place. Ouvrez `workspaces/demo_ws/src/demo_monitor/package.xml` et remplissez :

- `<maintainer email="...">` : votre nom et un courriel où on peut vous joindre.
- `<license>` : `Apache-2.0`, comme le reste du dépôt.
- `<description>` : une phrase qui dit ce que le paquet fait.

Puis les mêmes champs dans `setup.py` : `maintainer`, `maintainer_email`, `description`, `license`. `check.py` ne regarde pas `setup.py`, et ce n'est pas parce que l'outil ne le voit pas que c'est fini. Le lead, lui, le regarde.

`make check` doit ensuite ne plus rien dire sur `demo_monitor`. Il sortira toujours en erreur à cause des sept lignes de `vision` et `nav_stack`, et c'est normal.

## 4 - Rappel git, puis branche et PR

Un quart d'heure. Git a été vu en formation 0, section 3 : un commit, un push, un clone. On ne le réenseigne pas, on l'applique au travail que vous venez de faire.

Trois règles, et rien d'autre :

1. Une branche par tâche. `main` ne se pousse jamais directement, ni ici ni dans le dépôt de compétition.
2. Un message de commit en anglais, sur une ligne, qui dit ce que le commit change.
3. `make check` avant d'ouvrir la PR.

Les commandes, dans l'ordre où vous les tapez.

```bash
git status
```

Ce que git voit : les fichiers modifiés, les fichiers nouveaux, et la ligne `packages/tools (modified content)` qui dit que le sous-module `tools` a changé chez vous. Cette ligne est normale, c'est la section 2.4.

```bash
git switch -c prenom/monitor
```

Crée une branche à votre nom et s'y place. Le préfixe `prenom/` est la convention du dépôt : en lisant la liste des branches, on sait à qui parler.

```bash
git add workspaces/demo_ws config/demo.yaml
```

On nomme ce qu'on commet, jamais `git add -A` : votre clone contient aussi `NOTES.md`, `pannes/` et `config/sites/`, qui ne font pas partie de cette PR. Relisez ensuite ce qui est stagé :

```bash
git status --short
```

`git status --short` montrera aussi ` M packages/tools`. Il n'y a rien à refuser : ne tapez simplement jamais `git add packages/tools`. Un pointeur de sous-module commis pointerait vers un commit qui n'existe que chez vous, et le clone suivant échouerait.

Ce que vous commettez, c'est tout `workspaces/demo_ws` (les trois paquets `demo_bringup` avec son launch modifié, `demo_mission` et votre `demo_monitor`) et `config/demo.yaml`.

```bash
git commit -m "Add mission_monitor node to the demo workspace"
```

La photo, avec son message. En anglais, sur une ligne, au présent.

```bash
git push -u origin prenom/monitor
```

Envoie la branche sur GitHub. `-u` mémorise le lien, les `git push` suivants n'auront plus besoin d'arguments.

Ouvrez ensuite `https://github.com/zenith-polymtl/formation-5-automne-2026` dans le navigateur : GitHub propose votre branche en haut de la page, avec un bouton **Compare & pull request**. La description de la PR dit ce que le nœud fait, et surtout elle contient la ligne de `topics.py` que vous n'avez pas commise :

```
tools/topics.py : DEMO_SUMMARY = f'{EXTERNAL}/demo/summary'
```

C'est ce que le lead portera dans le dépôt `tools`.

Le lead relit ensuite avec la grille de [`5.3-projet/solution/CHECKLIST.md`](5.3-projet/solution/CHECKLIST.md) : six règles de code, et ce qui se vérifie autour. Elle est publique, vous pouvez la lire avant de déposer votre PR, et c'est même une bonne idée. La PR n'est pas un examen, c'est le prétexte à la conversation.

## 5 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `ModuleNotFoundError: No module named 'tools'` | Le lien vers le paquet partagé manque, ou le workspace n'est pas sourcé dans ce terminal | `make link C=demo PKG=tools`, `make build C=demo`, puis `source /opt/ros/humble/setup.bash && source install/setup.bash` |
| `make check` rouge sur le `package.xml` de `demo_monitor` | Les trois métadonnées que le squelette laisse vides | Les remplir, c'est l'exercice (section 3.5) |
| Le topic apparaît dans `ros2 topic list` mais `ros2 topic echo` n'affiche rien | Le TODO 6 n'est pas écrit : le nœud crée son publisher et ne publie jamais | Relire `tick()` |
| Le topic ne s'appelle pas `/aeac/external/demo/summary` | Un nom de topic écrit en clair dans le nœud au lieu de `topics.DEMO_SUMMARY` | `grep -rn "/aeac" workspaces/demo_ws/src/demo_monitor` |
| `ros2 param get` renvoie `14.0` alors que le YAML dit autre chose | Les clés sont sous `demo_mission:` au lieu d'une section `mission_monitor:`, ou c'est le mauvais `demo.yaml` qui a été modifié | Section 3.2 |
