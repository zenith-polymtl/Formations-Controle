# Formation 5.1 : le repo vu de haut

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Nommer les trois machines (poste WSL, Jetson, portable GCS), leurs régimes (développement, simulation, test, déploiement, vol) et ce qui tourne sur chacune
- Nommer chaque dossier du repo de mission, dire ce qu'on y met et pourquoi ce dossier existe
- Lire `make help` en trois sections et savoir laquelle vous concerne
- Cloner, initialiser et construire un repo de mission sans aide
- Réciter les règles du repo

Prérequis : les formations 2 et 3 terminées (WSL, Docker, Compose et Make en place ; un node ROS 2 écrit, lancé par un launch file et une cible make), et la formation d'introduction aux drones. La formation 4 n'est pas nécessaire : le simulateur utilisé ici est le SITL de Mission Planner.

Les formations 2 et 3 vous ont appris des outils. Ici les outils sont les mêmes, c'est la structure qui est nouvelle. Le repo de compétition fait vivre ensemble plusieurs missions, plusieurs conteneurs, plusieurs ordinateurs et plusieurs opérateurs. Chaque dossier existe pour une de ces raisons : le Dockerfile unique de la formation 2 est devenu un dossier `docker/` avec un fichier par rôle, le compose unique est devenu un dossier `compose/` avec un fichier par chose à lancer, et le Makefile qui coordonnait deux commandes en coordonne maintenant trois régimes. Même boîte à outils, rangée pour une équipe.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 1 h 45, dont une dizaine de minutes de visite du repo et une quinzaine de construction Docker pendant lesquelles on lit la suite.
> - **Prérequis** : formations 2 et 3 faites. Docker démarre sous WSL, `make` est installé, et vous avez un compte GitHub dans l'organisation `zenith-polymtl`.
> - **À la fin** : le conteneur de développement ouvert, le workspace `gcs_ws` construit, et le heartbeat du sol qui défile dans un `ros2 topic echo`.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une photo du schéma dessiné à la main (section 1.5) et une capture de `make status` (section 4.2).

Le repo que vous clonez est le repo template, `mission-template`. C'est le squelette dont les repos de compétition sont issus : les mêmes submodules, les mêmes conteneurs, les mêmes packages partagés, sans le code de mission. Votre clone est à vous, vous pouvez le casser. Le repo de compétition `aeac-2027`, lui, n'est jamais touché par la formation.

## 1 - Cloner, puis lire ARCHITECTURE.md

### 1.1 - On clone maintenant, on comprend après

La page que vous allez lire est dans le repo. On clone donc avant de comprendre, et le clone prend une seule commande :

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/mission-template
```

```bash
cd mission-template
```

Copiez l'option `--recurse-submodules` telle quelle : elle ramène les packages partagés, et la section 4 explique pourquoi.

### 1.2 - Quatre mots avant de lire

`ARCHITECTURE.md` emploie quatre mots que vous n'avez pas encore rencontrés. Les voici avant que vous les lisiez en contexte.

> [!NOTE]
> **Quatre mots avant de lire**
> - **systemd** : le programme qui lance des commandes au démarrage d'un ordinateur Linux, sans personne au clavier. Sur le drone, c'est lui qui démarre nos conteneurs quand on branche la batterie.
> - **Zenoh** : le pont qui fait passer certains topics par la radio, entre le drone et le sol. Sans lui, un topic publié sur le drone reste sur le drone.
> - **domaine ROS** : un numéro qui isole des réseaux ROS entre eux. Deux machines qui portent des numéros différents ne se voient pas, même branchées sur le même réseau.
> - **namespace de topics** : le début du nom d'un topic, ici `/aeac/external` ou `/aeac/internal`. C'est ce préfixe qui dit si le topic a le droit de traverser la radio.

Ouvrez maintenant `ARCHITECTURE.md`, à la racine. C'est une page, et c'est la seule lecture longue de la formation : prenez-y une demi-heure. Elle s'ouvre sur un arbre du repo, puis sur un schéma « qui tourne où », trois boîtes et une flèche. Regardez les deux avant de lire le texte. Ce que ce document ne dit pas, c'est comment la traversée de la radio se fait, avec quel logiciel et quelle configuration : c'est le sujet de la formation 6.

### 1.3 - Qui tourne où

Le tableau qui suit le schéma tient en cinq lignes, trois machines et cinq régimes :

| Machine | Régime | Ce qui tourne | Lancé par | Domaine ROS |
|---|---|---|---|---|
| Poste WSL | Développement | conteneur `dev` : coder, construire un workspace, rviz, `ros2 topic` | `make dev` | 3 |
| Poste WSL | Simulation | conteneur `dev`, où la mission est lancée avec `sim:=true`, et `mavros-sim` vers le SITL de Mission Planner | `make sim C=` | 3 |
| Jetson | Test sur véhicule | `mavros`, `zed`, `zenoh-air`, `vision`, la mission, en avant-plan | `make mavros`, `make drone C=` | 2 |
| Jetson | Déploiement | exactement les mêmes conteneurs, démarrés au boot | systemd (`make deploy`) | 2 |
| Portable GCS | Vol | conteneur `gcs` (workspace `gcs_ws`) et `zenoh-ground` | `make gcs C= DRONE=` | 3 |

Trois choses à retenir de ce tableau. Votre poste WSL est la seule machine que vous aurez pendant toute la formation 5 : les deux premières lignes sont les vôtres, les trois autres se lisent et ne se pratiquent pas. La Jetson est l'ordinateur embarqué sur le drone. Le test sur véhicule et le déploiement y lancent exactement les mêmes conteneurs, et la seule différence est qui appuie sur le bouton, vous à la main ou systemd au démarrage. Le portable GCS est l'ordinateur au sol le jour de la compétition ; le workspace qu'il fait tourner, `gcs_ws`, est celui que vous allez construire tout à l'heure.

La dernière colonne, le domaine ROS, sert à la suite : 2 sur la Jetson, 3 au sol et sur votre poste.

### 1.4 - Ce qui traverse la radio

Le drone et le sol sont deux mondes ROS séparés. Ce qui passe de l'un à l'autre passe par la radio, et c'est le nom du topic qui le décide : un topic `/aeac/external/...` traverse, un topic `/aeac/internal/...` reste sur le drone. C'est tout ce dont vous avez besoin ici.

## 3 - Le Makefile en trois sections

### 3.1 - make help

```bash
make help
```

```

1. Développement et simulation (poste WSL)
  help              Affiche cette aide
  print-vars        Affiche les variables résolues (pour déboguer)
  init              Après le clone : submodules, réglages git, dossiers ignorés. Sans risque à relancer.
  status            État de git et des submodules en une page
  check             Vérifie le repo (package.xml, liens, submodules, README). À lancer avant une PR.
  models            Télécharge les modèles de vision dans models/ (hors git)
  build             Construit le workspace de C dans le conteneur IMG (colcon)
  dev               Entre dans le conteneur de développement (tout le repo est monté dans /aeac)
  sim               Simulation de la mission C : mavros vers le SITL, puis le launch file dans le conteneur dev avec sim:=true et le site SITE
  shell             Ouvre un terminal dans le conteneur en cours (IMG=dev, gcs... pour en choisir un autre)
  down              Arrête tous les conteneurs aeac-* de ce poste (dev, mavros-sim, ...)
  logs              Suit les logs du conteneur en cours (IMG=mavros-sim pour ceux de mavros en simulation)
  takeoff           Arme et fait décoller le drone en simulation (node de test de sim_mocks)
  rc                Simule la manette au clavier (node de test de sim_mocks, garde le terminal)
  echo              Affiche un topic : make echo T=/aeac/internal/mission/state
  link              Lie un package partagé au workspace de C : make link C=water PKG=tools
  bag               Enregistre un rosbag daté dans bags/ (topics /aeac/* et mavros utiles)

2. Test sur véhicule (à la main, en avant-plan, Ctrl-C pour arrêter)
  mavros            mavros vers le Pixhawk (Jetson)
  zed               Caméra ZED (Jetson)
  zenoh-air         Pont Zenoh côté drone (Jetson)
  vision            Conteneur vision GPU (Jetson)
  drone             La mission C sur le drone (Jetson)
  gcs               Les nodes sol de la mission C + pont Zenoh vers DRONE (portable)

3. Déploiement (Jetson, systemd ; leads)
  deploy            Installe les services systemd depuis systemd/ et fixe la mission C au boot
  undeploy          Arrête et désactive tous les services (pour repasser en test à la main)
  %-status          État d'un service : make mavros-status, make mission-status, ...
  %-logs            Logs d'un service en direct : make mission-logs
  %-restart         Redémarre un service : make zenoh-air-restart
  bump              Avance un submodule sur origin/main et prépare le commit : make bump PKG=tools

Variables : C=gcs (mission)  IMG=dev (conteneur)  DRONE=hexa  SITE=sim (simulation)
Une commande qu'on retape souvent devient une cible d'ici : c'est fait pour.
```

Les trois sections sont les trois régimes du tableau de la section 1.3. La première est le poste WSL : c'est la vôtre, et c'est la seule que vous touchez pendant toute la formation 5. La deuxième est la Jetson ou le portable, à la main, en avant-plan, pour tester sur le véhicule. La troisième est le déploiement par systemd, réservée aux leads ; les cibles avec un `%` dedans s'utilisent en remplaçant le `%` par un nom de service, par exemple `make mission-logs`.

Lisez la dernière ligne de l'aide, elle dit quelque chose d'important. Quand une commande est longue et qu'on la retape dix fois par séance, on en fait une cible make. `takeoff`, `rc` et `echo` sont nées comme ça : elles remplacent trois commandes `ros2` qu'on tapait à la main dans le conteneur. Vous vous en servirez en 5.2.

La différence avec le Makefile de la formation 3.4 vaut la peine d'être notée. Là-bas, le Makefile était un raccourci devant un `docker compose`. Ici c'est l'interface du repo : chaque cible dit dans quel régime elle vous met, et la section dans laquelle elle est rangée dit sur quelle machine elle est censée tourner.

### 3.2 - Les variables

Quatre variables changent ce que font les cibles, et la fin de `make help` affiche toujours leurs valeurs courantes.

- `C=` est la mission, donc le workspace `workspaces/<C>_ws`. Par défaut `gcs`.
- `IMG=` est le conteneur dans lequel on travaille : `dev`, `drone`, `gcs` ou `vision`. Par défaut `dev`. C'est lui qui choisit le fichier de `compose/`.
- `DRONE=` est le fichier de configuration de la radio côté sol, `config/drones/<DRONE>.json5`. Par défaut `hexa`. Vous ne vous en servez pas dans cette formation.
- `SITE=` est le terrain en simulation, `config/sites/<SITE>.yaml`, `sim` par défaut. Vous le rencontrerez en 5.2.

`IMG=` n'est pas nécessaire pour `make shell`, ni pour `make logs` et `make bag`. Sur votre poste, un seul conteneur de travail tourne, `aeac-dev`, et ces trois cibles le trouvent toutes seules. `IMG=` sert à viser un autre conteneur, par exemple `make logs IMG=mavros-sim` en 5.2.

Pour voir ce que ça donne une fois résolu :

```bash
make print-vars
```

```
C=gcs  WS=workspaces/gcs_ws  IMG=dev  COMPOSE=compose/dev.yml  DRONE=hexa  SITE=sim  SITL_HOST=172.30.0.1
```

`SITL_HOST` est l'adresse où joindre le SITL de Mission Planner depuis un conteneur. Elle dépend de votre poste, et elle sert en 5.2. Trois cas :

- WSL en mode NAT, le cas par défaut : c'est l'adresse de Windows vue depuis WSL, et le Makefile la calcule tout seul avec `ip route`. La vôtre sera différente de celle ci-dessus.
- WSL en mode mirrored, ou Linux directement : `127.0.0.1`.
- Mac, avec Docker Desktop : `host.docker.internal`.

Si le calcul automatique tombe à côté, vous avez deux façons de le remplacer. Pour une fois : `make sim SITL_HOST=127.0.0.1`. Pour toujours : une ligne `SITL_HOST=127.0.0.1` dans un fichier `.env` à la racine, dont `.env.example` est le modèle à copier. `.env` est ignoré par git, donc votre réglage ne part sur le poste de personne.

## 4 - Initialiser et construire

L'ordre est celui du `README.md` du repo. À chaque commande, regardez ce qu'elle affiche : la phrase qui suit dit ce qu'elle a fait.

### 4.1 - make init

```bash
make init
```

```
Submodules initialisés, réglages git posés, dossiers models/ et bags/ créés.
```

Une ligne, trois choses faites. Elle remplit les submodules, et ne trouve rien à faire si vous avez cloné avec `--recurse-submodules`. Elle règle git pour que vos `git pull` et vos `git push` tiennent compte des submodules. Elle crée `models/` et `bags/`, deux dossiers ignorés par git. Elle est sans risque à relancer.

### 4.2 - make status

```bash
make status
```

Extrait de la sortie, la branche et les submodules :

```
Branche : main
Submodules (espace = à jour, + = commit différent du pointeur, - = non initialisé) :
 792d97ec77f009ee1d6126b2503a46d40a67ad57 packages/custom_interfaces (heads/aeac-2027)
 8f5f96bbcf79346562fea6de708658827eecb3cc packages/nav_stack (heads/main)
 9ab2274ab96d2e2f4829baa2691c71466bf526b1 packages/tools (heads/aeac-2027)
 2c837a1a28b0dca1cb747a039b6e7405ae9f8d09 packages/vision (heads/main)
 ff1bf990d34e271b6a6af23889113e60ae866877 packages/zed-ros2-wrapper (humble-v5.1.0-1-gff1bf99)
```

Vos identifiants de commit seront différents des miens. Ce qui compte est le premier caractère de chaque ligne, avant l'identifiant : un espace veut dire que le submodule est exactement sur le commit que le repo demande, un `-` qu'il est vide (vous avez oublié `--recurse-submodules`, et `make init` le règle), un `+` qu'il est sur un autre commit que celui attendu.

C'est ici que `packages/` devient concret. Un submodule est un repo dans un repo : le package partagé vit dans son propre repo GitHub, et celui-ci note seulement à quel commit il veut le voir. Ce qu'on vous demande d'en comprendre, et pas plus : savoir retrouver où vit un bout de code quand vous tombez sur un import, par exemple `tools.topics`, qui est dans `packages/tools/` et pas dans la mission ; et savoir que modifier un fichier là-dedans modifie un autre repo, qui sert à d'autres missions. Naviguer, pas administrer. Si `make status` dit qu'un submodule est modifié localement, demandez à un lead avant de continuer.

### 4.3 - make build C=gcs

```bash
make build C=gcs
```

C'est le quart d'heure de construction. Docker fabrique d'abord l'image à partir de `docker/dockerfile.gcs` (la première fois seulement), puis lance `colcon build --symlink-install` dans `workspaces/gcs_ws`. Vous voyez passer quatre packages : `custom_interfaces`, `tools`, `gcs_bringup` et `sim_mocks`.

```
Starting >>> custom_interfaces
Finished <<< custom_interfaces
Starting >>> gcs_bringup
Starting >>> sim_mocks
Starting >>> tools
Finished <<< sim_mocks
Finished <<< tools
Finished <<< gcs_bringup

Summary: 4 packages finished
```

Trois d'entre eux viennent de `packages/`. Regardez comment :

```bash
ls -l workspaces/gcs_ws/src
```

```
custom_interfaces -> ../../../packages/custom_interfaces
gcs_bringup
sim_mocks -> ../../../packages/sim_mocks
tools -> ../../../packages/tools
```

Un workspace contient ses propres packages, ici `gcs_bringup`, et des liens vers les packages partagés dont il a besoin. Ces liens sont posés une fois par un lead, avec `make link`, et commis dans le repo : vous recevez toujours un workspace déjà lié. `ls -l src` répond donc à la question « qu'est-ce que cette mission utilise, et qu'est-ce qui est partagé ».

`gcs_ws` est le workspace du sol, et rien d'autre : on n'y met jamais de code propre à un drone ou à une mission. Chaque mission a son propre workspace, y compris pendant le développement, et le conteneur `dev` sert à construire n'importe lequel. Si `C=gcs` est la valeur par défaut, c'est seulement parce que c'est le workspace que tout le monde a.

### 4.4 - make dev

```bash
make dev
```

La commande démarre le conteneur de développement s'il ne tourne pas, puis vous y ouvre un shell. Vous êtes maintenant dans `/aeac/workspaces/gcs_ws` :

```bash
pwd
```

```
/aeac/workspaces/gcs_ws
```

Deux endroits de `compose/dev.yml` expliquent cet affichage :

```yaml
    volumes:
      - ..:/aeac
      - /tmp/.X11-unix:/tmp/.X11-unix:rw
    working_dir: /aeac/workspaces/${C:-gcs}_ws
```

La première ligne de `volumes:` monte tout le repo dans `/aeac`, à l'intérieur du conteneur. C'est ce qui vous permet de construire et de lancer n'importe quel workspace depuis ce même conteneur, et c'est aussi pourquoi un fichier que vous modifiez dans VS Code sous WSL est immédiatement modifié dans le conteneur : c'est le même fichier. La seconde ligne passe l'affichage graphique, pour rviz. `working_dir` vous dépose directement dans le workspace de `C`.

Vous n'avez rien à sourcer. Le Dockerfile ajoute trois lignes à `/root/.bashrc`, et chaque terminal que vous ouvrez dans un conteneur les joue tout seul :

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
[ -f "$PWD/install/setup.bash" ] && source "$PWD/install/setup.bash"
ros2 daemon start > /dev/null 2>&1
```

ROS 2, puis le workspace du dossier courant s'il est construit, puis le daemon `ros2`. Vérifiez-le tout de suite :

```bash
ros2 topic list
```

Il répond, sans que vous ayez rien tapé avant.

### 4.5 - Le heartbeat du sol

`gcs_bringup` contient un seul launch file pour l'instant, `base.launch.py` : ce que le portable GCS lance quelle que soit la mission. Il démarre un node, le heartbeat du sol, qui publie une fois par seconde pour dire que la station est en vie.

Dans le terminal de `make dev` :

```bash
ros2 launch gcs_bringup base.launch.py
```

```
[INFO] [launch]: All log files can be found below /root/.ros/log/...
[INFO] [gcs_heartbeat-1]: process started with pid [42]
[gcs_heartbeat-1] [INFO] [gcs_heartbeat]: Heartbeat GCS démarré : publication à 1.0 Hz sur /aeac/external/gcs/heartbeat
```

Ouvrez un second terminal WSL, dans le repo, et entrez dans le conteneur qui tourne :

```bash
make shell
```

```bash
ros2 topic echo /aeac/external/gcs/heartbeat
```

```
data: true
---
data: true
---
```

Le nom de ce topic n'est écrit nulle part dans le node : il vient de `packages/tools/tools/topics.py`, où la constante `GCS_HEARTBEAT` le définit une fois pour toutes. C'est la règle des topics du repo, et vous la verrez appliquée dans chaque node que vous lirez. Son deuxième segment, `external`, dit qu'il est destiné à traverser la radio : c'est bien le cas, le sol envoie son heartbeat au drone.

`Ctrl-C` dans les deux terminaux quand vous avez vu défiler quelques messages, puis arrêtez le conteneur `dev` :

```bash
make down
```

`make down` arrête tous les conteneurs `aeac-*` de votre poste. Prenez l'habitude de le lancer en fin de séance, après une simulation aussi.

> [!TIP]
> **Jalon** : vous avez réussi si `data: true` défile une fois par seconde dans le second terminal pendant que le launch file tourne dans le premier.

## 5 - Les règles, en une page

Ouvrez le `README.md` du repo, section « Règles du repo », et lisez les sept règles à voix haute. Elles sont courtes, et elles vous seront opposées en revue de code :

1. `main` est ce qui vole. On travaille sur une branche, on ouvre une PR, un lead fusionne.
2. Le code de mission n'arme jamais et ne change jamais de mode : c'est le pilote. Les seuls nodes qui le font sont les `*_test` de `sim_mocks`, jamais inclus par un launch file de mission.
3. Un nom de topic s'écrit une fois, dans `tools/topics.py`. `/aeac/external/...` traverse la radio, `/aeac/internal/...` reste sur le drone.
4. Ce qui change entre deux drones, deux terrains ou deux essais est dans `config/`, pas dans le code.
5. Chaque mission a son workspace. `gcs_ws` est le workspace du sol : rien de propre à un drone ou à une mission n'y entre.
6. Code en anglais ; docs, logs et commentaires de haut niveau en français.
7. Ce qu'on apprend et qu'on n'a pas le temps de ranger va dans `NOTES.md`.

Deux d'entre elles sont à retenir avant d'écrire une seule ligne de code, et ce sont les deux premières. Le code de mission n'arme pas et ne change pas de mode, parce que c'est le pilote qui en est responsable, et vous avez déjà rencontré ce principe en formation 3.4 avec le node `takeoff`. Et `main` est ce qui vole : une branche, une PR, `make check` avant de la déposer, un lead qui fusionne. Vous ferez les deux en 5.3.

Où écrire, enfin. `NOTES.md` est le carnet : ce que vous avez appris, ce qui vous a fait perdre deux heures, le réglage qui a marché. Écrivez-y sans demander la permission. `procédure.md` est la checklist du jour J, écrite par ceux qui vont sur le terrain ; vous la lisez pour savoir qu'elle existe, vous ne la pratiquez pas, puisque vous n'avez pas de drone.

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `make build` dit qu'un package manque | Un submodule est vide : le clone a été fait sans `--recurse-submodules` | `make status` (un `-` en début de ligne), puis `make init` (section 4.2) |
| `Package 'gcs_bringup' not found` alors que le build a réussi | Ce terminal a été ouvert avant le build : le workspace n'existait pas encore quand le shell l'a cherché | Fermer ce terminal et en ouvrir un autre avec `make shell` (section 4.4) |
| `ros2 topic list` vide, ou le topic du heartbeat invisible dans le second terminal | Les deux terminaux ne sont pas dans le même conteneur, donc pas dans le même `ROS_DOMAIN_ID` | Ouvrir le second terminal avec `make shell`, jamais directement dans WSL (section 4.5) |
| Des fichiers appartenant à `root` apparaissent après un build | Les conteneurs tournent en root pour l'instant | `sudo chown -R $USER:$USER .` à la racine du repo |
| `make: command not found` sous WSL | Le package n'est pas installé | `sudo apt install make` |
| `make shell` dit qu'aucun conteneur ne tourne | Rien n'est démarré | `make dev` d'abord, dans le premier terminal |
| `make sim` ne joint pas le SITL, en 5.2 | `SITL_HOST` ne pointe pas sur la bonne machine (WSL en mode mirrored, Linux, Mac) | `make print-vars` pour voir la valeur, puis la corriger dans `.env` (section 3.2) |
| `make status` affiche un `+` devant un package de `packages/` | Le submodule est sur un autre commit que celui attendu par le repo | Ne rien pousser et demander à un lead (section 4.2) |
