# Formation 5.2 : une mission en simulation

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Installer un workspace de mission dans un dépôt de compétition, lier les paquets partagés et le construire
- Lancer une mission en simulation dans trois terminaux et suivre sa machine à états
- Expliquer ce que fait le paramètre `sim` et pourquoi le launch de vol et le launch de simulation sont le même fichier
- Dire où va un réglage : dans la mission, dans le site ou dans le drone
- Enregistrer un rosbag et vérifier ce qu'il contient
- Chercher une panne dans l'ordre : conteneur, nœud, donnée

Prérequis : la [formation 5.1](5.1-le-depot-vu-de-haut.md) terminée (dépôt de cohorte cloné, `make init`, `gcs_ws` construit), et le SITL de Mission Planner qui démarre, comme en formation 1.

En 5.1 vous avez visité le dépôt sans rien y faire tourner. Ici une vraie mission tourne, et elle est réduite à son squelette : quatre états, un waypoint, un interrupteur. C'est le même squelette que les missions de compétition, avec la moitié des lignes en moins.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 2 h 30, dont une demi-heure de débogage à la fin.
> - **Prérequis** : 5.1 faite, et le SITL de Mission Planner qui démarre. Avant d'ouvrir un terminal, prenez une feuille et écrivez les sept dossiers du dépôt avec une phrase chacun. Deux minutes, sans regarder. C'est le jalon de 5.1, section 2.
> - **À la fin** : la machine à états de la démo est passée par `IDLE`, `GOTO`, `ACT` et `RETURN` sans qu'aucun drone ne soit dans les airs, et le waypoint qu'elle vise vient d'un fichier YAML que vous avez modifié.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une capture du `ros2 topic echo` de l'état montrant les quatre transitions, le diff de votre YAML de site, et les trois causes trouvées à l'exercice de débogage.

Tout se passe sur votre poste WSL, dans le clone de `formation-5-automne-2026` que vous avez déjà. Travaillez sur une branche à vous :

```bash
git checkout -b prenom/demo
```

Remplacez `prenom` par le vôtre. `main` est ce qui vole, même dans le dépôt de la formation.

## 1 - Poser la démo

### 1.1 - Copier, lier, construire

Le workspace de la démo est fourni dans le dossier de la formation, sous `5-env_compétition/demo_ws/`. Il ne fait pas partie du dépôt de mission : vous l'y installez.

Depuis la racine du clone, en remplaçant `<dossier de la formation>` par le chemin où vous avez le dépôt Formations-Controle :

```bash
cp -r <dossier de la formation>/5-env_compétition/demo_ws workspaces/
```

```bash
cp workspaces/demo_ws/src/demo_bringup/config/demo.yaml config/
```

Deux copies, deux endroits, et ce n'est pas un hasard. Le code de la mission va dans `workspaces/demo_ws/`, ses réglages vont dans `config/`. La règle 4 du dépôt dit que ce qui change entre deux essais n'est pas dans le code ; le launch de la démo, lui, lit `/aeac/config/demo.yaml` et rien d'autre.

La démo utilise trois paquets partagés : `tools` pour les noms de topics, `custom_interfaces` pour le message d'état et `sim_mocks` pour les nœuds de test de la section 2. Les mocks sont un paquet partagé comme les autres, et on le lie au workspace pour que le shell ouvert par `make shell C=demo IMG=sim` le trouve. On lie les trois :

```bash
make link C=demo PKG=tools && make link C=demo PKG=custom_interfaces && make link C=demo PKG=sim_mocks
```

```
Lien créé : workspaces/demo_ws/src/tools. Pense à le commettre.
Lien créé : workspaces/demo_ws/src/custom_interfaces. Pense à le commettre.
Lien créé : workspaces/demo_ws/src/sim_mocks. Pense à le commettre.
```

C'est exactement ce que vous avez vu en 5.1 avec `ls -l workspaces/gcs_ws/src` : un workspace de mission contient ses propres paquets et des liens vers les paquets partagés. Vous venez de fabriquer ces liens vous-même.

```bash
make build C=demo
```

```
Starting >>> custom_interfaces
Finished <<< custom_interfaces
Starting >>> tools
Starting >>> demo_bringup
Starting >>> sim_mocks
Finished <<< demo_bringup
Finished <<< sim_mocks
Finished <<< tools
Starting >>> demo_mission
Finished <<< demo_mission

Summary: 5 packages finished
```

Cinq paquets : les trois partagés, le `demo_bringup` qui porte le launch et la configuration, et le `demo_mission` qui porte le nœud. Colcon les construit dans l'ordre des dépendances, `custom_interfaces` d'abord parce que tout le reste en dépend.

### 1.2 - Lire le nœud avant de le lancer

Ouvrez `workspaces/demo_ws/src/demo_mission/demo_mission/mission.py`. Deux cents lignes, dont un bon tiers de commentaires. Ne cherchez pas à tout comprendre : cherchez trois choses, et seulement elles. Les réponses sont juste en dessous, mais cherchez d'abord.

**Où sont les noms de topics ?** Le nœud publie son état à la ligne 102, sur `topics.DEMO_STATE`. La constante est dans `packages/tools/tools/topics.py` et vaut `/aeac/external/demo/state`. Le nom complet n'est écrit nulle part dans `mission.py`. Les quatre topics mavros, eux, sont en haut du fichier, lignes 25 à 28 : ils appartiennent à un paquet tiers, `topics.py` ne décrit que les topics `/aeac` écrits par l'équipe. Le deuxième segment, `external`, dit que l'état de la mission a le droit de traverser la radio vers le sol.

**Où sont les états ?** Dans `packages/custom_interfaces/msg/MissionState.msg`, importé ligne 14 et utilisé partout sous la forme `MissionState.IDLE`, `MissionState.GOTO`, `MissionState.ACT`, `MissionState.RETURN`. Le fichier `.msg` définit ces quatre constantes et leurs valeurs, 0 à 3. Aucun nœud ne les redéfinit : le message est la seule définition des états, et le sol lit les mêmes chiffres que le drone.

**Où est le waypoint ?** Nulle part. Cherchez une latitude dans `mission.py` : vous trouverez des paramètres `target.lat` et `target.lon` déclarés dans le bloc `PARAMETERS`, lignes 37 à 42, ligne 41 pour `target`, avec `0.0` en valeur par défaut, et rien d'autre. Ouvrez `workspaces/demo_ws/src/demo_bringup/launch/mission.launch.py` : la fonction `site_parameters`, lignes 20 à 37, ouvre `/aeac/config/sites/<site>.yaml`, en tire six valeurs et les passe au nœud. Le terrain est une donnée, pas du code.

La machine à états elle-même tient dans la fonction `next_state`, lignes 53 à 69. Elle ne connaît ni ROS, ni mavros, ni le GPS : elle reçoit l'état courant et quelques booléens, et rend le nouvel état ou `None`. C'est une forme qui revient souvent dans les missions Zenith, parce qu'elle se relit en une minute et se teste sans rien lancer.

> [!TIP]
> **Jalon** : vous avez réussi cette section si vous pouvez dire, fichier et ligne à l'appui, d'où viennent le nom du topic d'état, la valeur `2` de l'état `ACT`, et la latitude visée.

## 2 - Trois terminaux

C'est le cœur de la formation. Trois terminaux WSL, tous dans le dépôt, plus Mission Planner sous Windows.

Avant tout : lancez le SITL dans Mission Planner comme en formation 1, et attendez qu'il soit prêt. Si le SITL ne tourne pas, mavros n'a personne à qui parler et le reste de la section ne donnera rien.

### 2.1 - Terminal 1 : la simulation

```bash
make sim C=demo
```

Cette commande fait démarrer deux conteneurs, décrits dans `compose/sim.yml`. Le premier, `mavros-sim`, lance mavros vers le SITL, en TCP sur le port 5762 de `SITL_HOST`, l'adresse de Windows vue depuis WSL que vous avez rencontrée avec `make print-vars` en 5.1. Le second, `sim`, source ROS 2 et le workspace, puis lance le launch de la mission avec `sim:=true site:=${SITE:-sim}`. `SITE` est la quatrième variable du Makefile, à côté de `C`, `IMG` et `DRONE` ; elle vaut `sim` par défaut, et `make print-vars` l'affiche entre `DRONE` et `SITL_HOST`. On y revient en section 3.3.

Au bout de quelques secondes, au milieu des lignes de mavros, vous voyez celle du nœud de mission :

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Si mavros répète qu'il n'arrive pas à se connecter, c'est le SITL ou `SITL_HOST` : voyez la table de la section 6 avant d'aller plus loin. Laissez ce terminal tourner, c'est lui qui affiche la vie de la mission.

### 2.2 - Terminal 2 : le pilote et la manette

```bash
make shell C=demo IMG=sim
```

`make shell` entre dans un conteneur déjà lancé : il faut que le terminal 1 tourne, sinon Docker répond que le conteneur n'existe pas. Le `C=demo` n'est pas décoratif : le Makefile vaut `C ?= gcs`, et `compose/sim.yml` ouvre le shell dans `workspaces/${C:-gcs}_ws`. Sans `C=demo`, vous vous retrouvez dans `gcs_ws`, où `install/setup.bash` n'a rien de la démo. Et comme en 5.1 avec `make dev`, le shell qu'on vous ouvre ne source rien tout seul, même si le conteneur, lui, a sourcé pour lancer la mission. Dans chaque terminal ouvert par `make shell`, avant toute commande `ros2` :

```bash
source /opt/ros/humble/setup.bash && source install/setup.bash
```

Le drone simulé est au sol, désarmé, en mode STABILIZE. Le code de mission ne le fera pas décoller : la règle 2 du dépôt dit que le code de mission n'arme jamais et ne change jamais de mode. En vol, c'est le pilote qui le fait. En simulation, on a un nœud de test pour tenir ce rôle :

```bash
ros2 run sim_mocks takeoff_test --ros-args -p sim:=true
```

```
[INFO] [takeoff_test]: mode GUIDED
[INFO] [takeoff_test]: armement (renvoyé tant que refusé)
[INFO] [takeoff_test]: décollage à 10.0 m
[INFO] [takeoff_test]: terminé
```

Le drone monte à dix mètres dans Mission Planner et le nœud s'arrête tout seul. Essayez de le relancer sans `-p sim:=true` :

```bash
ros2 run sim_mocks takeoff_test
```

```
takeoff_test ne tourne qu'en simulation : ajoute -p sim:=true
```

Ce refus est voulu et il est écrit en clair dans `packages/sim_mocks/README.md` : un nœud qui arme ou change de mode porte le suffixe `_test` et refuse de démarrer sans `sim:=true`. C'est la seule façon d'armer depuis du code dans ce dépôt.

Le drone vole, il attend un ordre. Dans le même terminal :

```bash
ros2 run sim_mocks rc_simulator
```

```
[INFO] [rc_simulator]: Manette simulée : w/s/x e/d/c r/f/v, q pour quitter
```

Ce nœud remplace la manette : il lit votre clavier et publie des valeurs PWM sur `/mavros/rc/in`, dix fois par seconde, comme un vrai récepteur. Les touches `w`, `s` et `x` mettent le canal 8 en haut (1900), au centre (1500) et en bas (1100). Il lit le clavier du terminal où il a été lancé : pour que vos touches comptent, c'est ce terminal qui doit avoir le focus.

Ne tapez encore rien : ouvrez d'abord le troisième terminal.

### 2.3 - Terminal 3 : l'état de la mission

```bash
make shell C=demo IMG=sim
```

```bash
source /opt/ros/humble/setup.bash && source install/setup.bash
```

```bash
ros2 topic echo /aeac/external/demo/state
```

```
header:
  stamp:
    sec: 1758501234
    nanosec: 512000000
  frame_id: ''
state: 0
time_in_state: 3.5
---
```

`state` est un entier, et c'est là que `MissionState.msg` devient utile : `0` est `IDLE`, l'attente ; `1` est `GOTO`, en route vers le waypoint ; `2` est `ACT`, l'action sur place ; `3` est `RETURN`, le retour au point de départ. `time_in_state` est le nombre de secondes passées dans l'état courant, remis à zéro à chaque transition. Le tout défile deux fois par seconde, parce que `state_rate_hz` vaut `2.0` dans `config/demo.yaml`.

### 2.4 - Le GO

Cliquez dans le terminal 2, celui du `rc_simulator`, et appuyez sur `w`.

```
[INFO] [rc_simulator]: canal 8 = 1900
```

Dans le terminal 1, la mission part :

```
[mission-1] [INFO] [demo_mission]: Transition IDLE -> GOTO
```

Dans Mission Planner, le drone se met en route vers le waypoint du site `sim`. Le nœud ne lui donne pas d'ordre de déplacement une fois pour toutes : il republie un setpoint global à chaque tour de timer, deux fois par seconde, parce que mavros exige un flux continu de setpoints et que l'autopilote ignore ceux qui s'arrêtent (`mission.py`, lignes 140 à 142).

Quand le drone arrive à moins de trois mètres du waypoint, valeur `arrival_radius_m` de `config/demo.yaml` :

```
[mission-1] [INFO] [demo_mission]: Transition GOTO -> ACT
[mission-1] [INFO] [demo_mission]: Simulation : action factice, rien n'est déclenché
```

Cinq secondes plus tard, `act_duration_s` du même fichier :

```
[mission-1] [INFO] [demo_mission]: Transition ACT -> RETURN
```

Puis, une fois revenu près du point de départ :

```
[mission-1] [INFO] [demo_mission]: Transition RETURN -> IDLE
[mission-1] [INFO] [demo_mission]: Mission terminée
```

Le drone reste en l'air, en GUIDED : la démo ne se pose pas, c'est le pilote qui pose.

### 2.5 - Les règles de sécurité rencontrées ici

Relancez la mission une deuxième fois, en appuyant encore sur `w`. Il ne se passe rien. C'est voulu : un GO ne compte qu'après que l'interrupteur a été vu au moins une fois en position basse (`mission.py`, lignes 113 à 120, et la remise à zéro ligne 157). Un interrupteur déjà en haut au démarrage du nœud, ou resté en haut à la fin d'un tour, ne relance donc aucune mission. Appuyez sur `s` ou sur `x` pour redescendre le canal, puis sur `w` : la mission repart. Sur le terrain, cette règle évite qu'un drone parte parce qu'on a branché la batterie avec la manette dans le mauvais état.

Deuxième règle, à essayer pendant que la mission est en `GOTO` : dans Mission Planner, repassez le drone en mode LOITER, ou désarmez-le.

```
[mission-1] [INFO] [demo_mission]: Transition GOTO -> IDLE
[mission-1] [WARN] [demo_mission]: Le pilote a repris la main, mission interrompue
```

Hors de `IDLE`, perdre l'armement ou le mode GUIDED ramène la mission en `IDLE` immédiatement (`next_state`, lignes 56 à 58). La mission ne discute pas et ne réessaie pas : le pilote est au-dessus du code, toujours, et un nœud qui continuerait à publier des setpoints pendant que le pilote reprend la main serait un nœud dangereux. Repassez en GUIDED et redonnez le GO pour repartir.

Si vous donnez le GO alors que le drone n'est ni armé ni en GUIDED, la mission reste en `IDLE` et prévient une fois :

```
[mission-1] [WARN] [demo_mission]: GO reçu mais le drone n'est pas armé en GUIDED
```

### 2.6 - Ce que `sim:=true` fait, et ce qu'il ne fait pas

Maintenant que le tour est bouclé, la question qui compte : qu'est-ce qui change entre ce que vous venez de lancer et ce qui volera au-dessus d'un terrain ?

Presque rien. `compose/sim.yml` lance `ros2 launch demo_bringup mission.launch.py sim:=true site:=${SITE:-sim}`. Le launch de vol lance le même fichier, avec `sim:=false`. Le launch de simulation et le launch de vol ne sont pas deux fichiers, c'est un seul fichier avec un argument différent, déclaré lignes 59 et 60 de `mission.launch.py`.

Et cet argument ne fait qu'une chose : il devient le paramètre `sim` du nœud. Le nœud le lit une fois au démarrage, ligne 77, et s'en sert à un seul endroit, ligne 169 :

```python
if not self.sim:
    self._trigger_payload()
```

Un seul appel matériel dans la démo, donc un seul `if not self.sim`. C'est la règle : les nœuds qui touchent au matériel entourent leur appel matériel de ce test, et rien d'autre dans le code ne sait s'il est en simulation. Un nœud qui aurait dix `if self.sim` un peu partout serait un nœud dont vous ne pouvez plus rien conclure en simulation, parce que ce qui a marché en simulation n'est plus ce qui volera.

Remarquez aussi ce que le launch ne lance pas. `takeoff_test` et `rc_simulator`, vous les avez lancés à la main. Aucun launch de mission n'inclut un mock, jamais, et c'est ce qui garantit qu'un mock ne peut pas se retrouver dans les airs. Lisez `packages/sim_mocks/README.md` en entier, c'est une page : les trois mocks du dépôt, ce que chacun remplace, et la règle pour en écrire un. Le troisième, `target_mock`, remplace une détection du conteneur vision ; il vous servira quand la formation vision arrivera.

<details>
<summary>Pourquoi le nœud s'abonne à la position avec un profil QoS particulier</summary>

Lignes 98 à 101 de `mission.py`, l'abonnement à `/mavros/global_position/global` passe `qos_profile_sensor_data` au lieu du `10` habituel. Les capteurs de mavros publient en BEST_EFFORT ; un abonnement RELIABLE ne correspond alors pas à la publication, et ROS 2 ne vous le dit pas : le topic existe, il est listé, et aucun message n'arrive. C'est la panne la plus déroutante du lot, et c'est pour ça que `ros2 topic info -v` est dans la démarche de la section 5.

</details>

## 3 - Mission, site, drone

### 3.1 - Trois fichiers, trois questions

Vous avez maintenant croisé trois familles de réglages, et `config/README.md` les range selon une seule question : qu'est-ce qui fait changer cette valeur ?

`config/demo.yaml` change avec la mission. Ce sont les gains, les seuils, les durées, le mapping des interrupteurs de la manette : `rc.go_channel` à `7`, l'index du GO dans le message RC, donc le canal 8 de la manette et la touche `w` du `rc_simulator` ; `rc.go_pwm_min` à `1700`, à partir de quoi l'interrupteur compte comme haut ; `arrival_radius_m`, `act_duration_s`, `state_rate_hz`. Changer de terrain ne touche pas à ce fichier.

`config/sites/sim.yaml` change avec le terrain. Rien que des coordonnées : `home`, `scene.target`, `altitude_agl`. Le site `sim` est la position de départ du SITL d'ArduPilot, près de Canberra en Australie.

`config/drones/hexa.json5` change avec le drone. Ce sont les adresses de la radio, pour viser tel appareil depuis le sol. Vous ne l'ouvrez pas ici, c'est le sujet de la formation 6.

La règle derrière ce rangement est la règle 4 du dépôt : une valeur qui change entre deux drones, deux terrains ou deux essais n'est jamais écrite dans un nœud ni dans un launch. Quand vous hésitez sur l'endroit où mettre un réglage, posez-vous la question dans ce sens, et pas dans le sens « où est-ce que ce sera pratique à lire ».

### 3.2 - Déplacer le waypoint

La mission tourne toujours. Ouvrez `config/sites/sim.yaml` et changez la latitude de la cible :

```yaml
  scene:
    target:
      lat: -35.361900
      lon: 149.165700
```

`-35.362800` devient `-35.361900`, neuf dix-millièmes de degré, soit une centaine de mètres vers le nord. Un dix-millième de degré de latitude fait à peu près onze mètres, partout sur Terre ; pour la longitude, ça dépend de la latitude.

Ce fichier est lu par le launch au démarrage, pas en continu. Dans le terminal 1, `Ctrl-C`, puis :

```bash
make sim C=demo
```

Le `Ctrl-C` du terminal 1 a arrêté les conteneurs, et les terminaux 2 et 3 sont morts avec eux : le shell qu'ils tenaient ouvert était dans un conteneur qui n'existe plus. Rouvrez-en un nouveau dans chacun avec `make shell C=demo IMG=sim`, sourcez avec `source /opt/ros/humble/setup.bash && source install/setup.bash`, puis relancez `ros2 run sim_mocks rc_simulator` dans le terminal 2 et `ros2 topic echo /aeac/external/demo/state` dans le terminal 3. Le drone, lui, reste armé en GUIDED : il est dans le SITL, qui n'a pas redémarré, et `takeoff_test` n'est donc pas à refaire.

Redonnez le GO dans le terminal 2, après avoir remis le canal en bas avec `s`. Dans Mission Planner, le drone part cette fois vers un autre point, nettement plus loin. Rien n'a été reconstruit : `make build` n'a pas été relancé, parce qu'aucune ligne de code n'a changé.

```bash
git diff config/sites/sim.yaml
```

> [!TIP]
> **Jalon** : ce diff, deux lignes, est le deuxième jalon à poster. C'est la preuve la plus courte qu'un waypoint n'est pas du code.

### 3.3 - Un deuxième site

Un dépôt de compétition a un fichier de site par terrain. Le dossier de la formation en fournit un second :

Ouvrez-le : mêmes clés que `sim.yaml`, coordonnées du campus. Le launch ne lit que ces clés-là, et il choisit le fichier avec son argument `site`.

Ne donnez pas le GO. Le SITL démarre en Australie, près de Canberra, et il y est toujours : avec le site `polytechnique`, il recevrait un setpoint à Montréal et passerait le reste de la journée à traverser le Pacifique. ### 3.4 - Les règles de sécurité rencontrées ici

Essayez maintenant un site qui n'existe pas :

```bash
make sim C=demo SITE=inexistant
```

```
RuntimeError: Site inconnu : /aeac/config/sites/inexistant.yaml
```

Le launch refuse de démarrer et dit quel fichier il cherchait (`mission.launch.py`, lignes 34 et 35). Si le fichier existe mais qu'une clé y manque ou n'a pas la forme attendue, il refuse aussi, lignes 36 et 37, en nommant le fichier et la clé fautive : `/aeac/config/sites/polytechnique.yaml : clé manquante ou mal formée ('altitude_agl')`. Essayez, en commentant une ligne de votre copie, puis en relançant :

```bash
make sim C=demo SITE=polytechnique
```

Décommentez la ligne quand vous avez vu le refus. Et si le YAML est complet mais que les coordonnées valent zéro, c'est le nœud qui refuse, `mission.py` lignes 84 et 85 : `Coordonnées de site absentes : vérifier config/sites/<site>.yaml`.

Trois refus pour la même chose, à trois endroits, et c'est voulu. Les valeurs par défaut des coordonnées sont `0.0`, au large du golfe de Guinée, et une valeur par défaut sûre est une valeur qui ne vole pas. Un nœud qui démarre quand même avec un waypoint faux est bien plus dangereux qu'un nœud qui refuse de démarrer au sol.

La deuxième règle concerne la fraîcheur de la donnée. `distance_to`, lignes 144 à 149, rend `None` quand la dernière position GPS reçue a plus de deux secondes (`POSITION_MAX_AGE_S`), et `next_state` ne déclare aucune arrivée tant qu'une distance vaut `None`. Si le lien avec l'autopilote se coupe, la mission reste donc en `GOTO` au lieu de conclure qu'elle est arrivée sur la foi d'une position périmée. Une vieille position ne prouve pas où le drone se trouve, elle prouve où il se trouvait.

## 4 - Enregistrer

Un vol ne se rejoue pas. Ce qui n'a pas été enregistré pendant l'essai est perdu, et la question qu'on se posera le soir même sera toujours une question à laquelle il faut des données pour répondre. C'est pour ça qu'on enregistre à chaque vol, même quand tout va bien.

Relancez la simulation dans le terminal 1 avec `make sim C=demo`. Les terminaux 2 et 3 sont à rouvrir et à sourcer, le drone est toujours armé en GUIDED. Ouvrez ensuite un quatrième terminal :

```bash
make bag C=demo IMG=sim
```

L'enregistrement démarre dans un dossier daté sous `bags/`, par exemple `bags/2026-09-22_14-30`. Faites un tour complet de mission pendant qu'il tourne, du GO au retour en `IDLE`, puis `Ctrl-C` dans ce quatrième terminal.

Le Makefile ne prend pas tous les topics. Il passe cette expression régulière à `ros2 bag record` :

```
/aeac/.*|/mavros/(state|rc/in|local_position/pose|global_position/global|battery)
```

Tout ce que l'équipe publie, plus cinq topics mavros : l'état de l'autopilote, les entrées de la manette, la position locale, la position globale et la batterie. C'est ce qu'il faut pour rejouer une mission et comprendre pourquoi elle a fait ce qu'elle a fait. Le reste de mavros, qui est volumineux et rarement utile, reste dehors.

Depuis un shell du conteneur :

```bash
make shell C=demo IMG=sim
```

```bash
source /opt/ros/humble/setup.bash && source install/setup.bash
```

```bash
ros2 bag info /aeac/bags/2026-09-22_14-30
```

```
Files:             2026-09-22_14-30_0.db3
Duration:          48.2s
Messages:          1043
Topic information: Topic: /aeac/external/demo/state | Type: custom_interfaces/msg/MissionState | Count: 96
                   Topic: /mavros/state | Type: mavros_msgs/msg/State | Count: 48
                   Topic: /mavros/rc/in | Type: mavros_msgs/msg/RCIn | Count: 482
```

Remplacez la date par la vôtre. Le nombre de messages sur le topic d'état doit être à peu près le double de la durée en secondes, puisque le nœud publie à 2 Hz : si ce n'est pas le cas, l'enregistrement a commencé ou fini au mauvais moment.

`bags/` est ignoré par git, comme `models/`. Un rosbag ne se commet jamais, il se partage autrement.

## 5 - Quand ça ne marche pas : la démarche

Une demi-heure, pendant que la simulation tourne encore. Ce qui suit n'est pas une liste de pannes, la liste est dans la table de la section 6. C'est l'ordre dans lequel on cherche, et cet ordre vaut plus que n'importe quelle liste, parce qu'il tient encore devant une panne que personne n'a jamais vue.

Trois étages. On ne descend d'un étage qu'une fois celui du dessus vérifié.

### 5.1 - Étage 1 : est-ce que le conteneur tourne ?

```bash
docker ps
```

Vous devez voir `aeac-mavros-sim` et `aeac-sim`. Un conteneur absent de cette liste est un conteneur sorti, et alors :

```bash
make logs IMG=sim
```

Les dernières lignes avant la sortie disent pourquoi. Tant qu'un conteneur est sorti, aucune commande `ros2` ne vous apprendra quoi que ce soit : il n'y a personne pour publier, et une liste de topics vide ne veut alors rien dire du tout. C'est le piège de cet étage, et c'est pour ça qu'il est le premier.

### 5.2 - Étage 2 : est-ce que le nœud tourne ?

```bash
make shell C=demo IMG=sim
```

```bash
source /opt/ros/humble/setup.bash && source install/setup.bash
```

```bash
ros2 node list
```

```
/demo_mission
/mavros
/rc_simulator
```

```bash
ros2 topic list
```

Un nœud absent de `ros2 node list` alors que son conteneur tourne est un nœud mort au lancement : remontez aux logs du launch, dans le terminal 1 ou avec `make logs IMG=sim`, et cherchez la trace d'exception. Une liste de topics où il manque tous les `/mavros/*` ne dit pas que mavros est mort, elle dit d'abord de remonter à l'étage 1.

### 5.3 - Étage 3 : est-ce que la donnée circule ?

```bash
ros2 topic hz /aeac/external/demo/state
```

```
average rate: 2.001
```

Une fréquence conforme veut dire que l'émetteur est vivant. Pas de sortie du tout, alors que le topic est listé, veut dire l'inverse : un émetteur mort, ou un QoS incompatible entre les deux bouts.

```bash
ros2 topic echo /mavros/global_position/global --once
```

```bash
ros2 topic info -v /aeac/external/demo/state
```

`info -v` affiche les profils QoS des publicateurs et des abonnés. Deux profils qui ne se correspondent pas donnent exactement le même symptôme qu'une absence totale de message, et c'est ce qu'il faut savoir pour ne pas y perdre une soirée.

Enfin, quand tout circule mais que le comportement est faux, les valeurs :

```bash
ros2 param get /demo_mission arrival_radius_m
```

Un topic qui coule avec les mauvaises valeurs dedans est un problème d'étage 3, et il ressemble de loin à un problème d'étage 1. C'est en sautant des étages qu'on cherche au mauvais endroit.

### 5.4 - Exercice : trois pannes

Le dossier `5-env_compétition/pannes/` de la formation contient trois patchs. Chacun casse la démo d'une seule ligne, et chacun se diagnostique par un étage différent. Les numéros ne suivent pas l'ordre des étages : une panne ne s'annonce jamais.

Vous n'ouvrez pas les patchs. C'est tout l'exercice.

Copiez d'abord le dossier dans le clone, pour que `git apply` trouve les chemins :

```bash
cp -r <dossier de la formation>/5-env_compétition/pannes .
```

Ne cherchez pas à avoir un `git status` vide : à ce stade vous avez copié `demo_ws`, `demo.yaml` et `polytechnique.yaml`, modifié `config/sites/sim.yaml` et écrit dans `NOTES.md`. Ce qu'on vous demande est autre chose : qu'il n'y ait pas d'autre modification que celles du patch une fois la panne posée, pour ne pas chercher une panne que vous auriez écrite vous-même. Puis :

```bash
git apply pannes/panne-1.patch
```

```bash
make sim C=demo
```

Les terminaux 2 et 3 sont à rouvrir et à sourcer après chaque relance, comme en section 3.2.

Observez, puis descendez les trois étages dans l'ordre. Quand vous avez la cause, remettez le dépôt d'aplomb :

```bash
git apply -R pannes/panne-1.patch
find workspaces -maxdepth 1 -type d -empty -exec rmdir {} + 2>/dev/null || sudo find workspaces -maxdepth 1 -type d -empty -exec rmdir {} +
```

La seconde ligne est du ménage : une panne peut laisser un dossier vide dans `workspaces/`, que `git apply -R` ne retire pas parce que git ne suit pas les dossiers. La commande ne supprime que des dossiers vides, donc elle est sans danger ; la seconde forme sert quand le dossier n'appartient pas à l'utilisateur. S'il n'y a rien à retirer, elle ne fait rien. Le détail est dans [`pannes/README.md`](pannes/README.md).

`git apply -R --check pannes/panne-1.patch` vérifie sans rien changer que la panne est bien en place, et `git apply --check` qu'elle peut être appliquée. En cas de doute, `git status` puis `git checkout -- compose/sim.yml config/demo.yaml`, les deux seuls fichiers que les patchs touchent. Une panne à la fois : les trois appliquées ensemble vous apprennent à chercher trois choses à la fois, ce qui n'apprend rien.

Aucune des trois pannes ne demande de reconstruire : le code de la mission n'est pas touché. Vous n'avez donc jamais à refaire `make build C=demo` pendant cet exercice.

<details>
<summary>Si vous séchez</summary>

Voici les trois symptômes, sans dire lequel va avec quel patch. Une des trois pannes fait sortir le conteneur `sim` tout de suite. Une autre rend tous les topics `/mavros/*` invisibles. Une troisième laisse la mission en `IDLE` quoi que vous fassiez. Reprenez les trois étages de la section 5 à partir du symptôme que vous avez sous les yeux.

</details>

Pour chacune, écrivez une ligne dans `NOTES.md`, à la racine du clone : pas la cause, mais ce qui vous a mis sur la piste. Quelle commande, quel étage, quelle ligne de log. C'est cette ligne qui servira à la prochaine recrue, et à vous dans six mois.

> [!TIP]
> **Jalon** : les trois causes trouvées, `git apply -R --check` qui passe pour les trois patchs, et trois lignes dans `NOTES.md`. C'est le troisième jalon à poster.

Une phrase à retenir d'ici, et pas avant : sur le drone, ces trois étages servent tels quels le jour J, avec un étage de plus au-dessus, parce que là-bas le lancement ne vient pas de vous mais de systemd. La formation 6 ajoute cet étage.

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `mavros-sim` répète qu'il n'arrive pas à se connecter | Le SITL n'est pas lancé, ou `SITL_HOST` est faux | Lancer le SITL dans Mission Planner d'abord ; `make print-vars` pour voir l'adresse résolue ; formation 3.3 |
| `make print-vars` affiche `SITL_HOST=` vide | `ip route` ne renvoie pas de route par défaut dans WSL ; `compose/sim.yml` retombe alors sur `172.17.0.1`, qui n'est pas Windows | Vérifier le réseau WSL, puis `make sim C=demo SITL_HOST=<adresse de Windows>` |
| `takeoff_test` refuse de démarrer | Lancé sans `-p sim:=true` | C'est le comportement voulu (section 2.2) |
| Le GO ne passe pas, `rc_simulator` n'affiche rien | Le terminal du `rc_simulator` n'a pas le focus clavier | Cliquer dans ce terminal avant d'appuyer sur `w` |
| Le GO ne passe pas, `rc_simulator` affiche bien `canal 8 = 1900` | L'interrupteur n'a pas été vu en position basse depuis la dernière mission | `s` ou `x`, puis `w` (section 2.5) |
| L'état ne change pas après le GO, et un WARN parle de GUIDED | Le drone n'est pas armé, ou pas en GUIDED | `takeoff_test` d'abord, puis vérifier `ros2 topic echo /mavros/state` |
| Le waypoint n'a pas bougé après modification du YAML | Mauvais fichier modifié (celui de `workspaces/` au lieu de celui de `config/`), `SITE=` oublié, ou simulation pas relancée | `ros2 param get /demo_mission target.lat` (section 3.3) |
| `Package 'demo_bringup' not found` dans un `make shell` | Le shell ouvert par `make shell` ne source rien tout seul | `source /opt/ros/humble/setup.bash && source install/setup.bash` (section 2.2) |
| `make shell C=demo IMG=sim` répond que le conteneur n'existe pas | `make sim C=demo` ne tourne pas, ou s'est arrêté | Regarder le terminal 1, puis `docker ps` et `make logs IMG=sim` |
| Deux valeurs différentes pour le même paramètre selon le moment | Deux nœuds `demo_mission` tournent en même temps | `ros2 node list`, puis `Ctrl-C` sur celui de trop (section 5.2) |
| Rien ne répond et on ne sait pas par où commencer | C'est le cas normal | Les trois étages de la section 5, dans l'ordre, sans en sauter un |
