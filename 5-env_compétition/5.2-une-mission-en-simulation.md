# Formation 5.2 : une mission en simulation

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Installer un workspace de mission dans un repo de compétition et le construire
- Lancer une mission en simulation dans trois terminaux et suivre sa machine à états
- Expliquer ce que fait le paramètre `sim` et pourquoi le launch file de vol et celui de simulation sont le même fichier
- Dire où va un réglage : dans la mission, dans le site ou dans le drone
- Enregistrer un rosbag et vérifier ce qu'il contient
- Chercher une panne dans l'ordre : conteneur, node, donnée

Ici, vous faites tourner une vraie mission. Elle est réduite à l'essentiel : quatre états, un waypoint et un interrupteur.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 2 h.
> - **Prérequis** : la [formation 5.1](5.1-le-repo-vu-de-haut.md) terminée (repo template cloné, `make init`, `gcs_ws` construit), le SITL de Mission Planner qui démarre, comme en formation 1, et le conteneur `dev` de 5.1 arrêté (`make down`). Arrêtez aussi tout mavros resté allumé depuis les formations 2 ou 3 (conteneur `mavros` ou `b3-mavros` dans `docker ps`). Ce mavros occupe le port 5762 du SITL, et le mavros de la simulation ne pourrait pas s'y brancher. Pour l'arrêter, `make down` dans le dossier de cette formation-là suffit. Avant d'ouvrir un terminal, prenez une feuille et écrivez les dossiers du repo, avec une phrase pour chacun, en deux minutes et sans regarder.
> - **À la fin** : la machine à états de la démo est passée par `IDLE`, `GOTO`, `ACT` et `RETURN` sans qu'aucun vrai drone ne vole, et le waypoint qu'elle vise vient d'un fichier YAML que vous avez modifié.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une capture des quatre transitions, le diff de votre fichier de site, et la sortie du `ros2 param get` de la section 3.3.

Tout se passe sur votre poste WSL, dans votre clone du template, le dossier `mission-template` que vous avez déjà.

Travaillez sur une branche à vous. Une branche est une copie de travail du repo, avec un nom. Tant que vous êtes dessus, vos modifications ne touchent pas `main`. Dans un repo de compétition, `main` contient le code qui vole. Dans le template, `main` est la référence que tout le monde clone. Placez-vous d'abord dans votre clone :

```bash
cd ~/mission-template
```

```bash
git switch -c prenom/demo
```

Remplacez `prenom` par votre prénom. `git switch -c` crée la branche et vous place dessus. Pour savoir à tout moment sur quelle branche vous êtes, tapez `git branch --show-current`.

Dans l'explorateur de la seconde fenêtre, glissez le dossier `5-env_compétition/demo_ws` et déposez-le sur le dossier `workspaces/` de la première fenêtre.

Les réglages de la mission doivent aussi être copiés, mais à un autre endroit. Copiez-les avec le terminal, parce qu'un glisser-déposer dans VS Code déplacerait le fichier au lieu de le copier :

```bash
cp workspaces/demo_ws/src/demo_bringup/config/demo.yaml config/
```

Vous avez donc fait deux copies, à deux endroits différents. Le code de la mission va avec le code des autres missions, dans `workspaces/`. Ses réglages vont avec les réglages des autres missions, dans `config/`. On sépare les deux parce qu'on change souvent les réglages et rarement le code. Par exemple, un waypoint, un seuil ou une durée se modifient entre deux essais sans toucher à une ligne de Python. Le launch file de la démo donne à la node deux fichiers de `/aeac/config/`, et seulement ces deux-là : `demo.yaml` pour la mission et `sites/<site>.yaml` pour le terrain.

La démo se sert de trois packages partagés : `tools` pour les noms de topics, `custom_interfaces` pour le message d'état, et `sim_mocks` pour les nodes de simulation de la section 2. `sim_mocks` contient des mocks, qui remplacent le matériel absent, et une node de test, qui joue le rôle du pilote. ### 1.2 - Lire avant de lancer

Commencez par le launch file, `workspaces/demo_ws/src/demo_bringup/launch/mission.launch.py`. Il tient en une page et il se lit de haut en bas :

```python
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration, PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue

CONFIG_DIR = '/aeac/config'   # le repo est toujours monté à /aeac dans les conteneurs


def generate_launch_description():
    ld = LaunchDescription()

    sim = DeclareLaunchArgument('sim', default_value='false',
                                description='Vrai en simulation : aucun appel matériel')
    site = DeclareLaunchArgument('site', default_value='sim',
                                 description='Terrain, donc config/sites/<site>.yaml')
    mission = Node(
        package='demo_mission',
        executable='mission',
        name='demo_mission',
        output='screen',
        parameters=[
            f'{CONFIG_DIR}/demo.yaml',
            PathJoinSubstitution([f'{CONFIG_DIR}/sites',
                                  [LaunchConfiguration('site'), '.yaml']]),
            {'sim': ParameterValue(LaunchConfiguration('sim'), value_type=bool)},
        ],
    )

    ld.add_action(sim)
    ld.add_action(site)
    ld.add_action(mission)
    return ld
```

Le fichier déclare deux arguments et une node, puis les ajoute avec trois `add_action`. Les deux fichiers YAML sont donnés à la node tels quels : le launch file ne les ouvre pas, ne les lit pas et ne convertit rien. C'est `ros2 launch` qui les charge, dans l'ordre où ils sont écrits : `config/demo.yaml` d'abord, puis le fichier du site.

En formation 3.2, vous avez écrit un launch file avec `parameters=[{...}]` et rien d'autre. Celui-ci ajoute quelques éléments, chacun sur une ligne :

| Élément | Ce qu'il fait |
|---|---|
| `DeclareLaunchArgument('sim', default_value='false')` | Déclare un argument du launch file, qu'on passe à la commande sous la forme `sim:=true`. Si on ne le passe pas, il prend sa valeur par défaut. |
| `LaunchConfiguration('site')` | Donne la valeur de cet argument. Cette valeur n'existe qu'au lancement : on ne peut donc pas l'insérer dans une chaîne Python comme une variable ordinaire. |
| `PathJoinSubstitution([...])` | Assemble un chemin avec des morceaux connus seulement au lancement : `/aeac/config/sites/`, la valeur de `site`, puis `.yaml`. |
| `ParameterValue(..., value_type=bool)` | La valeur de l'argument est du texte, comme `'true'`. `ParameterValue` précise qu'elle doit arriver à la node sous forme de booléen. |
| Un chemin de fichier dans `parameters=[...]` | La liste accepte des fichiers YAML de paramètres à côté des dictionnaires. `ros2 launch` les applique dans l'ordre, et le dernier qui donne une valeur l'emporte. |

Un fichier de paramètres a toujours la même forme. Le premier niveau est le nom de la node visée : `demo_mission` dans `config/demo.yaml`, ou le joker `/**` (« toutes les nodes ») dans les fichiers de site. Le deuxième niveau est le mot-clé `ros__parameters`, avec deux `_`. Les valeurs viennent en dessous :

```yaml
demo_mission:
  ros__parameters:
    arrival_radius_m: 3.0
```

Si le nom d'une node ne correspond à aucune section, la node ne reçoit aucun paramètre, et aucune erreur ne s'affiche. On y revient en [5.3, section 3.2](5.3-projet-ajouter-un-node.md).

Ouvrez ensuite `workspaces/demo_ws/src/demo_mission/demo_mission/mission.py`. Le fichier fait un peu plus de deux cents lignes. Ne cherchez pas à tout comprendre : cherchez seulement les trois choses ci-dessous. Chaque réponse suit sa question, mais cherchez d'abord par vous-même.

**Où sont les noms de topics ?** La node publie son état sur `topics.DEMO_STATE`. Le publisher est créé ligne 125, et `publish_state` (lignes 225 à 230) s'en sert à chaque tour de timer. La constante est définie dans `packages/tools/tools/topics.py` et vaut `/aeac/external/demo/state`. Ce nom contient `external`, comme le heartbeat de 5.1 : l'état traverse donc la radio vers le sol. Le nom complet n'est écrit nulle part dans `mission.py`. Les noms de mavros, eux, sont écrits en haut du fichier, lignes 27 à 32 : cinq topics et un service. Ils sont là parce qu'ils appartiennent à un package tiers, et `topics.py` ne décrit que les topics `/aeac` écrits par l'équipe.

**Où sont les états ?** Les états sont dans `packages/custom_interfaces/msg/MissionState.msg`. Ce message est importé ligne 16 et utilisé partout sous la forme `MissionState.IDLE`, `MissionState.GOTO`, `MissionState.ACT`, `MissionState.RETURN`. Le fichier `.msg` définit ces quatre constantes et leurs valeurs, 0 à 3. Aucune node ne redéfinit ces constantes. Le message est donc la seule définition des états, et le sol lit les mêmes chiffres que le drone.

**Où est le waypoint ?** Le waypoint n'est nulle part dans le code. Cherchez-le dans `mission.py` : vous trouverez des paramètres `target.north_m` et `target.east_m` déclarés dans le bloc `PARAMETERS`, lignes 48 à 52, avec `0.0` en valeur par défaut, et rien d'autre. La vraie valeur vient de `config/sites/<site>.yaml`, que le launch file que vous venez de lire passe à la node. Cette valeur est une distance en mètres, au nord et à l'est du home. Le home, lui, vient de l'autopilote : c'est l'endroit où le drone a été armé, et mavros le publie sur `/mavros/home_position/home` (ligne 115). `home_callback` (lignes 143 à 145) calcule ensuite la position de la cible à partir du home, avec `offset_point` (lignes 63 à 67). Le terrain est donc une donnée, pas du code. Et comme la cible est comptée depuis le home, la même donnée fonctionne quel que soit l'endroit où le SITL démarre.

La machine à états elle-même tient dans la fonction `next_state`, lignes 70 à 86. Elle ne connaît ni ROS, ni mavros, ni le GPS : elle reçoit l'état courant, quelques booléens et deux distances, et renvoie le nouvel état ou `None`. On la relit en une minute, et on peut la tester sans rien lancer.

> [!TIP]
> **Jalon** : vous avez réussi cette section si vous pouvez dire, fichier et ligne à l'appui, d'où viennent le nom du topic d'état, la valeur `2` de l'état `ACT`, et la distance entre la cible et le home.

## 2 - Trois terminaux

Cette section est le cœur de la formation. Vous allez utiliser trois terminaux WSL, tous ouverts dans le repo, plus Mission Planner sous Windows.

```
  Windows                          WSL
+-------------+       TCP 5762   +--------------------------------------------+
|  Mission    |<-----------------|    +-----------------+  +----------------+ |
|  Planner    |                  |    | aeac-mavros-sim |  | aeac-dev       | |
|  (SITL)     |----------------->|    | mavros <-> SITL |  | le launch file | |
+-------------+                  |    | en arrière-plan |  | et les mocks   | |
                                 |    +-----------------+  +----------------+ |
                                 |                                            |
                                 |  Terminal 1 : make sim C=demo              |
                                 |  Terminal 2 : make takeoff, puis make rc   |
                                 |  Terminal 3 : make echo T=...              |
                                 |    les trois entrent dans aeac-dev         |
                                 +--------------------------------------------+
```

Avant tout, lancez le SITL dans Mission Planner comme en formation 1, et attendez qu'il soit prêt. Si le SITL ne tourne pas, mavros n'a rien à quoi se connecter, et le reste de la section ne fonctionnera pas.

### 2.1 - Terminal 1 : la simulation

```bash
make sim C=demo
```

Cette commande démarre deux conteneurs :

- `aeac-mavros-sim`, décrit dans `compose/sim.yml`, lance mavros en arrière-plan et le branche sur le SITL, à l'adresse `FCU_URL` que vous avez vue avec `make print-vars`.
- `aeac-dev` est le conteneur de développement. Le Makefile y lance le launch file de la mission, au premier plan dans ce terminal, avec `sim:=true site:=$(SITE)`.

`SITE` vaut `sim` par défaut.

La première fois, Docker doit d'abord construire l'image de mavros (`docker/dockerfile.mavros`), ce qui prend quelques minutes. Une fois les conteneurs démarrés, la node de mission affiche cette ligne :

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Dans les logs de ce document, l'horodatage que ROS 2 met après le niveau (`[INFO] [1758501234.512345678] [demo_mission]: ...`) est retiré pour la lisibilité.

Ce terminal n'affiche que la sortie du launch file. Pour voir les lignes de mavros, lancez `make logs IMG=mavros-sim` dans un autre terminal. C'est là que mavros signale s'il n'arrive pas à joindre le SITL. Laissez le terminal 1 tourner : c'est lui qui affiche le déroulement de la mission.

### 2.2 - Terminal 2 : le pilote et la manette

Le drone simulé est au sol, désarmé, en mode STABILIZE. Le code de mission ne le fera pas décoller, parce que la règle du repo est que le code de mission n'arme jamais le drone et ne change jamais son mode. En vol, c'est le pilote qui s'en charge. En simulation, une node de test joue ce rôle. Elle se lance avec sa propre cible make :

```bash
make takeoff
```

```
[WARN] [takeoff_test]: node de test : arme et décolle le drone
[INFO] [takeoff_test]: mode GUIDED
[INFO] [takeoff_test]: armement
[INFO] [takeoff_test]: décollage à 10.0 m
[INFO] [takeoff_test]: terminé
```

Si le SITL n'est pas encore tout à fait prêt, une étape peut être refusée. Une ligne comme `[WARN] [takeoff_test]: armement refusé par l'autopilote, nouvel essai` s'affiche alors, et la node renvoie la même étape une seconde plus tard. Vous n'avez rien à faire.

La node s'arrête toute seule dès que le décollage est accepté, et le drone continue de monter jusqu'à dix mètres dans Mission Planner. Le WARN au démarrage et le suffixe `_test` dans son nom signalent une node qui arme le drone ou change son mode. C'est la règle de `packages/sim_mocks/README.md`, et aucun launch file de mission n'inclut une telle node.

`make takeoff` s'exécute dans le conteneur qui tourne. De plus, `make takeoff` et `make rc` refusent de tourner ailleurs que dans le conteneur `dev`, celui de la simulation. Ainsi, une node qui arme le drone ne peut pas être lancée par erreur dans le conteneur du drone.

Le drone vole et attend un ordre. Dans le même terminal :

```bash
make rc
```

```
[INFO] [rc_simulator]: Manette simulée : w/s/x e/d/c r/f/v, q pour quitter
```

Cette node remplace la manette : elle lit votre clavier et publie des valeurs PWM sur `/mavros/rc/in`, dix fois par seconde, comme un vrai récepteur. Les touches `w`, `s` et `x` mettent le canal 8 en haut (1900), au centre (1500) et en bas (1100). Elle lit seulement le clavier du terminal où elle a été lancée. Pour que vos touches soient prises en compte, ce terminal doit donc avoir le focus.

Ne tapez encore rien : ouvrez d'abord le troisième terminal.

### 2.3 - Terminal 3 : l'état de la mission

```bash
make echo T=/aeac/external/demo/state
```

```
header:
  stamp:
    sec: 1758501234
    nanosec: 512000000
  frame_id: ''
state: 0
time_in_state: 3.5
---
```

`state` est un entier. Les constantes de `MissionState.msg` donnent l'état qui correspond à chaque valeur : `0` est `IDLE`, l'attente ; `1` est `GOTO`, en route vers le waypoint ; `2` est `ACT`, l'action sur place ; `3` est `RETURN`, le retour au point de départ. `time_in_state` est le nombre de secondes passées dans l'état courant, remis à zéro à chaque transition. Le message s'affiche deux fois par seconde, parce que `state_rate_hz` vaut `2.0` dans `config/demo.yaml`.

`make echo T=<topic>` est un raccourci pour `ros2 topic echo <topic>` dans le conteneur qui tourne.

### 2.4 - Le GO

Cliquez dans le terminal 2, celui du `rc_simulator`, et appuyez sur `w`.

```
[INFO] [rc_simulator]: canal 8 = 1900
```

Dans le terminal 1, la mission part :

```
[mission-1] [INFO] [demo_mission]: Transition IDLE -> GOTO
```

Dans Mission Planner, le drone se met en route vers le waypoint du site `sim`, une soixantaine de mètres au nord-est de l'endroit où il a décollé.

Quand il arrive à moins de trois mètres du waypoint (la valeur `arrival_radius_m` de `config/demo.yaml`) :

### 2.5 - Le pilote reste au-dessus du code

Redonnez le GO dans le terminal 2 : appuyez sur `s`, puis sur `w`. L'interrupteur doit quitter la position haute (passer sous 1700, la valeur `rc.go_pwm_min`) avant chaque GO. Sans cette règle, un interrupteur resté en haut relancerait la mission tout seul. Pendant que la mission est en `GOTO`, passez le drone en mode LOITER dans Mission Planner.

```
[mission-1] [INFO] [demo_mission]: Transition GOTO -> IDLE
[mission-1] [WARN] [demo_mission]: Le pilote a repris la main, mission interrompue
```

Dans tout état autre que `IDLE`, si le drone est désarmé ou quitte le mode GUIDED, la mission revient immédiatement en `IDLE` (`next_state`, lignes 73 à 75). La mission n'insiste pas et ne réessaie pas. Une node qui continuerait à publier des setpoints pendant que le pilote reprend la main serait dangereuse.

Pour repartir, repassez en GUIDED dans Mission Planner, puis redonnez le GO (`s`, puis `w`). Si vous donnez le GO alors que le drone est encore en LOITER, ou désarmé, la mission reste en `IDLE` et affiche un avertissement une seule fois :

```
[mission-1] [WARN] [demo_mission]: GO reçu mais le drone n'est pas armé en GUIDED
```

### 2.6 - Ce que `sim:=true` fait, et ce qu'il ne fait pas

Vous avez fait un tour complet de la mission. Il reste une question importante : qu'est-ce qui change entre ce que vous venez de lancer et ce qui volera au-dessus d'un terrain ?

La réponse est : presque rien. `make sim` lance, dans le conteneur `dev`, `ros2 launch demo_bringup mission.launch.py sim:=true site:=$(SITE)`. En vol, on lance le même launch file, avec `sim:=false`. Il n'y a donc pas deux fichiers, mais un seul fichier et un argument.

Cet argument ne fait qu'une chose : il devient le paramètre `sim` de la node. La node lit ce paramètre une fois au démarrage, ligne 94, et s'en sert à un seul endroit, ligne 214 :

```python
if not self.sim:
    self._trigger_payload()
```

`self.sim` sert à une seule chose : dire à la node qu'aucun matériel n'est branché. `_trigger_payload`, lignes 220 à 223, est l'endroit où une vraie mission appelle son matériel : ouvrir un servo, prendre une photo, larguer une charge. Dans la démo, `_trigger_payload` affiche seulement un WARN, parce qu'il n'y a rien à brancher.

La démo n'a qu'un appel matériel, donc un seul test de `self.sim`. Une vraie mission aura plusieurs appels matériels. Le piège est alors de répartir des `if self.sim` dans tout le fichier : vous ne savez plus ce que la simulation a vraiment prouvé. `ARCHITECTURE.md` donne la règle : regroupez les appels matériels derrière un seul `if not self.sim`, par exemple dans une méthode `_setup_hardware()` appelée une fois au démarrage. Le commentaire des lignes 210 à 213 le rappelle dans le code.

La machine à états et le message d'état sont un exemple, pas un gabarit imposé. Quatre états et un `time_in_state` suffisaient pour la démo. Une autre mission publiera autre chose, dans son propre message. Une seule chose ne change pas : l'état est défini dans `custom_interfaces`, et pas dans la node.

Remarquez enfin ce que le launch file ne lance pas. Vous avez lancé `takeoff_test` et `rc_simulator` à la main : aucun launch file de mission n'inclut un mock ou une node de test. C'est ce qui garantit qu'un mock ne peut pas se retrouver dans les airs.

Lisez `packages/sim_mocks/README.md`. C'est un tableau d'une page qui donne les trois nodes du package, ce que chacune remplace et la règle pour écrire un mock. La troisième node, `target_mock`, remplace une détection du conteneur vision.

<details>
<summary>Deux détails du code qui surprennent souvent</summary>

**Le setpoint republié.** Lignes 180 à 183, la node republie la position visée à chaque tour de timer, deux fois par seconde. Ce n'est pas une obligation : un setpoint de position globale peut n'être envoyé qu'une fois, s'il est bien reçu. Ce sont les setpoints de vitesse et d'accélération qui exigent un flux continu : sans ce flux, l'autopilote les abandonne. La démo republie quand même, parce que cela ne coûte qu'une ligne de code et qu'un message perdu est rattrapé au tour suivant.

**Le rayon d'arrivée.** `arrival_radius_m` vaut `3.0` dans `config/demo.yaml`. Il doit rester plus grand que le rayon à partir duquel l'autopilote considère un point comme atteint. Ce rayon est le paramètre ArduPilot `WPNAV_RADIUS`, en centimètres, qui vaut 200 par défaut. Si `arrival_radius_m` est plus petit, la mission attend une précision que ni le GPS ni l'autopilote ne garantissent, et `GOTO` peut ne jamais finir. Un commentaire le rappelle à côté de la valeur, dans `config/demo.yaml`.

</details>

### 2.7 - La position, la node la demande elle-même

Pour savoir qu'elle est arrivée, la mission a besoin de la position du drone. Or, vous l'avez vu en [formation 3.3, section 3](../3-ros2/3.3-mavros.md) : ArduPilot n'envoie sur une liaison que les messages qu'on lui demande, et personne ne demande ces messages sur la liaison de mavros. Sans demande, le topic `/mavros/global_position/global` existe mais ne publie rien. `distance_to` renvoie alors `None`, et la mission reste en `GOTO` pour toujours, avec le drone immobile au-dessus du waypoint.

`mission.py` applique donc cette leçon : la node demande elle-même ce dont elle a besoin. Lignes 120 à 124, elle crée un client du service `/mavros/set_message_interval` et un timer d'une seconde. À chaque tour du timer, `request_messages` (lignes 151 à 161) fait deux demandes. Elle demande le message 33, `GLOBAL_POSITION_INT`, à 5 Hz, sauf si une position fraîche est déjà là. Elle demande aussi le message 242, `HOME_POSITION`, tant que le home n'est pas arrivé.

Pourquoi redemander tant qu'aucune position fraîche n'arrive, au lieu d'une seule demande au démarrage ? Parce que la demande ne dure pas : elle se perd au redémarrage de l'autopilote. Si vous redémarrez le SITL pendant que la mission tourne, la position cesse d'arriver. Le timer détecte cette coupure et refait la demande, sans que personne ait à y penser. Tant que la position arrive, le timer ne fait rien.

Le home suit la même règle. L'autopilote n'envoie le home qu'au moment où il le fixe, c'est-à-dire à l'armement. Une node lancée après le décollage, ou relancée après un `Ctrl-C`, ne le verrait donc jamais passer. C'est la raison de la seconde demande. Tant que le home n'est pas arrivé, `tick` se contente de publier l'état (ligne 166), parce que sans home, il n'y a pas de cible.

<details>
<summary>Pourquoi la position arrive avec un profil QoS particulier</summary>

C'est le piège vu en [formation 3.3, section 2.4](../3-ros2/3.3-mavros.md). La QoS est un ensemble de réglages de livraison. Ces réglages doivent être compatibles entre la node qui publie et celle qui écoute. Sinon, le topic est bien listé, mais aucun message n'arrive. Les capteurs de mavros publient en BEST_EFFORT. C'est pourquoi, lignes 116 à 119 de `mission.py`, le subscriber de `/mavros/global_position/global` utilise `qos_profile_sensor_data` au lieu du `10` habituel. Sans ce profil, même si la demande de position réussissait, aucun message n'arriverait à la node.

</details>

## 3 - Mission, site, drone

### 3.1 - Trois fichiers, trois questions

Vous avez maintenant vu trois familles de réglages. `config/README.md` les classe selon une seule question : qu'est-ce qui fait changer cette valeur ?

`config/demo.yaml` change avec la mission. Il contient les gains, les seuils, les durées et le mapping des interrupteurs de la manette. Pour le mapping, `rc.go_channel` vaut `7` : c'est l'index du GO dans le message RC, donc le canal 8 de la manette et la touche `w` du `rc_simulator`. `rc.go_pwm_min` vaut `1700` : à partir de cette valeur, l'interrupteur compte comme haut. Le fichier contient aussi `arrival_radius_m`, `act_duration_s` et `state_rate_hz`. Changer de terrain ne touche pas à ce fichier.

`config/sites/sim.yaml` change avec le terrain. Il contient le nom du site (`site`) et deux valeurs : `target`, la cible en mètres au nord et à l'est du home, et `altitude_agl`, la hauteur de travail au-dessus du home. Le home n'est pas dans ce fichier : c'est l'autopilote qui le fournit, à l'endroit où le drone est armé. Le SITL de Mission Planner démarre là où sa carte est centrée. Comme la cible est comptée depuis le home, la démo fonctionne partout sans rien changer.

`config/drones/hexa.json5` change avec le drone. Il contient les adresses de la radio, qui permettent de viser un appareil précis depuis le sol. Vous n'ouvrirez pas ce fichier ici.

La règle derrière ce classement est celle de `config/README.md` : une valeur qui change entre deux drones, deux terrains ou deux essais n'est jamais écrite dans une node ni dans un launch file. Quand vous hésitez sur l'endroit où mettre un réglage, demandez-vous ce qui fait changer sa valeur, et pas où il serait pratique à lire.

### 3.2 - Déplacer le waypoint

Ouvrez `config/sites/sim.yaml`. Sans ses commentaires, il tient en cinq lignes. Il utilise le joker `/**` :

```yaml
/**:
  ros__parameters:
    site: sim
    target: {north_m: 50.0, east_m: 40.0}
    altitude_agl: 10.0
```

Éloignez la cible vers le nord :

```yaml
    target: {north_m: 150.0, east_m: 40.0}
```

`50.0` devient `150.0` : la cible s'éloigne de cent mètres vers le nord.

Ce fichier est lu au démarrage du launch file, pas en continu. Dans le terminal 1, faites `Ctrl-C`, puis lancez :

```bash
make sim C=demo
```

Le `Ctrl-C` n'arrête que le launch file. Le terminal affiche au passage une trace qui finit par `KeyboardInterrupt` et `process has died` : c'est seulement la node qui s'arrête, rien n'est cassé. Le conteneur `dev` et mavros continuent de tourner, donc les terminaux 2 et 3 aussi. Le drone reste armé en GUIDED, parce qu'il est dans le SITL et que le SITL n'a pas redémarré. Vous n'avez donc pas à refaire `make takeoff`.

Redonnez le GO dans le terminal 2 (`s`, puis `w`). Dans Mission Planner, le drone part cette fois vers un autre point, nettement plus loin. Rien n'a été reconstruit : `make build` n'a pas été relancé, parce qu'aucune ligne de code n'a changé.

```bash
git diff config/sites/sim.yaml
```

> [!TIP]
> **Jalon** : ce diff d'une ligne est le deuxième jalon à poster. C'est la preuve la plus courte qu'un waypoint n'est pas du code.

### 3.3 - Un deuxième site

Un repo de compétition a un fichier de site par terrain. Le repo en contient deux : `sim.yaml`, que vous venez de modifier, et `cimetiere.yaml`, le terrain de vol habituel du club. Ouvrez `cimetiere.yaml` : il a les mêmes clés que `sim.yaml`, avec d'autres distances.

Le choix du site se fait avec la variable `SITE` du Makefile, exactement comme `C` choisit la mission. Dans le terminal 1, faites `Ctrl-C`, puis lancez :

```bash
make sim C=demo SITE=cimetiere
```

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Comme la cible est comptée depuis le home, vous pouvez aussi tester ce site dans le SITL. Si vous voulez voir le drone partir plus loin vers le nord-est, redonnez le GO (`s`, puis `w`). L'exercice sert surtout à vérifier d'où vient le waypoint. Dans le terminal 3, arrêtez le `make echo` avec `Ctrl-C`, puis :

```bash
make shell
```

```bash
ros2 param get /demo_mission target.north_m
```

```
Double value is: 90.0
```

La valeur de `cimetiere.yaml` est bien arrivée dans la node, sans qu'une ligne de code ait changé et sans reconstruction.

> [!TIP]
> **Jalon** : cette sortie de `ros2 param get` est le troisième jalon à poster.

### 3.4 - Ce que le code refuse de faire

Essayez un site qui n'existe pas. Dans le terminal 1, faites `Ctrl-C`, puis lancez :

```bash
make sim C=demo SITE=inexistant
```

Dans le terminal 1, cherchez deux messages. Le premier est un avertissement de `ros2 launch`, `Parameter file path is not a file`, qui nomme le fichier de site introuvable. `ros2 launch` saute ce fichier et démarre la node quand même. La node démarre donc sans cible, et c'est elle qui refuse de continuer (`mission.py`, lignes 100 et 101) :

```
RuntimeError: Cible de site absente : vérifier config/sites/<site>.yaml
```

La node meurt, et la mission ne part pas. Le même refus se produit si le fichier existe mais que la cible vaut zéro. Dans ce cas, aucun avertissement ne s'affiche. L'avertissement est facile à rater au milieu des autres lignes, mais c'est lui qui nomme le fichier : lisez-le avant de chercher ailleurs.

Les valeurs par défaut de la cible sont `0.0`, ce qui place la cible sur le home, là où le drone se trouve déjà. Une valeur par défaut sûre est une valeur qui ne fait pas voler le drone. Une node qui démarre quand même avec un waypoint faux est bien plus dangereuse qu'une node qui refuse de démarrer au sol.

Relancez la démo sur le bon site, parce que la section 4 en a besoin :

```bash
make sim C=demo
```

La seconde chose que le code refuse concerne la fraîcheur de la donnée. `distance_to` (lignes 190 à 193) renvoie `None` quand la dernière position GPS reçue a plus de deux secondes. Cette limite est `POSITION_MAX_AGE_S` (ligne 42), vérifiée par `position_is_fresh`, juste au-dessus de `distance_to`. `next_state` ne déclare aucune arrivée tant qu'une distance vaut `None`. Si le lien avec l'autopilote se coupe, la mission reste donc en `GOTO` : elle ne conclut pas qu'elle est arrivée à partir d'une position périmée. Pendant ce temps, `request_messages` redemande la position chaque seconde. Une vieille position ne prouve pas où le drone se trouve, elle prouve où il se trouvait.

## 4 - Enregistrer

On ne peut pas rejouer un vol. Ce qui n'a pas été enregistré pendant l'essai est perdu. Or, pour répondre aux questions qu'on se pose le soir même, il faut toujours des données. C'est pour cela qu'on enregistre à chaque vol, même quand tout va bien.

La simulation tourne dans le terminal 1, le `rc_simulator` dans le terminal 2. Ouvrez un quatrième terminal, dans le repo :

```bash
make bag
```

L'enregistrement démarre dans un dossier daté sous `bags/`, par exemple `bags/2026-09-22_14-30`. Pendant l'enregistrement, faites un tour complet de mission, du GO (`s`, puis `w`, dans le terminal 2) jusqu'au retour en `IDLE`. Faites ensuite `Ctrl-C` dans ce quatrième terminal.

Le Makefile n'enregistre pas tous les topics. Il passe cette expression régulière à `ros2 bag record` :

```
/aeac/.*|/mavros/(state|rc/in|local_position/pose|global_position/global)
```

Cette expression prend tout ce que l'équipe publie, plus quatre topics mavros : l'état de l'autopilote, les entrées de la manette, la position locale et la position globale. C'est ce qu'il faut pour rejouer une mission et comprendre pourquoi elle a fait ce qu'elle a fait. Les autres topics de mavros sont volumineux et rarement utiles, donc ils ne sont pas enregistrés. S'il vous manque un jour un topic, modifiez la liste dans le Makefile : le prochain enregistrement l'inclura.

Le terminal 3 est toujours dans le conteneur depuis la section 3.3. Cherchez-y le nom exact de votre dossier :

```bash
ls /aeac/bags
```

Puis, avec ce nom à la place de la date d'exemple :

```bash
ros2 bag info /aeac/bags/2026-09-22_14-30
```

```
Files:             2026-09-22_14-30_0.db3
Duration:          48.2s
Messages:          867
Topic information: Topic: /aeac/external/demo/state | Type: custom_interfaces/msg/MissionState | Count: 96
                   Topic: /mavros/state | Type: mavros_msgs/msg/State | Count: 48
                   Topic: /mavros/rc/in | Type: mavros_msgs/msg/RCIn | Count: 482
                   Topic: /mavros/global_position/global | Type: sensor_msgs/msg/NavSatFix | Count: 241
                   Topic: /mavros/local_position/pose | Type: geometry_msgs/msg/PoseStamped | Count: 0
```

Cette sortie est un extrait : la vraie sortie a quelques lignes de plus, et vos nombres seront différents. Vous pouvez vérifier chaque compte avec la fréquence de son publisher. Le topic d'état, à 2 Hz, donne à peu près le double de la durée en secondes. La position globale, demandée à 5 Hz, donne au moins cinq fois la durée (en SITL, elle arrive souvent à 10 Hz, donc dix fois). Le `rc_simulator`, à 10 Hz, donne dix fois la durée. Si un compte est loin de sa valeur attendue, ce publisher ne tournait pas pendant tout l'enregistrement.

`/mavros/local_position/pose` fait partie de l'enregistrement, mais il est vide. Ce topic vient du message 32, et la démo ne demande que le message 33. Une mission qui utilise la position locale demanderait le message 32, et le bag contiendrait alors ce topic.

`bags/` est ignoré par git, comme `models/`. On ne fait jamais de commit d'un rosbag : on le partage autrement.

En fin de séance, faites `Ctrl-C` dans le terminal 1, puis `make down`. `make down` arrête `dev` et `mavros-sim`, et donc tout ce qui tournait dans les autres terminaux.

## 5 - Quand ça ne marche pas : la démarche

Cette section n'est pas une liste de pannes : cette liste se trouve dans la table de la section 6. Cette section donne l'ordre dans lequel on cherche une panne. Cet ordre est plus utile que n'importe quelle liste, parce qu'il fonctionne encore face à une panne que personne n'a jamais vue.

La recherche se fait sur trois étages. Vérifiez chaque étage avant de descendre au suivant.

**Étage 1 : est-ce que le conteneur tourne ?**

```bash
docker ps
```

Vous devez voir `aeac-dev` et `aeac-mavros-sim`. S'il en manque un, relancez `make sim C=demo`. Si mavros ne se connecte pas, la raison est affichée dans `make logs IMG=mavros-sim`. Si le launch file s'est arrêté, sa trace d'erreur est dans le terminal 1. Tant que cet étage n'est pas réglé, les commandes `ros2` ne vous apprendront rien : aucune node ne tourne pour publier, et une liste de topics vide ne veut alors rien dire. C'est le piège de cet étage, et c'est pour cela qu'il vient en premier.

**Étage 2 : est-ce que la node tourne ?**

```bash
make shell
```

```bash
ros2 node list
```

```
/demo_mission
/mavros
...
/rc_simulator
```

mavros 2 apparaît sous plusieurs noms, à la place des `...`. Leur nombre exact n'a pas d'importance ici. Une node que vous n'avez pas lancée, ou un `/demo_mission` en double, vient en général d'un poste voisin (voir la table de la section 6).

Si une node est absente de cette liste alors que son conteneur tourne, c'est qu'elle est morte au lancement. Remontez les lignes du launch file dans le terminal 1 et cherchez la trace d'exception. S'il manque toutes les nodes de mavros, retournez à l'étage 1 : `aeac-mavros-sim` tourne-t-il encore ?

**Étage 3 : est-ce que la donnée circule ?**

```bash
ros2 topic hz /aeac/external/demo/state
```

Une fréquence autour de 2 veut dire que le publisher est vivant. Si la commande n'affiche rien alors que le topic est listé, le publisher ne publie rien.

Pour la position de mavros, l'absence de sortie peut avoir une cause de plus : personne n'a demandé la position (section 2.7). Si `ros2 topic hz` voit passer les messages mais que votre node ne reçoit rien, le problème vient de la QoS (section 2.7). `ros2 topic info -v <topic>` affiche les profils QoS des deux côtés.

Enfin, quand tout circule mais que le comportement est faux, regardez les valeurs que la node a reçues :

```bash
ros2 param get /demo_mission arrival_radius_m
```

Si vous sautez un étage, vous risquez de chercher au mauvais endroit. Sur le drone, un étage de plus s'ajoutera au-dessus des trois autres. Là-bas, ce n'est pas vous qui lancez les programmes, mais systemd. La première question devient donc : « est-ce que le service a démarré ? ».

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `make logs IMG=mavros-sim` répète que mavros n'arrive pas à se connecter | Le SITL n'est pas lancé, ou `FCU_URL` est faux | Lancer le SITL dans Mission Planner d'abord ; `make print-vars` pour voir `FCU_URL` |
| `mavros-sim` ne se connecte jamais alors que le SITL tourne, et `docker ps` montre `mavros` ou `b3-mavros` | Un mavros des formations 2 ou 3 est resté allumé et occupe le port 5762 | `make down` dans le dossier de cette formation-là, puis `make sim C=demo` |
| mavros ne se connecte jamais alors que le SITL tourne bien | WSL en mode NAT (Windows 10), ou le SITL tourne sur une autre machine | Dans `.env` : `SITL_HOST=<adresse de ip route show default>` en NAT, ou `SITL=<URL mavros>` pour l'autre machine (5.1, section 3.2) ; `make print-vars` pour vérifier `FCU_URL` |
| Le GO ne passe pas, `rc_simulator` n'affiche rien | Le terminal du `rc_simulator` n'a pas le focus clavier | Cliquer dans ce terminal avant d'appuyer sur `w` |
| Le GO ne passe pas, `rc_simulator` affiche bien `canal 8 = 1900` | L'interrupteur doit quitter la position haute (sous 1700) avant chaque GO | `s` ou `x`, puis `w` |
| L'état ne change pas après le GO, et un WARN parle de GUIDED | Le drone n'est pas armé, ou pas en GUIDED | `make echo T=/mavros/state` (champs `armed` et `mode`) ; au sol, `make takeoff` ; en l'air, repasser en GUIDED dans Mission Planner (section 2.5) |
| La mission reste en `GOTO` alors que le drone est au-dessus du waypoint | La position n'arrive pas à la node, ou `arrival_radius_m` est trop petit | `ros2 topic hz /mavros/global_position/global` : sans sortie, mavros est-il connecté (`make logs IMG=mavros-sim`) ? la demande de position est-elle toujours dans le code (section 2.7) ? Sinon `ros2 param get /demo_mission arrival_radius_m`, à garder au-dessus de `WPNAV_RADIUS / 100` (section 2.6) |
| La mission reste en `IDLE` après le GO, sans aucun WARN | Le home n'est pas arrivé : sans lui, la node n'a pas de cible | `ros2 topic hz /mavros/home_position/home` : sans sortie, mavros est-il connecté (`make logs IMG=mavros-sim`) ? la demande du message 242 est-elle toujours dans `request_messages` (section 2.7) ? |
| La mission s'arrête au lancement sur `No module named 'custom_interfaces'` | Le workspace a été construit alors que ses liens étaient encore des fichiers texte (copie depuis Windows) | `make build C=demo`, qui recrée les liens, puis relancer ; `ls -l workspaces/demo_ws/src` doit montrer trois flèches (section 1.1) |
| Le waypoint n'a pas bougé après modification du YAML | Mauvais fichier modifié (celui de `workspaces/` au lieu de celui de `config/`), `SITE=` oublié, ou simulation pas relancée | `ros2 param get /demo_mission target.north_m` (section 3.3) |
| La node meurt au démarrage sur `Cible de site absente`, avec plus haut un avertissement `Parameter file path is not a file` | Nom de site inexistant dans `SITE=` (sans l'avertissement : cible à zéro dans le fichier du site) | `ls config/sites/`, puis relancer avec le bon `SITE=` (section 3.4) |
| `make shell` répond qu'aucun conteneur ne tourne | `aeac-dev` n'est pas démarré | `make sim C=demo` dans le terminal 1, puis `docker ps` |
| Deux valeurs différentes pour le même paramètre selon le moment | Deux nodes `demo_mission` tournent : la fenêtre du terminal 1 a été fermée au lieu d'un `Ctrl-C`, et le launch file précédent tourne encore dans `dev` | `make down`, puis `make sim C=demo` |
| Le GO part tout seul, ou `ros2 topic info` compte plus d'abonnés que vous n'avez de terminaux ouverts | Une fenêtre fermée au lieu d'un `q` (pour `make rc`) ou d'un `Ctrl-C` laisse sa commande tourner dans `aeac-dev` : un vieux `rc_simulator` resté à 1900 donne le GO à la place du nouveau | `make down`, puis `make sim C=demo` ; à l'avenir, quitter la commande avant de fermer la fenêtre |
| Deux `demo_mission`, le GO part tout seul, ou `ros2 node list` montre des nodes que vous n'avez pas lancées | Un autre poste sur le même réseau utilise le même domaine ROS : ses nodes et les vôtres se voient | Dans `.env` : `SIM_DOMAIN=<numéro>`, un numéro par poste (voir `.env.example`), puis `make down` et `make sim C=demo` |
| Rien ne répond et on ne sait pas par où commencer | C'est le cas normal | Les trois étages de la section 5, dans l'ordre, sans en sauter un |
