# Formation 5.2 : une mission en simulation

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Installer un workspace de mission dans un repo de compétition et le construire
- Lancer une mission en simulation dans trois terminaux et suivre sa machine à états
- Expliquer ce que fait le paramètre `sim` et pourquoi le launch file de vol et celui de simulation sont le même fichier
- Dire où va un réglage : dans la mission, dans le site ou dans le drone
- Enregistrer un rosbag et vérifier ce qu'il contient
- Chercher une panne dans l'ordre : conteneur, node, donnée

Prérequis : la [formation 5.1](5.1-le-repo-vu-de-haut.md) terminée (repo template cloné, `make init`, `gcs_ws` construit), et le SITL de Mission Planner qui démarre, comme en formation 1.

En 5.1 vous avez visité le repo et lancé une seule node, le heartbeat du sol. Ici une vraie mission tourne. Elle est réduite à son squelette : quatre états, un waypoint, un interrupteur.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 2 h.
> - **Prérequis** : 5.1 faite, le SITL de Mission Planner qui démarre, et le conteneur `dev` de 5.1 arrêté (`make down`). Arrêtez aussi un mavros resté allumé depuis les formations 2 ou 3 (conteneur `mavros` ou `b3-mavros` dans `docker ps`) : il occupe le port 5762 du SITL, et celui de la simulation ne pourrait pas s'y brancher. `make down` dans le dossier de cette formation-là suffit. Avant d'ouvrir un terminal, prenez une feuille et écrivez les dossiers du repo avec une phrase chacun. Deux minutes, sans regarder. C'est le jalon de 5.1, section 2.
> - **À la fin** : la machine à états de la démo est passée par `IDLE`, `GOTO`, `ACT` et `RETURN` sans qu'aucun vrai drone ne vole, et le waypoint qu'elle vise vient d'un fichier YAML que vous avez modifié.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une capture des quatre transitions, le diff de votre fichier de site, et la sortie du `ros2 param get` de la section 3.3.

Tout se passe sur votre poste WSL, dans votre clone du template, le dossier `mission-template` que vous avez déjà.

Travaillez sur une branche à vous. Une branche est une copie de travail du repo, avec un nom. Tant que vous êtes dessus, vos modifications ne touchent pas `main`. Dans un repo de compétition, `main` est ce qui vole ; sur le template, c'est la référence que tout le monde clone. C'est cette branche que le lead relira en 5.3. Placez-vous d'abord dans votre clone :

```bash
cd ~/mission-template
```

```bash
git switch -c prenom/demo
```

Remplacez `prenom` par le vôtre. `git switch -c` crée la branche et vous place dessus ; `git branch --show-current` vous dira toujours où vous êtes.

## 1 - Poser la démo

### 1.1 - Copier et construire

Le workspace de la démo est fourni dans le dossier de la formation, sous `5-env_compétition/demo_ws/`. Il ne fait pas partie du repo de mission : vous l'y installez. Il y a deux façons de le faire.

**Option A, au terminal (la plus sûre).** Depuis la racine du clone, en remplaçant `<dossier de la formation>` par le chemin de votre clone de Formations-Controle (`~/Formations-Controle` si vous avez suivi la formation 2) :

```bash
cp -r <dossier de la formation>/5-env_compétition/demo_ws workspaces/
```

**Option B, dans VS Code.** Ouvrez votre clone de `mission-template` dans VS Code, puis ouvrez le dossier Formations-Controle dans une seconde fenêtre. Dans l'explorateur de la seconde fenêtre, attrapez le dossier `5-env_compétition/demo_ws` et déposez-le sur le dossier `workspaces/` de la première.

Les trois liens symboliques de `demo_ws/src` arrivent parfois en fichiers texte : avec l'option B, ou quand votre clone de Formations-Controle est sous Windows (`/mnt/c`). Rien à faire : `make build`, plus bas, les recrée et l'écrit (`Lien réparé`).

Même chose pour les réglages de la mission, qui vont ailleurs. Copiez-les avec le terminal (un glisser dans VS Code déplacerait le fichier au lieu de le copier) :

```bash
cp workspaces/demo_ws/src/demo_bringup/config/demo.yaml config/
```

Deux copies, deux endroits. Le code de la mission va avec le code des autres missions, dans `workspaces/`. Ses réglages vont avec les réglages des autres missions, dans `config/`. On sépare les deux parce qu'on change un réglage souvent et le code rarement : un waypoint, un seuil ou une durée se modifient entre deux essais sans toucher à une ligne de Python. Le launch file de la démo donne à la node deux fichiers de `/aeac/config/`, `demo.yaml` pour la mission et `sites/<site>.yaml` pour le terrain, et rien d'autre.

La démo se sert de trois packages partagés : `tools` pour les noms de topics, `custom_interfaces` pour le message d'état, et `sim_mocks` pour les nodes de simulation de la section 2 : des mocks, qui remplacent le matériel absent, et une node de test, qui joue le pilote. Comme dans `gcs_ws` en 5.1, les liens vers `packages/` sont déjà dans le workspace, posés par un lead.

```bash
make build C=demo
```

Cinq packages : les trois partagés, `demo_mission` qui porte la node, et `demo_bringup` qui porte le launch file. Comme en 5.1, les durées sont retirées et l'ordre des lignes peut varier, mais pas celui des dépendances : `demo_mission` attend `tools`, et `demo_bringup` attend `demo_mission`, qu'il lance.

### 1.2 - Lire avant de lancer

Commencez par le launch file, `workspaces/demo_ws/src/demo_bringup/launch/mission.launch.py`. Il tient en une page et il se lit de haut en bas :

```python
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration, PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue

CONFIG_DIR = '/aeac/config'   # le repo est toujours monté à /aeac dans les conteneurs


def generate_launch_description():
    ld = LaunchDescription()

    sim = DeclareLaunchArgument('sim', default_value='false',
                                description='Vrai en simulation : aucun appel matériel')
    site = DeclareLaunchArgument('site', default_value='sim',
                                 description='Terrain, donc config/sites/<site>.yaml')
    mission = Node(
        package='demo_mission',
        executable='mission',
        name='demo_mission',
        output='screen',
        parameters=[
            f'{CONFIG_DIR}/demo.yaml',
            PathJoinSubstitution([f'{CONFIG_DIR}/sites',
                                  [LaunchConfiguration('site'), '.yaml']]),
            {'sim': ParameterValue(LaunchConfiguration('sim'), value_type=bool)},
        ],
    )

    ld.add_action(sim)
    ld.add_action(site)
    ld.add_action(mission)
    return ld
```

Deux arguments, une node, trois `add_action`. Les deux fichiers YAML sont donnés à la node tels quels : le launch file ne les ouvre pas, ne les lit pas et ne convertit rien. C'est `ros2 launch` qui les charge, dans l'ordre où ils sont écrits, `config/demo.yaml` puis le fichier du site.

En formation 3.2, vous avez écrit un launch file avec `parameters=[{...}]` et rien d'autre. Celui-ci ajoute quelques pièces, une ligne chacune :

| Pièce | Ce qu'elle fait |
|---|---|
| `DeclareLaunchArgument('sim', default_value='false')` | Déclare un argument du launch file, qu'on passe à la commande sous la forme `sim:=true`. Sans rien, il vaut sa valeur par défaut. |
| `LaunchConfiguration('site')` | La valeur de cet argument. Elle n'existe qu'au lancement, donc on ne peut pas la coller dans une chaîne Python comme une variable ordinaire. |
| `PathJoinSubstitution([...])` | Assemble un chemin avec des morceaux connus seulement au lancement : `/aeac/config/sites/`, la valeur de `site`, puis `.yaml`. |
| `ParameterValue(..., value_type=bool)` | Précise que la valeur de l'argument, du texte comme `'true'`, doit arriver à la node en booléen. |
| Un chemin de fichier dans `parameters=[...]` | La liste accepte des fichiers YAML de paramètres à côté des dictionnaires ; `ros2 launch` les applique dans l'ordre, et le dernier qui donne une valeur l'emporte. |

Un fichier de paramètres a toujours la même forme. Le premier niveau est le nom de la node visée, `demo_mission` dans `config/demo.yaml`, ou le joker `/**`, « toutes les nodes », dans les fichiers de site. Le deuxième est le mot-clé `ros__parameters`, avec deux `_`. Les valeurs viennent dessous :

```yaml
demo_mission:
  ros__parameters:
    arrival_radius_m: 3.0
```

Une node dont le nom ne correspond à aucune section ne reçoit rien, sans erreur : on y revient en [5.3, section 3.2](5.3-projet-ajouter-un-node.md).

Ouvrez ensuite `workspaces/demo_ws/src/demo_mission/demo_mission/mission.py`. Un peu plus de deux cents lignes. Ne cherchez pas à tout comprendre : cherchez trois choses, et seulement elles. Les réponses sont juste en dessous, mais cherchez d'abord.

**Où sont les noms de topics ?** La node publie son état sur `topics.DEMO_STATE` : le publisher est créé ligne 125, et `publish_state`, lignes 225 à 230, s'en sert à chaque tour de timer. La constante est dans `packages/tools/tools/topics.py` et vaut `/aeac/external/demo/state` : `external`, comme le heartbeat de 5.1, donc l'état traverse la radio vers le sol. Le nom complet n'est écrit nulle part dans `mission.py`. Les noms de mavros, eux, sont en haut du fichier, lignes 27 à 32, cinq topics et un service : ils appartiennent à un package tiers, et `topics.py` ne décrit que les topics `/aeac` écrits par l'équipe.

**Où sont les états ?** Dans `packages/custom_interfaces/msg/MissionState.msg`, importé ligne 16 et utilisé partout sous la forme `MissionState.IDLE`, `MissionState.GOTO`, `MissionState.ACT`, `MissionState.RETURN`. Le fichier `.msg` définit ces quatre constantes et leurs valeurs, 0 à 3. Aucune node ne les redéfinit : le message est la seule définition des états, et le sol lit les mêmes chiffres que le drone.

**Où est le waypoint ?** Nulle part dans le code. Cherchez-le dans `mission.py` : vous trouverez des paramètres `target.north_m` et `target.east_m` déclarés dans le bloc `PARAMETERS`, lignes 48 à 52, avec `0.0` en valeur par défaut, et rien d'autre. La vraie valeur arrive de `config/sites/<site>.yaml`, passé à la node par le launch file que vous venez de lire : une distance en mètres, au nord et à l'est du home. Le home, lui, vient de l'autopilote : c'est l'endroit où le drone a armé, que mavros publie sur `/mavros/home_position/home` (ligne 115). `home_callback`, lignes 143 à 145, en tire la position de la cible avec `offset_point`, lignes 63 à 67. Le terrain est une donnée, pas du code, et la même donnée marche où que le SITL démarre.

La machine à états elle-même tient dans la fonction `next_state`, lignes 70 à 86. Elle ne connaît ni ROS, ni mavros, ni le GPS : elle reçoit l'état courant, quelques booléens et deux distances, et rend le nouvel état ou `None`. Elle se relit en une minute et se teste sans rien lancer.

> [!TIP]
> **Jalon** : vous avez réussi cette section si vous pouvez dire, fichier et ligne à l'appui, d'où viennent le nom du topic d'état, la valeur `2` de l'état `ACT`, et la distance entre la cible et le home.

C'est le cœur de la formation. Trois terminaux WSL, tous ouverts dans le repo, plus Mission Planner sous Windows. Un quatrième servira en section 4, le temps d'un enregistrement.

|  (SITL)     |----------------->|    | mavros <-> SITL |  | le launch file | |
+-------------+                  |    | en arrière-plan |  | et les mocks   | |

                                 |  Terminal 3 : make echo T=...              |

Avant tout : lancez le SITL dans Mission Planner comme en formation 1, et attendez qu'il soit prêt. Si le SITL ne tourne pas, mavros n'a personne à qui parler et le reste de la section ne donnera rien.

### 2.1 - Terminal 1 : la simulation

```bash
make sim C=demo
```

Cette commande démarre deux conteneurs :

- `aeac-mavros-sim`, décrit dans `compose/sim.yml`, lance mavros en arrière-plan et le branche sur le SITL, à l'adresse `FCU_URL` que vous avez vue avec `make print-vars` en 5.1.
- `aeac-dev` est le conteneur de 5.1. Le Makefile y lance le launch file de la mission, au premier plan dans ce terminal, avec `sim:=true site:=$(SITE)`.

`SITE` vaut `sim` tant que vous ne dites rien ; on le change en section 3.3.

La première fois, Docker construit d'abord l'image de mavros (`docker/dockerfile.mavros`) : comptez quelques minutes. Une fois les conteneurs démarrés, vous voyez la ligne de la node de mission :

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Dans les logs de ce document, l'horodatage que ROS 2 met après le niveau (`[INFO] [1758501234.512345678] [demo_mission]: ...`) est retiré pour la lisibilité.

Ce terminal n'affiche que le launch file. Les lignes de mavros sont ailleurs, avec `make logs IMG=mavros-sim` dans un autre terminal : c'est là que mavros dit s'il n'arrive pas à joindre le SITL. Laissez le terminal 1 tourner, c'est lui qui affiche la vie de la mission.

### 2.2 - Terminal 2 : le pilote et la manette

Le drone simulé est au sol, désarmé, en mode STABILIZE. Le code de mission ne le fera pas décoller : la règle du repo est que le code de mission n'arme jamais et ne change jamais de mode. En vol c'est le pilote qui le fait. En simulation, une node de test tient ce rôle, et elle a sa cible make :

```bash
make takeoff
```

```
[WARN] [takeoff_test]: node de test : arme et décolle le drone
[INFO] [takeoff_test]: mode GUIDED
[INFO] [takeoff_test]: armement
[INFO] [takeoff_test]: décollage à 10.0 m
[INFO] [takeoff_test]: terminé
```

Si le SITL n'est pas encore tout à fait prêt, une étape peut être refusée. Une ligne comme `[WARN] [takeoff_test]: armement refusé par l'autopilote, nouvel essai` s'affiche alors, et la node renvoie la même étape une seconde plus tard. Vous n'avez rien à faire.

La node s'arrête toute seule dès que le décollage est accepté, et le drone continue de monter jusqu'à dix mètres dans Mission Planner. Le WARN du démarrage et le suffixe `_test` de son nom signalent une node qui arme ou change de mode : c'est la règle de `packages/sim_mocks/README.md`, et aucun launch file de mission n'inclut une telle node.

`make takeoff` entre dans le conteneur qui tourne, comme `make shell` en 5.1. `make takeoff` et `make rc` refusent en plus de tourner ailleurs que dans le conteneur `dev`, celui de la simulation : une node qui arme ne peut pas partir par erreur dans le conteneur du drone.

Le drone vole, il attend un ordre. Dans le même terminal :

```bash
make rc
```

```
[INFO] [rc_simulator]: Manette simulée : w/s/x e/d/c r/f/v, q pour quitter
```

Cette node remplace la manette : elle lit votre clavier et publie des valeurs PWM sur `/mavros/rc/in`, dix fois par seconde, comme un vrai récepteur. Les touches `w`, `s` et `x` mettent le canal 8 en haut (1900), au centre (1500) et en bas (1100). Elle lit le clavier du terminal où elle a été lancée : pour que vos touches comptent, c'est ce terminal qui doit avoir le focus.

Ne tapez encore rien : ouvrez d'abord le troisième terminal.

### 2.3 - Terminal 3 : l'état de la mission

```bash
make echo T=/aeac/external/demo/state
```

```
header:
  stamp:
    sec: 1758501234
    nanosec: 512000000
  frame_id: ''
state: 0
time_in_state: 3.5
---
```

`state` est un entier, et c'est là que `MissionState.msg` devient utile : `0` est `IDLE`, l'attente ; `1` est `GOTO`, en route vers le waypoint ; `2` est `ACT`, l'action sur place ; `3` est `RETURN`, le retour au point de départ. `time_in_state` est le nombre de secondes passées dans l'état courant, remis à zéro à chaque transition. Le tout défile deux fois par seconde, parce que `state_rate_hz` vaut `2.0` dans `config/demo.yaml`.

`make echo T=<topic>` est un raccourci pour `ros2 topic echo <topic>` dans le conteneur qui tourne.

### 2.5 - Le pilote reste au-dessus du code

Redonnez le GO dans le terminal 2 : `s`, puis `w`. L'interrupteur doit repasser en bas avant chaque GO, sinon un interrupteur resté en haut relancerait la mission tout seul. Pendant que la mission est en `GOTO`, passez le drone en mode LOITER dans Mission Planner.

```
[mission-1] [INFO] [demo_mission]: Transition GOTO -> IDLE
[mission-1] [WARN] [demo_mission]: Le pilote a repris la main, mission interrompue
```

Hors de `IDLE`, perdre l'armement ou le mode GUIDED ramène la mission en `IDLE` immédiatement (`next_state`, lignes 73 à 75). La mission ne discute pas et ne réessaie pas. Une node qui continuerait à publier des setpoints pendant que le pilote reprend la main serait une node dangereuse.

Pour repartir, repassez en GUIDED dans Mission Planner, puis redonnez le GO (`s`, puis `w`). Si vous donnez le GO encore en LOITER, ou avec un drone désarmé, la mission reste en `IDLE` et prévient une fois :

```
[mission-1] [WARN] [demo_mission]: GO reçu mais le drone n'est pas armé en GUIDED
```

### 2.6 - Ce que `sim:=true` fait, et ce qu'il ne fait pas

Maintenant que le tour est bouclé, la question qui compte : qu'est-ce qui change entre ce que vous venez de lancer et ce qui volera au-dessus d'un terrain ?

Presque rien. `make sim` lance, dans le conteneur `dev`, `ros2 launch demo_bringup mission.launch.py sim:=true site:=$(SITE)`. En vol, on lance le même launch file, avec `sim:=false`. Ce ne sont pas deux fichiers, c'est un fichier et un argument, déclaré dans le `DeclareLaunchArgument` que vous avez lu en 1.2.

Cet argument ne fait qu'une chose : il devient le paramètre `sim` de la node. Elle le lit une fois au démarrage, ligne 94, et s'en sert à un seul endroit, ligne 214 :

```python
if not self.sim:
    self._trigger_payload()
```

Voyez `self.sim` comme un outil : il dit à la node qu'aucun matériel n'est branché. `_trigger_payload`, lignes 220 à 223, est l'endroit où une vraie mission appelle son matériel : ouvrir un servo, prendre une photo, larguer une charge. La démo se contente d'un WARN, parce qu'il n'y a rien à brancher.

La démo n'a qu'un appel matériel, donc un seul test. Une vraie mission en aura plusieurs, et le piège est de semer des `if self.sim` dans tout le fichier : vous ne savez alors plus ce que la simulation a vraiment prouvé. La règle d'`ARCHITECTURE.md` : regroupez les appels matériels derrière un seul `if not self.sim`, par exemple dans une méthode `_setup_hardware()` appelée une fois au démarrage. Le commentaire des lignes 210 à 213 le rappelle dans le code.

La machine à états et le message d'état sont un exemple, pas un gabarit imposé. Quatre états et un `time_in_state`, c'est ce qui convenait à la démo. Une autre mission publiera autre chose, dans un message à elle. Ce qui ne change pas, c'est que l'état vit dans `custom_interfaces` et pas dans la node.

Remarquez enfin ce que le launch file ne lance pas. `takeoff_test` et `rc_simulator`, vous les avez lancés à la main, et aucun launch file de mission n'inclut un mock ou une node de test : c'est ce qui garantit qu'un mock ne peut pas se retrouver dans les airs. (Un lead peut ajouter un launch file réservé à la simulation qui démarre la mission et ses mocks d'un coup : [annexe 5.4, section 2](5.4-annexe-leads-creer-un-environnement.md).)

Lisez `packages/sim_mocks/README.md`, un tableau d'une page : les trois nodes du package, ce que chacune remplace, et la règle pour écrire un mock. La troisième, `target_mock`, remplace une détection du conteneur vision ; elle vous servira avec la formation vision.

<details>
<summary>Deux détails du code qui surprennent souvent</summary>

**Le setpoint republié.** Lignes 180 à 183, la node republie la position visée à chaque tour de timer, deux fois par seconde. Ce n'est pas une obligation : un setpoint de position globale peut n'être envoyé qu'une fois, s'il est bien reçu. Ce sont les setpoints de vitesse et d'accélération qui exigent un flux continu, faute de quoi l'autopilote les abandonne. La démo republie quand même : c'est une ligne de code, et un message perdu est rattrapé au tour suivant.

**Le rayon d'arrivée.** `arrival_radius_m` vaut `3.0` dans `config/demo.yaml`, et il doit rester plus grand que le rayon où l'autopilote déclare un point atteint : le paramètre ArduPilot `WPNAV_RADIUS`, en centimètres, 200 par défaut. En dessous, la mission attend une précision que ni le GPS ni l'autopilote ne garantissent, et `GOTO` peut ne jamais finir. Le commentaire de `config/demo.yaml` le dit à côté de la valeur.

</details>

### 2.7 - La position, la node la demande elle-même

Pour savoir qu'elle est arrivée, la mission a besoin de la position du drone. Or vous l'avez vu en [formation 3.3, section 3](../3-ros2/3.3-mavros.md) : ArduPilot n'envoie sur une liaison que les messages qu'on lui demande, et personne ne les demande sur celle de mavros. Sans demande, `/mavros/global_position/global` existe mais reste muet, `distance_to` rend `None`, et la mission reste en `GOTO` pour toujours, le drone immobile au-dessus du waypoint.

`mission.py` applique donc la leçon de 3.3 : la node demande elle-même ce dont elle a besoin. Lignes 120 à 124, elle crée un client du service `/mavros/set_message_interval` et un timer d'une seconde. À chaque tour, `request_messages`, lignes 151 à 161, demande le message 33, `GLOBAL_POSITION_INT`, à 5 Hz, sauf si une position fraîche est déjà là, et le message 242, `HOME_POSITION`, tant que le home manque.

Pourquoi redemander tant qu'aucune position fraîche n'arrive, au lieu d'une seule demande au démarrage ? Parce que la demande ne dure pas : elle se perd au redémarrage de l'autopilote. Si vous redémarrez le SITL pendant que la mission tourne, la position s'arrête, le timer le voit et redemande, sans que personne ait à y penser. Tant que la position arrive, il ne fait rien.

Le home suit la même règle. L'autopilote ne l'envoie qu'au moment où il le fixe, à l'armement : une node lancée après le décollage, ou relancée après un `Ctrl-C`, ne le verrait jamais passer. D'où la seconde demande. Tant qu'il n'est pas arrivé, `tick` ne fait que publier l'état (ligne 166) : sans home, il n'y a pas de cible.

<details>
<summary>Pourquoi la position arrive avec un profil QoS particulier</summary>

C'est le piège vu en [formation 3.3, section 2.4](../3-ros2/3.3-mavros.md). La QoS, ce sont des réglages de livraison qui doivent se correspondre entre la node qui publie et celle qui écoute ; sinon le topic est bien listé, mais aucun message n'arrive. Les capteurs de mavros publient en BEST_EFFORT, donc lignes 116 à 119 de `mission.py`, le subscriber de `/mavros/global_position/global` prend `qos_profile_sensor_data` au lieu du `10` habituel. Sans lui, la demande de position aurait beau réussir, rien n'arriverait à la node.

</details>

## 3 - Mission, site, drone

### 3.1 - Trois fichiers, trois questions

Vous avez maintenant croisé trois familles de réglages, et `config/README.md` les range selon une seule question : qu'est-ce qui fait changer cette valeur ?

`config/demo.yaml` change avec la mission. Ce sont les gains, les seuils, les durées, le mapping des interrupteurs de la manette : `rc.go_channel` à `7`, l'index du GO dans le message RC, donc le canal 8 de la manette et la touche `w` du `rc_simulator` ; `rc.go_pwm_min` à `1700`, à partir de quoi l'interrupteur compte comme haut ; `arrival_radius_m`, `act_duration_s`, `state_rate_hz`. Changer de terrain ne touche pas à ce fichier.

`config/sites/sim.yaml` change avec le terrain. Deux valeurs : `target`, la cible en mètres au nord et à l'est du home, et `altitude_agl`, la hauteur de travail au-dessus du home. Le home n'y est pas : c'est l'autopilote qui le donne, là où le drone arme. Le SITL de Mission Planner démarre là où sa carte est centrée, et la démo marche partout sans rien changer.

`config/drones/hexa.json5` change avec le drone. Ce sont les adresses de la radio, pour viser tel appareil depuis le sol. Vous ne l'ouvrez pas ici, c'est le sujet de la formation 6.

La règle derrière ce rangement est celle de `config/README.md` : une valeur qui change entre deux drones, deux terrains ou deux essais n'est jamais écrite dans une node ni dans un launch file. Quand vous hésitez sur l'endroit où mettre un réglage, posez-vous la question dans ce sens, et pas dans le sens « où est-ce que ce sera pratique à lire ».

### 3.2 - Déplacer le waypoint

Ouvrez `config/sites/sim.yaml`. Sans ses commentaires, il tient en cinq lignes, sous le joker `/**` vu en 1.2 :

```yaml
/**:
  ros__parameters:
    site: sim
    target: {north_m: 50.0, east_m: 40.0}
    altitude_agl: 10.0
```

Éloignez la cible vers le nord :

```yaml
    target: {north_m: 150.0, east_m: 40.0}
```

`50.0` devient `150.0` : la cible recule de cent mètres vers le nord.

Ce fichier est lu au démarrage du launch file, pas en continu. Dans le terminal 1, `Ctrl-C`, puis :

```bash
make sim C=demo
```

Le `Ctrl-C` n'arrête que le launch file. Il affiche au passage une trace qui finit par `KeyboardInterrupt` et `process has died` : c'est la node qui s'arrête, rien n'est cassé. Le conteneur `dev` et mavros continuent, donc les terminaux 2 et 3 aussi. Le drone reste armé en GUIDED : il est dans le SITL, qui n'a pas redémarré, donc `make takeoff` n'est pas à refaire.

Redonnez le GO dans le terminal 2 (`s`, puis `w`). Dans Mission Planner, le drone part cette fois vers un autre point, nettement plus loin. Rien n'a été reconstruit : `make build` n'a pas été relancé, parce qu'aucune ligne de code n'a changé.

```bash
git diff config/sites/sim.yaml
```

> [!TIP]
> **Jalon** : ce diff, une ligne, est le deuxième jalon à poster. C'est la preuve la plus courte qu'un waypoint n'est pas du code.

### 3.3 - Un deuxième site

Un repo de compétition a un fichier de site par terrain. Le repo en livre deux : `sim.yaml`, que vous venez de modifier, et `cimetiere.yaml`, le terrain de vol habituel du club. Ouvrez le second : mêmes clés, autres distances.

Le choix du site se fait avec la variable `SITE` du Makefile, exactement comme `C` choisit la mission. Dans le terminal 1, `Ctrl-C`, puis :

```bash
make sim C=demo SITE=cimetiere
```

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Comme la cible se compte depuis le home, ce site se vole aussi dans le SITL : redonnez le GO (`s`, puis `w`) si vous voulez voir le drone partir plus loin vers le nord-est. L'exercice sert surtout à vérifier d'où vient le waypoint. Dans le terminal 3, arrêtez le `make echo` avec `Ctrl-C`, puis :

```bash
make shell
```

```bash
ros2 param get /demo_mission target.north_m
```

```
Double value is: 90.0
```

La valeur de `cimetiere.yaml` est bien arrivée dans la node, sans qu'une ligne de code ait changé et sans reconstruction. C'est tout ce que l'exercice devait montrer.

> [!TIP]
> **Jalon** : cette sortie de `ros2 param get` est le troisième jalon à poster.

### 3.4 - Ce que le code refuse de faire

Essayez un site qui n'existe pas. Dans le terminal 1, `Ctrl-C`, puis :

```bash
make sim C=demo SITE=inexistant
```

Dans le terminal 1, cherchez deux messages. D'abord un avertissement de `ros2 launch`, `Parameter file path is not a file`, qui nomme le fichier de site introuvable : il le saute et démarre la node quand même. La node démarre donc sans cible, et c'est elle qui refuse, `mission.py` lignes 100 et 101 :

```
RuntimeError: Cible de site absente : vérifier config/sites/<site>.yaml
```

La node meurt, et la mission ne part pas. Le même refus arrive si le fichier existe mais que la cible vaut zéro ; dans ce cas, pas d'avertissement. L'avertissement est facile à rater au milieu des autres lignes, mais c'est lui qui nomme le fichier : lisez-le avant de chercher ailleurs.

Les valeurs par défaut de la cible sont `0.0` : une cible sur le home, là où le drone est déjà. Une valeur par défaut sûre est une valeur qui ne vole pas, et une node qui démarre quand même avec un waypoint faux est bien plus dangereuse qu'une node qui refuse de démarrer au sol.

Relancez la démo sur le bon site, la section 4 en a besoin :

```bash
make sim C=demo
```

La seconde chose que le code refuse concerne la fraîcheur de la donnée. `distance_to`, lignes 190 à 193, rend `None` quand la dernière position GPS reçue a plus de deux secondes (`POSITION_MAX_AGE_S`, ligne 42, vérifié par `position_is_fresh` juste au-dessus), et `next_state` ne déclare aucune arrivée tant qu'une distance vaut `None`. Si le lien avec l'autopilote se coupe, la mission reste donc en `GOTO` au lieu de conclure qu'elle est arrivée sur la foi d'une position périmée, et `request_messages` redemande la position chaque seconde (section 2.7). Une vieille position ne prouve pas où le drone se trouve, elle prouve où il se trouvait.

## 4 - Enregistrer

Un vol ne se rejoue pas. Ce qui n'a pas été enregistré pendant l'essai est perdu, et la question qu'on se posera le soir même demandera toujours des données pour y répondre. C'est pour ça qu'on enregistre à chaque vol, même quand tout va bien.

La simulation tourne dans le terminal 1, le `rc_simulator` dans le terminal 2. Ouvrez un quatrième terminal, dans le repo :

```bash
make bag
```

L'enregistrement démarre dans un dossier daté sous `bags/`, par exemple `bags/2026-09-22_14-30`. Faites un tour complet de mission pendant qu'il tourne, du GO (`s`, puis `w`, dans le terminal 2) au retour en `IDLE`, puis `Ctrl-C` dans ce quatrième terminal.

Le Makefile ne prend pas tous les topics. Il passe cette expression régulière à `ros2 bag record` :

```
/aeac/.*|/mavros/(state|rc/in|local_position/pose|global_position/global)
```

Tout ce que l'équipe publie, plus quatre topics mavros : l'état de l'autopilote, les entrées de la manette, la position locale et la position globale. C'est ce qu'il faut pour rejouer une mission et comprendre pourquoi elle a fait ce qu'elle a fait. Le reste de mavros est volumineux et rarement utile, il reste dehors. Si un jour il vous manque un topic, la liste se modifie dans le Makefile, et le prochain enregistrement l'aura.

Le terminal 3 est toujours dans le conteneur depuis la section 3.3. Cherchez-y le nom exact de votre dossier :

```bash
ls /aeac/bags
```

Puis, avec ce nom à la place de la date d'exemple :

```bash
ros2 bag info /aeac/bags/2026-09-22_14-30
```

```
Files:             2026-09-22_14-30_0.db3
Duration:          48.2s
Messages:          867
Topic information: Topic: /aeac/external/demo/state | Type: custom_interfaces/msg/MissionState | Count: 96
                   Topic: /mavros/state | Type: mavros_msgs/msg/State | Count: 48
                   Topic: /mavros/rc/in | Type: mavros_msgs/msg/RCIn | Count: 482
                   Topic: /mavros/global_position/global | Type: sensor_msgs/msg/NavSatFix | Count: 241
                   Topic: /mavros/local_position/pose | Type: geometry_msgs/msg/PoseStamped | Count: 0
```

C'est un extrait : la vraie sortie a quelques lignes de plus, et vos nombres seront différents. Chaque compte se vérifie avec la fréquence de son publisher : le topic d'état à 2 Hz donne à peu près le double de la durée en secondes, la position globale, demandée à 5 Hz, au moins cinq fois la durée (en SITL elle arrive souvent à 10 Hz, donc dix fois), et le `rc_simulator`, à 10 Hz, dix fois. Un compte loin du sien veut dire que ce publisher ne tournait pas pendant tout l'enregistrement.

`/mavros/local_position/pose` est enregistré, mais vide : c'est le message 32, et la démo ne demande que le 33 (section 2.7). Une mission qui se sert de la position locale la demanderait, et le bag l'aurait.

`bags/` est ignoré par git, comme `models/`. Un rosbag ne fait jamais l'objet d'un commit, il se partage autrement.

En fin de séance, `Ctrl-C` dans le terminal 1, puis `make down` : il arrête `dev` et `mavros-sim`, et avec eux ce qui tournait dans les autres terminaux.

## 5 - Quand ça ne marche pas : la démarche

Ce qui suit n'est pas une liste de pannes, la liste est dans la table de la section 6. C'est l'ordre dans lequel on cherche, et cet ordre vaut plus que n'importe quelle liste, parce qu'il tient encore devant une panne que personne n'a jamais vue.

Trois étages. On ne descend d'un étage qu'une fois celui du dessus vérifié.

**Étage 1 : est-ce que le conteneur tourne ?**

```bash
docker ps
```

Vous devez voir `aeac-dev` et `aeac-mavros-sim`. S'il en manque un, relancez `make sim C=demo`. Si mavros ne se connecte pas, sa raison est dans `make logs IMG=mavros-sim`. Si le launch file s'est arrêté, sa trace d'erreur est dans le terminal 1. Tant que cet étage n'est pas réglé, aucune commande `ros2` ne vous apprendra quoi que ce soit : il n'y a personne pour publier, et une liste de topics vide ne veut alors rien dire. C'est le piège de cet étage, et c'est pour ça qu'il est le premier.

**Étage 2 : est-ce que la node tourne ?**

```bash
make shell
```

```bash
ros2 node list
```

```
/demo_mission
/mavros
...
/rc_simulator
```

mavros 2 apparaît sous plusieurs noms, à la place des `...` ; leur nombre exact n'a pas d'importance ici. Une node que vous n'avez pas lancée, ou un `/demo_mission` en double, vient en général d'un poste voisin : voir la table de la section 6.

Une node absente de cette liste alors que son conteneur tourne est une node morte au lancement : remontez les lignes du launch file dans le terminal 1, et cherchez la trace d'exception. S'il manque toutes les nodes de mavros, remontez à l'étage 1 : `aeac-mavros-sim` tourne-t-il encore ?

**Étage 3 : est-ce que la donnée circule ?**

```bash
ros2 topic hz /aeac/external/demo/state
```

Une fréquence autour de 2 veut dire que le publisher est vivant. Pas de sortie du tout alors que le topic est listé veut dire qu'il ne publie rien.

Pour la position de mavros, l'absence de sortie a une cause de plus : personne ne l'a demandée (section 2.7). Et si `ros2 topic hz` voit passer les messages mais que votre node ne reçoit rien, c'est la QoS (section 2.7) : `ros2 topic info -v <topic>` affiche les profils des deux côtés.

Enfin, quand tout circule mais que le comportement est faux, regardez les valeurs que la node a reçues :

```bash
ros2 param get /demo_mission arrival_radius_m
```

C'est en sautant des étages qu'on cherche au mauvais endroit. Sur le drone, un étage s'ajoutera au-dessus des trois autres : là-bas le lancement ne vient pas de vous mais de systemd, et la première question devient « est-ce que le service a démarré ? ». La formation 6 en parle.

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `make logs IMG=mavros-sim` répète que mavros n'arrive pas à se connecter | Le SITL n'est pas lancé, ou `FCU_URL` est faux | Lancer le SITL dans Mission Planner d'abord ; `make print-vars` pour voir `FCU_URL` |
| `mavros-sim` ne se connecte jamais alors que le SITL tourne, et `docker ps` montre `mavros` ou `b3-mavros` | Un mavros des formations 2 ou 3 est resté allumé et occupe le port 5762 | `make down` dans le dossier de cette formation-là, puis `make sim C=demo` |
| mavros ne se connecte jamais alors que le SITL tourne bien | WSL en mode NAT (Windows 10), ou le SITL tourne sur une autre machine | Dans `.env` : `SITL_HOST=<adresse de ip route show default>` en NAT, ou `SITL=<URL mavros>` pour l'autre machine (5.1, section 3.2) ; `make print-vars` pour vérifier `FCU_URL` |
| Le GO ne passe pas, `rc_simulator` n'affiche rien | Le terminal du `rc_simulator` n'a pas le focus clavier | Cliquer dans ce terminal avant d'appuyer sur `w` |
| Le GO ne passe pas, `rc_simulator` affiche bien `canal 8 = 1900` | L'interrupteur doit repasser en bas avant chaque GO | `s` ou `x`, puis `w` |
| L'état ne change pas après le GO, et un WARN parle de GUIDED | Le drone n'est pas armé, ou pas en GUIDED | `make echo T=/mavros/state` (champs `armed` et `mode`) ; au sol, `make takeoff` ; en l'air, repasser en GUIDED dans Mission Planner (section 2.5) |
| La mission reste en `GOTO` alors que le drone est au-dessus du waypoint | La position n'arrive pas à la node, ou `arrival_radius_m` est trop petit | `ros2 topic hz /mavros/global_position/global` : sans sortie, mavros est-il connecté (`make logs IMG=mavros-sim`) ? la demande de position est-elle toujours dans le code (section 2.7) ? Sinon `ros2 param get /demo_mission arrival_radius_m`, à garder au-dessus de `WPNAV_RADIUS / 100` (section 2.6) |
| La mission reste en `IDLE` après le GO, sans aucun WARN | Le home n'est pas arrivé : sans lui, la node n'a pas de cible | `ros2 topic hz /mavros/home_position/home` : sans sortie, mavros est-il connecté (`make logs IMG=mavros-sim`) ? la demande du message 242 est-elle toujours dans `request_messages` (section 2.7) ? |
| La mission s'arrête au lancement sur `No module named 'custom_interfaces'` | Le workspace a été construit alors que ses liens étaient encore des fichiers texte (copie depuis Windows) | `make build C=demo`, qui recrée les liens, puis relancer ; `ls -l workspaces/demo_ws/src` doit montrer trois flèches (section 1.1) |
| Le waypoint n'a pas bougé après modification du YAML | Mauvais fichier modifié (celui de `workspaces/` au lieu de celui de `config/`), `SITE=` oublié, ou simulation pas relancée | `ros2 param get /demo_mission target.north_m` (section 3.3) |
| La node meurt au démarrage sur `Cible de site absente`, avec plus haut un avertissement `Parameter file path is not a file` | Nom de site inexistant dans `SITE=` (sans l'avertissement : cible à zéro dans le fichier du site) | `ls config/sites/`, puis relancer avec le bon `SITE=` (section 3.4) |
| `make shell` répond qu'aucun conteneur ne tourne | `aeac-dev` n'est pas démarré | `make sim C=demo` dans le terminal 1, puis `docker ps` |
| Deux valeurs différentes pour le même paramètre selon le moment | Deux nodes `demo_mission` tournent : la fenêtre du terminal 1 a été fermée au lieu d'un `Ctrl-C`, et le launch file précédent tourne encore dans `dev` | `make down`, puis `make sim C=demo` |
| Le GO part tout seul, ou `ros2 topic info` compte plus d'abonnés que vous n'avez de terminaux ouverts | Une fenêtre fermée au lieu d'un `q` (pour `make rc`) ou d'un `Ctrl-C` laisse sa commande tourner dans `aeac-dev` : un vieux `rc_simulator` resté à 1900 donne le GO à la place du nouveau | `make down`, puis `make sim C=demo` ; à l'avenir, quitter la commande avant de fermer la fenêtre |
| Deux `demo_mission`, le GO part tout seul, ou `ros2 node list` montre des nodes que vous n'avez pas lancées | Un autre poste sur le même réseau utilise le même domaine ROS : ses nodes et les vôtres se voient | Dans `.env` : `SIM_DOMAIN=<numéro>`, un numéro par poste (voir `.env.example`), puis `make down` et `make sim C=demo` |
| Rien ne répond et on ne sait pas par où commencer | C'est le cas normal | Les trois étages de la section 5, dans l'ordre, sans en sauter un |
