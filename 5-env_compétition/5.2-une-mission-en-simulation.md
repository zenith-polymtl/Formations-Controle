# Formation 5.2 : une mission en simulation

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Installer un workspace de mission dans un repo de compétition et le construire
- Lancer une mission en simulation dans trois terminaux et suivre sa machine à états
- Expliquer ce que fait le paramètre `sim` et pourquoi le launch file de vol et celui de simulation sont le même fichier
- Dire où va un réglage : dans la mission, dans le site ou dans le drone
- Enregistrer un rosbag et vérifier ce qu'il contient
- Chercher une panne dans l'ordre : conteneur, node, donnée

Prérequis : la [formation 5.1](5.1-le-depot-vu-de-haut.md) terminée (repo template cloné, `make init`, `gcs_ws` construit), et le SITL de Mission Planner qui démarre, comme en formation 1.

En 5.1 vous avez visité le repo sans rien y faire tourner. Ici une vraie mission tourne. Elle est réduite à son squelette : quatre états, un waypoint, un interrupteur.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 2 h.
> - **Prérequis** : 5.1 faite, le SITL de Mission Planner qui démarre, et le conteneur `dev` de 5.1 arrêté (`make down`). Avant d'ouvrir un terminal, prenez une feuille et écrivez les dossiers du repo avec une phrase chacun. Deux minutes, sans regarder. C'est le jalon de 5.1, section 2.
> - **À la fin** : la machine à états de la démo est passée par `IDLE`, `GOTO`, `ACT` et `RETURN` sans qu'aucun drone ne soit dans les airs, et le waypoint qu'elle vise vient d'un fichier YAML que vous avez modifié.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une capture des quatre transitions, le diff de votre fichier de site, et la sortie du `ros2 param get` de la section 3.3.

Tout se passe sur votre poste WSL, dans votre clone du template, le dossier `mission-template` que vous avez déjà.

Travaillez sur une branche à vous. Une branche est une copie de travail du repo, avec un nom. Tant que vous êtes dessus, vos modifications ne touchent pas `main`, qui reste ce qui vole. C'est cette branche que le lead relira en 5.3.

```bash
git switch -c prenom/demo
```

Remplacez `prenom` par le vôtre. `git switch -c` crée la branche et vous place dessus ; `git branch --show-current` vous dira toujours où vous êtes.

## 1 - Poser la démo

### 1.1 - Copier et construire

Le workspace de la démo est fourni dans le dossier de la formation, sous `5-env_compétition/demo_ws/`. Il ne fait pas partie du repo de mission : vous l'y installez. Deux dossiers à déplacer, et il y a deux façons de le faire.

**Option A, dans VS Code.** Ouvrez votre clone de `mission-template` dans VS Code, puis ouvrez le dossier Formations-Controle dans une seconde fenêtre. Dans l'explorateur de la seconde fenêtre, attrapez le dossier `5-env_compétition/demo_ws` et déposez-le sur le dossier `workspaces/` de la première. VS Code copie le dossier entier.

**Option B, au terminal.** Depuis la racine du clone, en remplaçant `<dossier de la formation>` par le chemin où vous avez Formations-Controle :

```bash
cp -r <dossier de la formation>/5-env_compétition/demo_ws workspaces/
```

Dans les deux cas, votre clone de Formations-Controle doit être dans le système de fichiers de WSL, pas sous `/mnt/c` : les trois liens de `demo_ws/src` sont des liens symboliques, et une copie qui part de Windows les recopie en fichiers texte. Le `ls -l` plus bas le dit tout de suite, les trois lignes doivent porter une flèche.

Même chose pour les réglages de la mission, qui vont ailleurs. Glissez `workspaces/demo_ws/src/demo_bringup/config/demo.yaml` sur le dossier `config/`, ou bien :

```bash
cp workspaces/demo_ws/src/demo_bringup/config/demo.yaml config/
```

Deux copies, deux endroits. Le code de la mission va avec le code des autres missions, dans `workspaces/`. Ses réglages vont avec les réglages des autres missions, dans `config/`. On sépare les deux parce qu'on change un réglage souvent et le code rarement : un waypoint, un seuil ou une durée se modifient entre deux essais sans toucher à une ligne de Python. Le launch file de la démo lit `/aeac/config/demo.yaml`, et rien d'autre.

La démo se sert de trois packages partagés : `tools` pour les noms de topics, `custom_interfaces` pour le message d'état, et `sim_mocks` pour les nodes de test de la section 2. Vous n'avez rien à faire pour les avoir : les liens sont déjà dans le workspace que vous venez de copier, posés par un lead.

```bash
ls -l workspaces/demo_ws/src
```

```
custom_interfaces -> ../../../packages/custom_interfaces
demo_bringup
demo_mission
sim_mocks -> ../../../packages/sim_mocks
tools -> ../../../packages/tools
```

Trois liens et deux vrais dossiers. C'est la forme d'un workspace de mission, la même que `gcs_ws` en 5.1 : les packages locaux de la mission, plus des liens vers les packages partagés de `packages/`. Poser ces liens est un geste de lead, vous les recevez faits.

```bash

```

```

Starting >>> tools
Starting >>> demo_bringup
Starting >>> sim_mocks
Finished <<< demo_bringup
Finished <<< sim_mocks
```

Cinq packages : les trois partagés, `demo_bringup` qui porte le launch file, et `demo_mission` qui porte le node. Colcon les construit dans l'ordre des dépendances, `custom_interfaces` d'abord parce que tout le reste en dépend.

### 1.2 - Lire avant de lancer

Commencez par le launch file, `workspaces/demo_ws/src/demo_bringup/launch/mission.launch.py`. Il tient en une page et il se lit de haut en bas :

```python
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration, PathJoinSubstitution
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue

CONFIG_DIR = '/aeac/config'   # le repo est toujours monté à /aeac dans les conteneurs


def generate_launch_description():
    ld = LaunchDescription()

    sim = DeclareLaunchArgument('sim', default_value='false',
                                description='Vrai en simulation : aucun appel matériel')
    site = DeclareLaunchArgument('site', default_value='sim',
                                 description='Terrain, donc config/sites/<site>.yaml')
    mission = Node(
        package='demo_mission',
        executable='mission',
        name='demo_mission',
        output='screen',
        parameters=[
            f'{CONFIG_DIR}/demo.yaml',
            PathJoinSubstitution([f'{CONFIG_DIR}/sites',
                                  [LaunchConfiguration('site'), '.yaml']]),
            {'sim': ParameterValue(LaunchConfiguration('sim'), value_type=bool)},
        ],
    )

    ld.add_action(sim)
    ld.add_action(site)
    ld.add_action(mission)
    return ld
```

Deux arguments, un node, trois `add_action`. Les deux fichiers YAML sont donnés au node tels quels : le launch file ne les ouvre pas, ne les lit pas et ne convertit rien. C'est `ros2 launch` qui les charge, dans l'ordre où ils sont écrits, `config/demo.yaml` puis le fichier du site.

Ouvrez ensuite `workspaces/demo_ws/src/demo_mission/demo_mission/mission.py`. Un peu plus de deux cents lignes, dont un bon tiers de commentaires. Ne cherchez pas à tout comprendre : cherchez trois choses, et seulement elles. Les réponses sont juste en dessous, mais cherchez d'abord.

**Où sont les noms de topics ?** Le node publie son état à la ligne 104, sur `topics.DEMO_STATE`. La constante est dans `packages/tools/tools/topics.py` et vaut `/aeac/external/demo/state`. Le nom complet n'est écrit nulle part dans `mission.py`. Les quatre topics mavros, eux, sont en haut du fichier, lignes 27 à 30 : ils appartiennent à un package tiers, et `topics.py` ne décrit que les topics `/aeac` écrits par l'équipe. Le deuxième segment, `external`, dit que l'état de la mission a le droit de traverser la radio vers le sol.

**Où sont les états ?** Dans `packages/custom_interfaces/msg/MissionState.msg`, importé ligne 16 et utilisé partout sous la forme `MissionState.IDLE`, `MissionState.GOTO`, `MissionState.ACT`, `MissionState.RETURN`. Le fichier `.msg` définit ces quatre constantes et leurs valeurs, 0 à 3. Aucun node ne les redéfinit : le message est la seule définition des états, et le sol lit les mêmes chiffres que le drone.

**Où est le waypoint ?** Nulle part dans le code. Cherchez une latitude dans `mission.py` : vous trouverez des paramètres `target.lat` et `target.lon` déclarés dans le bloc `PARAMETERS`, lignes 39 à 44, avec `0.0` en valeur par défaut, et rien d'autre. La vraie valeur arrive de `config/sites/<site>.yaml`, passé au node par le launch file que vous venez de lire. Le terrain est une donnée, pas du code.

La machine à états elle-même tient dans la fonction `next_state`, lignes 55 à 71. Elle ne connaît ni ROS, ni mavros, ni le GPS : elle reçoit l'état courant et quelques booléens, et rend le nouvel état ou `None`. Elle se relit en une minute et se teste sans rien lancer.

> [!TIP]
> **Jalon** : vous avez réussi cette section si vous pouvez dire, fichier et ligne à l'appui, d'où viennent le nom du topic d'état, la valeur `2` de l'état `ACT`, et la latitude visée.

## 2 - Trois terminaux

C'est le cœur de la formation. Trois terminaux WSL, tous ouverts dans le repo, plus Mission Planner sous Windows.

```
  Windows                          WSL
+-------------+       TCP 5762   +--------------------------------------------+
|  Mission    |<-----------------|    +-----------------+  +----------------+ |
|  Planner    |                  |    | aeac-mavros-sim |  | aeac-dev       | |
|  (SITL)     |----------------->|    | mavros <-> SITL |  | le launch file | |
+-------------+                  |    | en arrière-plan |  | et les mocks   | |
                                 |    +-----------------+  +----------------+ |
                                 |                                            |
                                 |  Terminal 1 : make sim C=demo (le launch)  |
                                 |  Terminal 2 : make takeoff, puis make rc   |
                                 |  Terminal 3 : make echo T=...              |
                                 |    les trois entrent dans aeac-dev         |
                                 +--------------------------------------------+
```

Avant tout : lancez le SITL dans Mission Planner comme en formation 1, et attendez qu'il soit prêt. Si le SITL ne tourne pas, mavros n'a personne à qui parler et le reste de la section ne donnera rien.

### 2.1 - Terminal 1 : la simulation

```bash
make sim C=demo
```

Cette commande démarre deux conteneurs. `aeac-mavros-sim`, décrit dans `compose/sim.yml`, lance mavros en arrière-plan et le branche sur le SITL, en TCP sur le port 5762 de `SITL_HOST`, l'adresse que vous avez vue avec `make print-vars` en 5.1. `aeac-dev` est le conteneur de 5.1 : le Makefile y lance le launch file de la mission, au premier plan dans ce terminal, avec `sim:=true site:=$(SITE)`, donc le site `sim` tant que vous ne demandez rien d'autre. Changer de mission avec `C=` recrée `dev` dans le bon workspace, et ferme les autres terminaux ouverts dedans. `SITE` est la quatrième variable du Makefile, à côté de `C`, `IMG` et `DRONE` ; on s'en sert en section 3.3.

Au bout de quelques secondes, vous voyez la ligne du node de mission :

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Ce terminal n'affiche que le launch file. Les lignes de mavros sont ailleurs, avec `make logs IMG=mavros-sim` dans un autre terminal : c'est là que mavros dit s'il n'arrive pas à joindre le SITL. Laissez le terminal 1 tourner, c'est lui qui affiche la vie de la mission.

### 2.2 - Terminal 2 : le pilote et la manette

Le drone simulé est au sol, désarmé, en mode STABILIZE. Le code de mission ne le fera pas décoller : la règle du repo est que le code de mission n'arme jamais et ne change jamais de mode. En vol c'est le pilote qui le fait. En simulation, un node de test tient ce rôle, et il a sa cible make :

```bash
make takeoff
```

```
[WARN] [takeoff_test]: node de test : arme et décolle le drone
[INFO] [takeoff_test]: mode GUIDED
[INFO] [takeoff_test]: armement (renvoyé tant que refusé)
[INFO] [takeoff_test]: décollage à 10.0 m
[INFO] [takeoff_test]: terminé
```

Le drone monte à dix mètres dans Mission Planner, puis le node s'arrête tout seul. Il n'y a aucun paramètre à lui passer : le WARN du démarrage et le suffixe `_test` dans son nom sont ce qui le signale. C'est écrit dans `packages/sim_mocks/README.md` : un node qui arme ou change de mode porte ce suffixe et annonce ce qu'il va faire, et aucun launch file de mission ne l'inclut.

`make takeoff` entre dans le conteneur qui tourne, sans que vous ayez à dire lequel ni à sourcer quoi que ce soit. C'est la même mécanique que `make shell`, vue en 5.1. `make takeoff` et `make rc` refusent en plus de tourner ailleurs que dans le conteneur `dev` : cette garde du Makefile remplace l'ancien `-p sim:=true` qu'il fallait penser à passer.

Le drone vole, il attend un ordre. Dans le même terminal :

```bash
make rc
```

```
[INFO] [rc_simulator]: Manette simulée : w/s/x e/d/c r/f/v, q pour quitter
```

Ce node remplace la manette : il lit votre clavier et publie des valeurs PWM sur `/mavros/rc/in`, dix fois par seconde, comme un vrai récepteur. Les touches `w`, `s` et `x` mettent le canal 8 en haut (1900), au centre (1500) et en bas (1100). Il lit le clavier du terminal où il a été lancé : pour que vos touches comptent, c'est ce terminal qui doit avoir le focus.

Ne tapez encore rien : ouvrez d'abord le troisième terminal.

### 2.3 - Terminal 3 : l'état de la mission

```bash
make echo T=/aeac/external/demo/state
```

```
header:
  stamp:
    sec: 1758501234
    nanosec: 512000000
  frame_id: ''
state: 0
time_in_state: 3.5
---
```

`state` est un entier, et c'est là que `MissionState.msg` devient utile : `0` est `IDLE`, l'attente ; `1` est `GOTO`, en route vers le waypoint ; `2` est `ACT`, l'action sur place ; `3` est `RETURN`, le retour au point de départ. `time_in_state` est le nombre de secondes passées dans l'état courant, remis à zéro à chaque transition. Le tout défile deux fois par seconde, parce que `state_rate_hz` vaut `2.0` dans `config/demo.yaml`.

`make echo T=<topic>` est un raccourci pour `ros2 topic echo <topic>` dans le conteneur qui tourne. Si vous préférez rester dans un terminal du conteneur pour enchaîner plusieurs commandes, `make shell` vous y ouvre un shell où `ros2` marche tout de suite.

### 2.5 - Le pilote reste au-dessus du code

Essayez ceci pendant que la mission est en `GOTO` : dans Mission Planner, repassez le drone en mode LOITER, ou désarmez-le.

```
[mission-1] [INFO] [demo_mission]: Transition GOTO -> IDLE
[mission-1] [WARN] [demo_mission]: Le pilote a repris la main, mission interrompue
```

Hors de `IDLE`, perdre l'armement ou le mode GUIDED ramène la mission en `IDLE` immédiatement (`next_state`, lignes 58 à 60). La mission ne discute pas et ne réessaie pas. Un node qui continuerait à publier des setpoints pendant que le pilote reprend la main serait un node dangereux. Repassez en GUIDED et redonnez le GO pour repartir.

Si vous donnez le GO alors que le drone n'est ni armé ni en GUIDED, la mission reste en `IDLE` et prévient une fois :

```
[mission-1] [WARN] [demo_mission]: GO reçu mais le drone n'est pas armé en GUIDED
```

### 2.6 - Ce que `sim:=true` fait, et ce qu'il ne fait pas

Maintenant que le tour est bouclé, la question qui compte : qu'est-ce qui change entre ce que vous venez de lancer et ce qui volera au-dessus d'un terrain ?

Presque rien. `make sim` lance, dans le conteneur `dev`, `ros2 launch demo_bringup mission.launch.py sim:=true site:=$(SITE)`. Le launch de vol lance le même fichier, avec `sim:=false`. Ce ne sont pas deux fichiers, c'est un fichier et un argument, déclaré dans le `DeclareLaunchArgument` que vous avez lu en 1.2.

Cet argument ne fait qu'une chose : il devient le paramètre `sim` du node. Le node le lit une fois au démarrage, ligne 79, et s'en sert à un seul endroit, ligne 174 :

```python
if not self.sim:
    self._trigger_payload()
```

Voyez `self.sim` comme un outil : il dit au node qu'aucun matériel n'est branché. La démo n'a qu'un appel matériel, donc un seul test. Une vraie mission en aura plusieurs, et le piège est de semer des `if self.sim` dans tout le fichier : vous ne savez alors plus ce que la simulation a vraiment prouvé. La bonne habitude est de rassembler tout ce qui dépend de `sim` au même endroit, une méthode `_setup_hardware()` par exemple, appelée une fois au démarrage. Le commentaire des lignes 170 à 173 le dit dans le code.

`_trigger_payload`, lignes 180 à 183, est l'endroit où une vraie mission branche son matériel : ouvrir un servo, prendre une photo, larguer une charge. Dans la démo elle se contente d'un WARN, parce qu'il n'y a rien à brancher. Quand vous écrirez votre mission, c'est la méthode à remplir, et c'est la seule du fichier qui doit parler au matériel.

La machine à états et le message d'état sont un exemple, pas un gabarit imposé. Quatre états et un `time_in_state`, c'est ce qui convenait à la démo. Une autre mission publiera autre chose, dans un message à elle. Ce qui ne change pas, c'est que l'état vit dans `custom_interfaces` et pas dans le node.

Remarquez enfin ce que le launch file ne lance pas. `takeoff_test` et `rc_simulator`, vous les avez lancés à la main, et aucun launch file de mission n'inclut un mock. C'est ce qui garantit qu'un mock ne peut pas se retrouver dans les airs.

Lisez `packages/sim_mocks/README.md` en entier, c'est une page : les trois mocks du repo, ce que chacun remplace, et la règle pour en écrire un. Le troisième, `target_mock`, remplace une détection du conteneur vision ; il vous servira quand la formation vision arrivera.

<details>
<summary>Deux détails du code qui surprennent souvent</summary>

**Le setpoint republié.** Lignes 143 à 146, le node republie la position visée à chaque tour de timer, deux fois par seconde. Ce n'est pas une obligation : un setpoint de position globale peut n'être envoyé qu'une fois, s'il est bien reçu. Ce sont les setpoints de vitesse et d'accélération qui exigent un flux continu, faute de quoi l'autopilote les abandonne. La démo republie quand même, parce que c'est une ligne de code et qu'un message perdu passe alors inaperçu.

**Le rayon d'arrivée.** `arrival_radius_m` vaut `3.0` dans `config/demo.yaml`, et il doit rester plus grand que le rayon d'acceptation de l'autopilote, le paramètre ArduPilot `WPNAV_RADIUS`, qui est en centimètres et vaut 200 par défaut. Autrement, la mission attend une précision que l'autopilote ne cherche pas : le drone se considère arrivé, s'arrête, et la mission reste en `GOTO` pour toujours.

</details>

<details>
<summary>Pourquoi la position arrive avec un profil QoS particulier</summary>

La QoS, ce sont des réglages de livraison qui doivent se correspondre entre le node qui publie et celui qui écoute. S'ils ne se correspondent pas, rien ne se plaint : le topic existe, il est listé, et aucun message n'arrive. `ros2 topic info -v <topic>` affiche les profils des deux côtés et montre la différence.

C'est le piège vu en [formation 3.3, section 2.4](../3-ros2/3.3-mavros.md). Les capteurs de mavros publient en BEST_EFFORT, donc lignes 100 à 103 de `mission.py`, l'abonnement à `/mavros/global_position/global` prend `qos_profile_sensor_data` au lieu du `10` habituel.

</details>

## 3 - Mission, site, drone

### 3.1 - Trois fichiers, trois questions

Vous avez maintenant croisé trois familles de réglages, et `config/README.md` les range selon une seule question : qu'est-ce qui fait changer cette valeur ?

`config/demo.yaml` change avec la mission. Ce sont les gains, les seuils, les durées, le mapping des interrupteurs de la manette : `rc.go_channel` à `7`, l'index du GO dans le message RC, donc le canal 8 de la manette et la touche `w` du `rc_simulator` ; `rc.go_pwm_min` à `1700`, à partir de quoi l'interrupteur compte comme haut ; `arrival_radius_m`, `act_duration_s`, `state_rate_hz`. Changer de terrain ne touche pas à ce fichier.

`config/sites/sim.yaml` change avec le terrain. Rien que des coordonnées : `home`, `target`, `altitude_agl`. Le site `sim` est la position de départ du SITL d'ArduPilot, près de Canberra en Australie.

`config/drones/hexa.json5` change avec le drone. Ce sont les adresses de la radio, pour viser tel appareil depuis le sol. Vous ne l'ouvrez pas ici, c'est le sujet de la formation 6.

La règle derrière ce rangement est celle de `config/README.md` : une valeur qui change entre deux drones, deux terrains ou deux essais n'est jamais écrite dans un node ni dans un launch file. Quand vous hésitez sur l'endroit où mettre un réglage, posez-vous la question dans ce sens, et pas dans le sens « où est-ce que ce sera pratique à lire ».

### 3.2 - Déplacer le waypoint

Ouvrez `config/sites/sim.yaml`. Le fichier est écrit en paramètres ROS 2, sous le joker `/**` qui veut dire « tous les nodes ». C'est ce qui permet au launch file de le donner au node sans rien lire ni convertir.

```yaml
/**:
  ros__parameters:
    site: sim
    home: {lat: -35.363262, lon: 149.165237, alt: 584.0}
    target: {lat: -35.362800, lon: 149.165700}
    altitude_agl: 10.0
```

Changez la latitude de la cible :

```yaml
    target: {lat: -35.361900, lon: 149.165700}
```

`-35.362800` devient `-35.361900`, neuf dix-millièmes de degré, soit une centaine de mètres vers le nord. Un dix-millième de degré de latitude fait à peu près onze mètres, partout sur Terre ; pour la longitude, ça dépend de la latitude.

Ce fichier est lu au démarrage du launch file, pas en continu. Dans le terminal 1, `Ctrl-C`, puis :

```bash
make sim C=demo
```

Le `Ctrl-C` n'arrête que le launch file. Le conteneur `dev` et mavros continuent, donc les terminaux 2 et 3 aussi. Le drone reste armé en GUIDED : il est dans le SITL, qui n'a pas redémarré, donc `make takeoff` n'est pas à refaire.

Redonnez le GO dans le terminal 2, après avoir remis le canal en bas avec `s`. Dans Mission Planner, le drone part cette fois vers un autre point, nettement plus loin. Rien n'a été reconstruit : `make build` n'a pas été relancé, parce qu'aucune ligne de code n'a changé.

```bash
git diff config/sites/sim.yaml
```

> [!TIP]
> **Jalon** : ce diff, une ligne, est le deuxième jalon à poster. C'est la preuve la plus courte qu'un waypoint n'est pas du code.

### 3.3 - Un deuxième site

Un repo de compétition a un fichier de site par terrain. Le repo en livre deux : `sim.yaml`, que vous venez de modifier, et `cimetiere.yaml`, le terrain de vol habituel du club. Ouvrez le second : mêmes clés, autres coordonnées.

Le choix du site se fait avec la variable `SITE` du Makefile, exactement comme `C` choisit la mission. Dans le terminal 1, `Ctrl-C`, puis :

```bash
make sim C=demo SITE=cimetiere
```

```
[mission-1] [INFO] [demo_mission]: Mission démo prête en IDLE : GO attendu sur le canal 8 de la manette.
```

Ne donnez pas le GO. Le SITL démarre en Australie et il y est toujours : avec le site `cimetiere`, il recevrait un setpoint à Montréal et passerait le reste de la journée à traverser le Pacifique. L'exercice ne sert pas à voir voler, il sert à vérifier d'où vient le waypoint. Dans le terminal 3, arrêtez le `make echo` avec `Ctrl-C`, puis :

```bash
make shell
```

```bash
ros2 param get /demo_mission target.lat
```

```
Double value is: 45.5056
```

La valeur de `cimetiere.yaml` est bien arrivée dans le node, sans qu'une ligne de code ait changé et sans reconstruction. C'est tout ce que l'exercice devait montrer.

> [!TIP]
> **Jalon** : cette sortie de `ros2 param get` est le troisième jalon à poster.

`Ctrl-C` dans le terminal 1 quand vous l'avez vue, puis `make sim C=demo` pour revenir au site `sim`.

### 3.4 - Ce que le code refuse de faire

Essayez un site qui n'existe pas :

```bash
make sim C=demo SITE=inexistant
```

Le launch file s'arrête tout de suite dans le terminal 1, et son message nomme le fichier de paramètres qu'il ne trouve pas. Le launch file ne vérifie rien lui-même : c'est `ros2 launch` qui refuse de charger un fichier absent. Le message est sec, mais le nom de fichier est dedans, et c'est ce qu'il faut savoir pour ne pas chercher ailleurs.

Si le fichier existe mais que les coordonnées valent zéro, c'est le node qui refuse, `mission.py` lignes 86 et 87 :

```
RuntimeError: Coordonnées de site absentes : vérifier config/sites/<site>.yaml
```

Les valeurs par défaut des coordonnées sont `0.0`, au large du golfe de Guinée. Une valeur par défaut sûre est une valeur qui ne vole pas, et un node qui démarre quand même avec un waypoint faux est bien plus dangereux qu'un node qui refuse de démarrer au sol.

La seconde chose que le code refuse concerne la fraîcheur de la donnée. `distance_to`, lignes 148 à 153, rend `None` quand la dernière position GPS reçue a plus de deux secondes (`POSITION_MAX_AGE_S`, ligne 33), et `next_state` ne déclare aucune arrivée tant qu'une distance vaut `None`. Si le lien avec l'autopilote se coupe, la mission reste donc en `GOTO` au lieu de conclure qu'elle est arrivée sur la foi d'une position périmée. Une vieille position ne prouve pas où le drone se trouve, elle prouve où il se trouvait.

## 4 - Enregistrer

Un vol ne se rejoue pas. Ce qui n'a pas été enregistré pendant l'essai est perdu, et la question qu'on se posera le soir même demandera toujours des données pour y répondre. C'est pour ça qu'on enregistre à chaque vol, même quand tout va bien.

La simulation tourne, les terminaux 2 et 3 aussi. Ouvrez un quatrième terminal :

```bash
make bag
```

L'enregistrement démarre dans un dossier daté sous `bags/`, par exemple `bags/2026-09-22_14-30`. Faites un tour complet de mission pendant qu'il tourne, du GO au retour en `IDLE`, puis `Ctrl-C` dans ce quatrième terminal.

Le Makefile ne prend pas tous les topics. Il passe cette expression régulière à `ros2 bag record` :

```
/aeac/.*|/mavros/(state|rc/in|local_position/pose|global_position/global)
```

Tout ce que l'équipe publie, plus quatre topics mavros : l'état de l'autopilote, les entrées de la manette, la position locale et la position globale. C'est ce qu'il faut pour rejouer une mission et comprendre pourquoi elle a fait ce qu'elle a fait. Le reste de mavros est volumineux et rarement utile, il reste dehors. Si un jour il vous manque un topic, la liste se modifie dans le Makefile, et le prochain enregistrement l'aura.

```bash
make shell
```

```bash
ros2 bag info /aeac/bags/2026-09-22_14-30
```

```
Files:             2026-09-22_14-30_0.db3
Duration:          48.2s
Messages:          1043
Topic information: Topic: /aeac/external/demo/state | Type: custom_interfaces/msg/MissionState | Count: 96
                   Topic: /mavros/state | Type: mavros_msgs/msg/State | Count: 48
                   Topic: /mavros/rc/in | Type: mavros_msgs/msg/RCIn | Count: 482
```

Remplacez la date par la vôtre. Le nombre de messages sur le topic d'état doit être à peu près le double de la durée en secondes, puisque le node publie à 2 Hz : si ce n'est pas le cas, l'enregistrement a commencé ou fini au mauvais moment.

`bags/` est ignoré par git, comme `models/`. Un rosbag ne se commet jamais, il se partage autrement.

En fin de séance, `Ctrl-C` dans le terminal 1, puis `make down` : il arrête `dev` et `mavros-sim`.

## 5 - Quand ça ne marche pas : la démarche

Ce qui suit n'est pas une liste de pannes, la liste est dans la table de la section 6. C'est l'ordre dans lequel on cherche, et cet ordre vaut plus que n'importe quelle liste, parce qu'il tient encore devant une panne que personne n'a jamais vue.

Trois étages. On ne descend d'un étage qu'une fois celui du dessus vérifié.

**Étage 1 : est-ce que le conteneur tourne ?**

```bash
docker ps
```

Vous devez voir `aeac-dev` et `aeac-mavros-sim`. S'il en manque un, relancez `make sim C=demo`. Si mavros ne se connecte pas, sa raison est dans `make logs IMG=mavros-sim`. Si le launch file s'est arrêté, sa trace d'erreur est dans le terminal 1. Tant que cet étage n'est pas réglé, aucune commande `ros2` ne vous apprendra quoi que ce soit : il n'y a personne pour publier, et une liste de topics vide ne veut alors rien dire. C'est le piège de cet étage, et c'est pour ça qu'il est le premier.

**Étage 2 : est-ce que le node tourne ?**

```bash
make shell
```

```bash
ros2 node list
```

```
/demo_mission
/mavros
/rc_simulator
```

Un node absent de cette liste alors que son conteneur tourne est un node mort au lancement : remontez aux lignes du launch file dans le terminal 1, et cherchez la trace d'exception. Une liste de topics où il manque tous les `/mavros/*` ne dit pas que mavros est mort, elle dit d'abord de remonter à l'étage 1.

**Étage 3 : est-ce que la donnée circule ?**

```bash
ros2 topic hz /aeac/external/demo/state
```

Une fréquence conforme, autour de 2, veut dire que l'émetteur est vivant. Pas de sortie du tout alors que le topic est listé veut dire l'inverse : un émetteur mort, ou deux profils QoS qui ne se correspondent pas.

```bash
ros2 topic info -v /aeac/external/demo/state
```

Deux profils QoS différents donnent exactement le même symptôme qu'une absence totale de message. C'est ce qu'il faut savoir pour ne pas y perdre une soirée.

Enfin, quand tout circule mais que le comportement est faux, regardez les valeurs :

```bash
ros2 param get /demo_mission arrival_radius_m
```

Un topic qui coule avec les mauvaises valeurs dedans est un problème d'étage 3, et il ressemble de loin à un problème d'étage 1. C'est en sautant des étages qu'on cherche au mauvais endroit.

Le jour J, sur le drone, ces trois étages servent tels quels, avec un étage de plus au-dessus : là-bas le lancement ne vient pas de vous mais de systemd, et la première question devient « est-ce que le service a démarré ? ». La formation 6 ajoute cet étage.

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `make logs IMG=mavros-sim` répète que mavros n'arrive pas à se connecter | Le SITL n'est pas lancé, ou `SITL_HOST` est faux | Lancer le SITL dans Mission Planner d'abord ; `make print-vars` pour voir l'adresse résolue |
| `make print-vars` affiche `SITL_HOST=` vide | `ip route` ne renvoie pas de route par défaut | WSL en mode mirrored ou Linux natif : `SITL_HOST=127.0.0.1` ; Mac : `host.docker.internal` ; dans `.env` ou sur la ligne de commande (5.1) |
| Le GO ne passe pas, `rc_simulator` n'affiche rien | Le terminal du `rc_simulator` n'a pas le focus clavier | Cliquer dans ce terminal avant d'appuyer sur `w` |
| Le GO ne passe pas, `rc_simulator` affiche bien `canal 8 = 1900` | L'interrupteur doit repasser en bas avant chaque GO | `s` ou `x`, puis `w` |
| L'état ne change pas après le GO, et un WARN parle de GUIDED | Le drone n'est pas armé, ou pas en GUIDED | `make takeoff` d'abord, puis `make echo T=/mavros/state` |
| `make build C=demo` ne construit que deux packages | Les liens de `demo_ws/src` ont été copiés depuis Windows : ce sont des fichiers texte, pas des liens | Refaire la copie depuis WSL, puis `ls -l workspaces/demo_ws/src` (section 1.1) |
| Le waypoint n'a pas bougé après modification du YAML | Mauvais fichier modifié (celui de `workspaces/` au lieu de celui de `config/`), `SITE=` oublié, ou simulation pas relancée | `ros2 param get /demo_mission target.lat` (section 3.3) |
| Le launch file s'arrête tout de suite et nomme un fichier de paramètres | Nom de site inexistant dans `SITE=` | Vérifier `ls config/sites/` (section 3.4) |
| `make shell` répond qu'aucun conteneur ne tourne | `aeac-dev` n'est pas démarré | `make sim C=demo` dans le terminal 1, puis `docker ps` |
| Deux valeurs différentes pour le même paramètre selon le moment | Deux nodes `demo_mission` tournent : la fenêtre du terminal 1 a été fermée au lieu d'un `Ctrl-C`, et l'ancien launch file tourne encore dans `dev` | `make down`, puis `make sim C=demo` |
| Rien ne répond et on ne sait pas par où commencer | C'est le cas normal | Les trois étages de la section 5, dans l'ordre, sans en sauter un |
