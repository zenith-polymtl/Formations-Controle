# Formation 5.1 : le repo vu de haut

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Nommer les trois machines (poste WSL, Jetson, portable GCS), leurs cinq régimes (développement, simulation, test sur véhicule, déploiement, vol) et ce qui tourne sur chacune
- Nommer les sept dossiers du repo de mission et dire en une phrase ce que chacun contient
- Lire `make help` en trois sections et savoir laquelle vous concerne
- Cloner, initialiser et construire un repo de mission, puis lancer un launch file dans le conteneur de développement
- Retrouver les règles du repo, et dire les deux qui comptent avant d'écrire du code

Prérequis : la formation 0 (git, section 3), la formation 1 (le SITL de Mission Planner), et les formations 2 et 3 terminées (WSL, Docker, Compose et Make en place ; une node ROS 2 écrite, lancée par un launch file et une cible make). La formation 4 n'est pas nécessaire : le simulateur utilisé ici est le SITL de Mission Planner.

Les formations 2 et 3 vous ont appris les outils : Docker, Compose, Make, ROS 2. Vous utilisez les mêmes outils ici, mais à plus grande échelle. Le repo de compétition regroupe plusieurs missions, plusieurs conteneurs, plusieurs ordinateurs et plusieurs opérateurs. Chaque dossier du repo existe pour répondre à l'un de ces besoins. Dans la formation 2, le dossier `docker/` contenait une seule recette d'image ; ici, il en contient une par rôle. Les deux fichiers compose de la formation 2 sont devenus un fichier par chose à lancer. Le Makefile de la formation 2 avait huit cibles ; celui-ci en a une trentaine, rangées en trois sections. Ce sont les mêmes outils, organisés pour une équipe.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 1 h 45. La visite du repo prend une dizaine de minutes. La construction Docker prend une quinzaine de minutes, et vous lisez la suite pendant qu'elle tourne.
> - **Prérequis** : formations 2 et 3 faites. Docker démarre sous WSL, `make` est installé, et vous avez un compte GitHub membre de l'organisation `zenith-polymtl`. Si ce n'est pas le cas, demandez à un lead de vous ajouter à l'organisation et à l'équipe contrôle avant la séance. Sinon, votre push de la formation 5.3 sera refusé.
> - **À la fin** : vous avez ouvert le conteneur de développement, construit le workspace `gcs_ws`, et vous voyez le heartbeat du sol défiler dans un `ros2 topic echo`.
> - **Aide** : posez votre question sur Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une photo du schéma dessiné à la main (section 1.5) et une capture de `make status` (section 4.2).

Le repo que vous allez cloner est le repo template, `mission-template`. C'est le squelette à partir duquel on crée les repos de compétition. Il a les mêmes submodules, les mêmes conteneurs et les mêmes packages partagés, mais pas de code de mission. Votre clone vous appartient : vous pouvez le casser sans risque. La formation ne touche jamais au repo de compétition `aeac-2027`.

**D'aeac-2026 au template.** Les formations 2 et 3 vous ont parlé du repo `aeac-2026`. Le template succède à ce repo : il reprend les mêmes idées, organisées autrement. Si vous croisez l'ancien repo, ou quelqu'un qui en parle, le tableau suivant donne les correspondances.

| Dans aeac-2026 | Dans le template (et aeac-2027) |
|---|---|
| un package `bringup` partagé, avec un launch file par mission (`water_mission.launch.py`, ...) | un workspace par mission, avec son package `<mission>_bringup` et son `launch/mission.launch.py` |
| `make mavros-sim` | `make sim C=<mission>` |
| `make mavros-gazebo` | `make sim C=<mission> SITL=gazebo` |
| `nav_stack`, dont la node `init` qui demande les flux de messages à l'autopilote | le même `nav_stack`, submodule partagé dans `packages/nav_stack` |

> [!WARNING]
> **Mêmes noms, autre sens.** Quatre cibles ont le même nom qu'une cible des formations 2 et 3, mais elles ne font plus la même chose. Si une de ces commandes vous surprend, relisez ce tableau.

| Cible | Dans les formations 2 et 3 | Ici |
|---|---|---|
| `make build` | construit l'image Docker | construit le workspace de `C=` avec colcon, dans un conteneur (la première fois, l'image est aussi construite) |
| `make mavros` | démarre mavros vers le SITL | démarre mavros vers le Pixhawk, sur la Jetson ; la simulation passe par `make sim` |
| `make shell` | démarre le conteneur au besoin, puis ouvre un shell | entre dans un conteneur qui tourne déjà, et refuse si aucun ne tourne |
| `make mavros-logs` | les logs du conteneur mavros | les logs du service systemd `mavros` sur la Jetson (`journalctl`) ; en simulation, c'est `make logs IMG=mavros-sim` |

## 1 - Cloner, puis lire ARCHITECTURE.md

### 1.1 - On clone maintenant, on comprend après

La page à lire, `ARCHITECTURE.md`, se trouve dans le repo. Vous devez donc cloner le repo avant de la lire. Le clone ne demande qu'une commande. Clonez dans votre home WSL, pas sous `/mnt/c`. Sur le disque Windows, tout est lent et `colcon build` échoue à cause des permissions (formation 2, section 2.7).

```bash
cd ~
```

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/mission-template
```

```bash
cd mission-template
```

Copiez la commande avec son option `--recurse-submodules` : cette option télécharge aussi les packages partagés. La section 4 explique pourquoi elle est nécessaire.

### 1.2 - Lire ARCHITECTURE.md

Ouvrez maintenant `ARCHITECTURE.md`, à la racine du repo. Ce fichier fait une seule page, et c'est la seule lecture longue de la formation. Comptez 20 à 30 minutes.

La page commence par un arbre du repo. Elle définit ensuite cinq mots, en une phrase chacun : systemd, DDS, Zenoh, domaine ROS, namespace de topics. Deux de ces mots vous servent dès cette formation : le domaine ROS et le namespace de topics. Les trois autres sont le sujet de la formation 6 : lisez leur définition une fois, sans chercher à la retenir.

Ensuite, la page montre le schéma « qui tourne où » (trois boîtes et une flèche), puis un tableau qui l'accompagne. Regardez le schéma et le tableau avant de lire le texte. La section « Ce qui traverse la radio » cite des noms que vous ne connaissez pas encore (SIYI, Tailscale, `lo-multicast`, les listes `allow`) : lisez-la sans vous y arrêter. Le plan d'adressage et la section « Pour les leads » ne vous concernent pas encore.

### 1.3 - Qui tourne où

Le tableau qui suit le schéma a cinq lignes. Il couvre trois machines et cinq régimes. Un régime est une façon de faire tourner le code : développement et simulation sur le poste WSL, test sur véhicule et déploiement sur la Jetson, vol sur le portable GCS. Retenez trois choses de ce tableau.

Votre poste WSL est la seule machine que vous utiliserez pendant toute la formation 5. Les deux premières lignes du tableau vous concernent donc directement. Les trois autres sont à lire, pas à pratiquer. Sur votre poste, tout passe par le conteneur `dev`, le conteneur de développement. Vous y écrivez le code, vous y construisez un workspace et, en 5.2, vous y lancerez la simulation.

La Jetson est l'ordinateur embarqué sur le drone. Le test sur véhicule et le déploiement y lancent exactement les mêmes conteneurs. La seule différence est la façon de les démarrer : à la main pour le test sur véhicule, ou par systemd au démarrage pour le déploiement.

Le portable GCS est l'ordinateur au sol le jour de la compétition. Il fait tourner le workspace `gcs_ws`, que vous allez construire en section 4.

La dernière colonne du tableau donne le domaine ROS de chaque machine : 2 sur la Jetson, 3 au sol et sur votre poste. Vous en aurez besoin en section 3.2.

### 1.4 - Ce qui traverse la radio

Le drone et le sol sont deux systèmes ROS séparés. Les messages qui passent de l'un à l'autre passent par la radio. C'est le nom du topic qui décide si un message traverse : un topic `/aeac/external/...` traverse la radio, un topic `/aeac/internal/...` reste sur le drone. Pour cette formation, c'est tout ce que vous devez savoir sur la radio.

## 2 - La visite du repo, dossier par dossier

Cette visite prend une dizaine de minutes. Elle ne demande qu'une seule commande :

```bash
ls
```

```
ARCHITECTURE.md  Makefile  NOTES.md  README.md  compose  config  docker  packages  procédure.md  scripts  systemd  workspaces
```

Voici le même contenu sous forme d'arbre, avec une description de chaque ligne :

```
mission-template/
├── workspaces/       une mission, un workspace
├── packages/         les packages partagés entre missions
├── config/           les réglages, hors du code
├── compose/          ce qui lance les conteneurs
├── docker/           les recettes des images
├── systemd/          le démarrage automatique sur le drone
├── scripts/          les vérifications du repo
├── Makefile          la porte d'entrée : make help
├── README.md         par où commencer, et les règles du repo
├── ARCHITECTURE.md   la carte, celle que vous venez de lire
├── procédure.md      la checklist du jour J
└── NOTES.md          le carnet de l'équipe
```

Vous n'avez pas besoin de retenir les détails de cet arbre. Il sert à vous repérer dans le repo, par exemple quand une commande échoue. Les sept dossiers sont décrits ci-dessous en une ligne chacun ; le détail est dans `ARCHITECTURE.md`, que vous venez de lire. L'arbre d'`ARCHITECTURE.md` montre aussi `models/` et `bags/`. Ces deux dossiers sont hors git, et `make init` les crée en section 4.1.

**`docker/`** une image par rôle : `dockerfile.drone`, `dockerfile.gcs`, `dockerfile.mavros`, `dockerfile.vision`.

**`compose/`** un fichier par chose à lancer ; `dev.yml` décrit le conteneur `dev`, le seul que vous utilisez dans cette partie. `sim.yml` s'y ajoute en 5.2.

**`config/`** les réglages sortis du code, rangés selon ce qui les fait changer : la mission, le site, le drone.

**`packages/`** les packages partagés entre plusieurs missions. Cinq d'entre eux ont chacun leur propre repo GitHub ; la section 4.2 explique ce mécanisme. Le sixième, `sim_mocks`, remplace le matériel en simulation et se trouve directement dans ce repo.

**`scripts/`** les vérifications du repo : `check.py`, que vous lancerez avec `make check` en 5.3.

**`systemd/`** un service par brique sur la Jetson. Le jour J, grâce à ces services, tout démarre à la mise sous tension, sans personne au clavier.

**`workspaces/`** un workspace par mission. `gcs_ws` est le workspace du sol ; `vision_ws` se construit seulement sur la Jetson.

Il reste les fichiers de la racine. Quatre d'entre eux sont des documents : `README.md` dit par où commencer, `ARCHITECTURE.md` est la carte du repo, `procédure.md` est la checklist du jour J et `NOTES.md` est le carnet de l'équipe. Vous lisez les deux premiers dans cette formation ; les deux autres vous sont seulement présentés. Le dernier fichier est le `Makefile`. Comme dans les formations précédentes, il coordonne tout le reste. La section suivante lui est consacrée.

> [!TIP]
> **Jalon** : sans regarder l'écran, vous nommez les sept dossiers (`docker/`, `compose/`, `config/`, `packages/`, `scripts/`, `systemd/`, `workspaces/`) et vous dites en une phrase ce que chacun contient. Au début de 5.2, c'est la seule chose de 5.1 qu'on vous redemandera.

## 3 - Le Makefile en trois sections

### 3.1 - make help

```bash
make help
```

```

1. Développement et simulation (poste WSL)
  help              Affiche cette aide
  print-vars        Affiche les variables résolues (pour déboguer)
  init              Après le clone : submodules, réglages git, dossiers ignorés. Sans risque à relancer.
  status            État de git et des submodules en une page
  check             Vérifie le repo (package.xml, liens, submodules, README). À lancer avant une PR.
  models            Télécharge les modèles de vision dans models/ (hors git)
  build             Construit le workspace de C dans le conteneur IMG (colcon)
  dev               Entre dans le conteneur de développement (tout le repo est monté dans /aeac)
  sim               Simulation de la mission C : mavros vers la source SITL, puis le launch file dans le conteneur dev avec sim:=true et le site SITE
  shell             Ouvre un terminal dans le conteneur en cours (IMG=dev, gcs... pour en choisir un autre)
  down              Arrête tous les conteneurs aeac-* de ce poste (dev, mavros-sim, ...)
  logs              Suit les logs du conteneur en cours (IMG=mavros-sim pour ceux de mavros en simulation)
  takeoff           Arme et fait décoller le drone en simulation (node de test de sim_mocks)
  rc                Simule la manette au clavier (mock de sim_mocks, garde le terminal)
  echo              Affiche un topic : make echo T=/mavros/state
  link              Lie un package partagé au workspace de C : make link C=demo PKG=tools
  bag               Enregistre un rosbag daté dans bags/ (/aeac/* et mavros ; au sol, /aeac/external/* seulement)

2. Test sur véhicule (à la main, en avant-plan, Ctrl-C pour arrêter)
  mavros            mavros vers le Pixhawk (Jetson)
  zed               Caméra ZED (Jetson)
  zenoh-air         Pont Zenoh côté drone (Jetson)
  vision            Conteneur vision GPU (Jetson)
  drone             La mission C sur le drone, sur le terrain SITE de .env (Jetson)
  gcs               Les nodes sol de la mission C + pont Zenoh vers DRONE (portable)

3. Déploiement (Jetson, systemd ; leads)
  deploy            Installe les services systemd depuis systemd/ et fixe la mission C au boot
  undeploy          Arrête et désactive tous les services (pour repasser en test à la main)
  %-status          État d'un service : make mavros-status, make mission-status, ...
  %-logs            Logs d'un service en direct : make mission-logs
  %-restart         Redémarre un service : make zenoh-air-restart
  bump              Avance un submodule sur sa branche (.gitmodules, main par défaut) et prépare le commit : make bump PKG=tools

Variables : C=gcs (mission)  IMG=dev (conteneur)  DRONE=hexa  SITE=sim  SITL=mp (simulation)
Une commande qu'on retape souvent devient une cible d'ici : c'est fait pour.
```

Les trois sections regroupent les cinq régimes du tableau d'`ARCHITECTURE.md` (section 1.3). La première section couvre le développement et la simulation, sur le poste WSL. C'est la vôtre : c'est la seule que vous utilisez pendant toute la formation 5. La deuxième section couvre le test sur véhicule, lancé à la main et en avant-plan sur la Jetson. Elle couvre aussi le vol côté sol, avec `make gcs` sur le portable. La troisième section, réservée aux leads, couvre le déploiement par systemd. Pour utiliser une cible qui contient un `%`, remplacez le `%` par un nom de service, par exemple `make mission-logs`.

La dernière ligne de l'aide est importante. Elle signifie que, quand une commande est longue et qu'on la retape dix fois par séance, on en fait une cible make. Les cibles `takeoff`, `rc` et `echo` ont été créées de cette façon : elles remplacent trois commandes `ros2` qu'on tapait à la main dans le conteneur. Vous vous servirez de ces trois cibles en 5.2.

### 3.2 - Les variables

Cinq variables changent ce que font les cibles, et la fin de `make help` affiche toujours leurs valeurs courantes.

- `C=` est la mission, donc le workspace `workspaces/<C>_ws`. Par défaut, c'est `gcs`.
- `IMG=` est le conteneur dans lequel on travaille : `dev`, `drone`, `gcs` ou `vision`. Par défaut, c'est `dev`. Pour `make build`, `IMG=` choisit aussi le fichier de `compose/` à utiliser.
- `DRONE=` est le fichier de configuration de la radio côté sol, `config/drones/<DRONE>.json5`. Par défaut, c'est `hexa`. Vous ne vous en servez pas dans cette formation.
- `SITE=` est le terrain en simulation, `config/sites/<SITE>.yaml`. Par défaut, c'est `sim`. Vous le rencontrerez en 5.2.
- `SITL=` est la source de la simulation, donc l'endroit où mavros se branche pendant `make sim`. Par défaut, c'est `mp`, le SITL de Mission Planner de la formation 1 ; c'est le seul que vous utiliserez. Deux autres valeurs existent : `gazebo`, le SITL de Gazebo (sujet de la formation 4, à venir), et une URL mavros pour un SITL qui tourne sur une autre machine, par exemple `SITL=tcp://192.168.1.50:5760`.

Vous n'avez pas besoin d'`IMG=` pour `make shell`, `make echo` ou `make bag`. Sur votre poste, un seul conteneur de travail tourne, `aeac-dev`, et ces cibles le trouvent seules. `IMG=` sert à viser un autre conteneur. Le cas que vous rencontrerez, en 5.2, est `make logs IMG=mavros-sim` : cette commande affiche les logs de mavros, où mavros indique s'il joint le SITL. Sans `IMG=`, `make logs` suivrait `aeac-dev`, dont les logs n'ont rien d'utile.

Pour voir les valeurs que le Makefile utilise réellement, lancez :

```bash
make print-vars
```

```
C=gcs  WS=workspaces/gcs_ws  IMG=dev  COMPOSE=compose/dev.yml  DRONE=hexa  SITE=sim  SITL=mp  FCU_URL=tcp://127.0.0.1:5762
```

`FCU_URL` est l'adresse où mavros joint le SITL. Elle dépend de `SITL=`. Avec `SITL=mp`, c'est le port 5762 de `SITL_HOST`, qui vaut `127.0.0.1`. En WSL Mirrored (formation 2, section 1.5), un conteneur en réseau hôte (le mode host de la formation 2) voit Windows à cette adresse, et c'est sur Windows que tourne Mission Planner. Vous n'avez donc rien à régler.

Un seul cas demande un réglage : WSL en mode NAT, sous Windows 10, où le mode Mirrored n'existe pas. Dans ce cas, `SITL_HOST` doit recevoir l'adresse de Windows vue depuis WSL. Cette commande affiche cette adresse :

```bash
ip route show default | awk '{print $3}'
```

Copiez d'abord le modèle de réglages locaux :

```bash
cp .env.example .env
```

Ouvrez ensuite `.env`. Retirez le `#` devant `SITL_HOST=`, puis ajoutez l'adresse affichée. Le Makefile lit `.env` à chaque commande. Git ignore ce fichier : votre réglage reste donc sur votre poste. Ensuite, `make print-vars` affiche `FCU_URL` avec votre adresse.

`.env.example` contient aussi `SIM_DOMAIN`, le domaine ROS du conteneur `dev` et de la simulation. Sa valeur par défaut est 3. Ce réglage sert seulement en séance de groupe, quand plusieurs postes sont sur le même réseau. Chaque poste prend alors son propre numéro, comme l'explique le commentaire du fichier. Sinon, les nodes des postes voisins se voient entre elles. Les deux derniers réglages du fichier, `SITE` et `FCU_DEVICE`, servent seulement sur la Jetson.

## 4 - Initialiser et construire

Les commandes de cette section suivent l'ordre du `README.md` du repo. Après chaque commande, regardez ce qu'elle affiche, puis lisez le paragraphe qui suit : il explique ce que la commande a fait.

### 4.1 - make init

```bash
make init
```

```
Submodules initialisés, réglages git posés, dossiers models/ et bags/ créés.
```

Cette commande fait trois choses. Elle remplit les submodules ; si vous avez cloné avec `--recurse-submodules`, elle n'a rien à faire sur ce point. Elle règle git pour que vos `git pull` et vos `git push` tiennent compte des submodules. Elle crée `models/` et `bags/`, deux dossiers ignorés par git. Vous pouvez la relancer sans risque.

### 4.2 - make status

Cette section montre concrètement ce que contient `packages/`. Cinq de ses six packages sont des submodules. Comme l'explique `ARCHITECTURE.md` (section « Submodules »), un submodule est un repo dans un repo : votre repo retient seulement le commit à utiliser. `make status` montre où en est chaque submodule.

```bash
make status
```

Voici un extrait de la sortie, avec la branche et les submodules :

```
Branche : main
Submodules (espace = à jour, + = commit différent du pointeur, - = non initialisé) :
 792d97ec77f009ee1d6126b2503a46d40a67ad57 packages/custom_interfaces (heads/aeac-2027)
 8f5f96bbcf79346562fea6de708658827eecb3cc packages/nav_stack (heads/main)
 9ab2274ab96d2e2f4829baa2691c71466bf526b1 packages/tools (heads/aeac-2027)
 2c837a1a28b0dca1cb747a039b6e7405ae9f8d09 packages/vision (heads/main)
 ff1bf990d34e271b6a6af23889113e60ae866877 packages/zed-ros2-wrapper (humble-v5.1.0-1-gff1bf99)
```

Seul le premier caractère de chaque ligne compte. Un espace signifie que le submodule est sur le commit voulu. Un `-` signifie qu'il est vide : `make init` règle ce cas. Un `+` signifie qu'il est sur un autre commit : demandez à un lead. Le texte entre parenthèses peut être différent chez vous, et il ne compte pas.

`sim_mocks` n'est pas dans la liste, parce qu'il se trouve directement dans ce repo. Sur les submodules, vous devez savoir deux choses. D'abord, un import comme `tools.topics` vient de `packages/tools/`, pas de la mission. Ensuite, modifier un fichier dans un submodule modifie un autre repo, qui sert aussi à d'autres missions. Si un package de `packages/` apparaît comme modifié sous la liste, demandez à un lead avant de continuer.

### 4.3 - make build C=gcs

```bash
make build C=gcs
```

La première fois, cette commande prend environ 15 minutes, parce que Docker construit d'abord l'image à partir de `docker/dockerfile.gcs`. Il lance ensuite `colcon build --symlink-install` dans `workspaces/gcs_ws`. Vous voyez passer quatre packages : `custom_interfaces`, `tools`, `gcs_bringup` et `sim_mocks`.

```
Starting >>> custom_interfaces
Starting >>> sim_mocks
Finished <<< sim_mocks
Finished <<< custom_interfaces
Starting >>> tools
Finished <<< tools
Starting >>> gcs_bringup
Finished <<< gcs_bringup

Summary: 4 packages finished
```

Cette sortie ne montre pas les durées que colcon affiche entre crochets. L'ordre des lignes peut aussi varier chez vous. Une règle, par contre, ne change pas : colcon attend qu'un package soit fini avant de construire les packages qui en dépendent. Il lit ces dépendances dans leur `package.xml`. `gcs_bringup` passe donc toujours après `tools`, et `tools` passe toujours après `custom_interfaces`.

Trois de ces quatre packages viennent de `packages/`. Pour voir comment, lancez :

```bash
ls -l workspaces/gcs_ws/src
```

Voici la fin de chaque ligne. Les colonnes de droits, de propriétaire et de date sont retirées ici :

```
custom_interfaces -> ../../../packages/custom_interfaces
gcs_bringup
sim_mocks -> ../../../packages/sim_mocks
tools -> ../../../packages/tools
```

La flèche `->` marque un symlink, le raccourci dont parle `ARCHITECTURE.md`. `tools` n'est donc pas une copie : c'est `packages/tools`, vu depuis le workspace. Un workspace contient ainsi deux choses : ses propres packages, ici `gcs_bringup`, et des liens vers les packages partagés dont il a besoin. Un lead crée ces liens une seule fois avec `make link`, puis les ajoute au repo par un commit. Vous recevez donc toujours un workspace où les liens existent déjà. Un `ls -l` sur le dossier `src/` d'un workspace montre ce que la mission utilise, et ce qui est partagé.

`gcs_ws` sert uniquement au sol : on n'y met jamais de code spécifique à un drone ou à une mission. Chaque mission a son propre workspace, y compris pendant le développement. Le conteneur `dev` peut construire n'importe lequel de ces workspaces. `C=gcs` est la valeur par défaut seulement parce que `gcs_ws` est le workspace que tout le monde a.

### 4.4 - make dev

```bash
make dev
```

La commande démarre le conteneur de développement s'il ne tourne pas, puis ouvre un shell dans ce conteneur. Vous êtes maintenant dans `/aeac/workspaces/gcs_ws`. Pour le vérifier :

```bash
pwd
```

```
/aeac/workspaces/gcs_ws
```

Deux passages de `compose/dev.yml` expliquent ce résultat :

```yaml
    volumes:
      - ..:/aeac
      - /tmp/.X11-unix:/tmp/.X11-unix:rw
    working_dir: /aeac/workspaces/${C:-gcs}_ws
```

La première ligne de `volumes:` monte tout le repo dans `/aeac`, à l'intérieur du conteneur. Grâce à ce montage, vous pouvez construire et lancer n'importe quel workspace depuis ce même conteneur. Pour la même raison, un fichier que vous modifiez dans VS Code sous WSL est immédiatement modifié dans le conteneur : c'est le même fichier. La seconde ligne de `volumes:` donne au conteneur l'accès à l'affichage graphique, pour rviz. `working_dir` vous place directement dans le workspace de `C`.

Vous n'avez rien à sourcer : le Dockerfile ajoute trois lignes à `/root/.bashrc`, et chaque terminal que vous ouvrez dans le conteneur `dev` les exécute automatiquement :

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
[ -f "$PWD/install/setup.bash" ] && source "$PWD/install/setup.bash"
ros2 daemon start > /dev/null 2>&1
```

Ces lignes sourcent ROS 2, puis le workspace du dossier courant s'il est construit. Elles démarrent ensuite le daemon `ros2`. Vérifiez-le tout de suite :

```bash
ros2 topic list
```

La commande fonctionne sans que vous ayez lancé de `source` avant. Elle affiche au moins `/parameter_events` et `/rosout`.

### 4.5 - Le heartbeat du sol

Pour l'instant, `gcs_bringup` contient un seul launch file, `base.launch.py`. Ce launch file contient ce que le portable GCS lance quelle que soit la mission. Il démarre une node, le heartbeat du sol. Cette node publie un message une fois par seconde pour signaler que la station au sol est en vie.

Dans le terminal de `make dev`, lancez :

```bash
ros2 launch gcs_bringup base.launch.py
```

```
[INFO] [launch]: All log files can be found below /root/.ros/log/...
[INFO] [gcs_heartbeat-1]: process started with pid [42]
[gcs_heartbeat-1] [INFO] [gcs_heartbeat]: Heartbeat GCS démarré : publication à 1.0 Hz sur /aeac/external/gcs/heartbeat
```

ROS 2 écrit aussi un horodatage après `[INFO]`. Pour la lisibilité, cet horodatage est retiré des sorties de cette formation.

Ouvrez un second terminal WSL et placez-vous dans le repo. Entrez ensuite dans le conteneur qui tourne :

```bash
make shell
```

```bash
ros2 topic echo /aeac/external/gcs/heartbeat
```

```
data: true
---
data: true
---
```

Le nom de ce topic n'est écrit nulle part dans la node. Il vient de `packages/tools/tools/topics.py`, où la constante `GCS_HEARTBEAT` le définit une seule fois. C'est la règle des topics du repo, et chaque node que vous lirez l'applique. Le deuxième segment du nom, `external`, indique que ce topic doit traverser la radio. C'est bien le cas : le sol envoie son heartbeat au drone.

Quand vous avez vu défiler quelques messages, faites `Ctrl-C` dans les deux terminaux. Tapez ensuite `exit` pour sortir du conteneur. Deux messages peuvent vous surprendre, mais aucun n'indique une panne. Le launch file se termine sur une trace `RCLError: failed to shutdown` : la node du heartbeat s'arrête mal, sans conséquence. Et `make` écrit une ligne `make: *** ... Error` quand il vous rend la main, parce que le shell du conteneur lui transmet le code de sortie du `Ctrl-C`. De retour dans WSL, à la racine du repo, arrêtez le conteneur `dev` :

```bash
make down
```

`make down` arrête tous les conteneurs `aeac-*` de votre poste. Prenez l'habitude de le lancer en fin de séance, et aussi après une simulation.

> [!TIP]
> **Jalon** : vous avez réussi si `data: true` défile une fois par seconde dans le second terminal pendant que le launch file tourne dans le premier.

## 5 - Les règles, en une page

Ouvrez le `README.md` du repo, à la section « Règles du repo », et lisez les sept règles. Elles sont courtes, et on vous les rappellera en revue de code :

1. `main` est ce qui vole. On travaille sur une branche, on ouvre une PR, un lead merge.
2. Le code de mission n'arme jamais et ne change jamais de mode : c'est le pilote. Les seules nodes qui le font sont les `*_test` de `sim_mocks`, jamais inclus par un launch file de mission.
3. Un nom de topic s'écrit une fois, dans `tools/topics.py`. `/aeac/external/...` traverse la radio, `/aeac/internal/...` reste sur le drone.
4. Ce qui change entre deux drones, deux terrains ou deux essais est dans `config/`, pas dans le code.
5. Chaque mission a son workspace. `gcs_ws` est le workspace du sol : rien de spécifique à un drone ou à une mission n'y entre.
6. Code en anglais ; docs, logs et commentaires de haut niveau en français.
7. Ce qu'on apprend et qu'on n'a pas le temps de ranger va dans `NOTES.md`.

Deux de ces règles sont à retenir avant d'écrire une seule ligne de code : les deux premières. La règle 2 dit que le code de mission n'arme pas et ne change pas de mode, parce que c'est le pilote qui en est responsable. Vous avez déjà rencontré ce principe en formation 3.4, avec la node `takeoff`. La règle 1 dit que `main` est ce qui vole, dans un repo de compétition comme `aeac-2027`. Le `main` du template ne vole pas, puisque le template n'a pas de mission. La discipline y est pourtant la même : vous créez une branche, vous lancez `make check`, puis vous ouvrez une PR qu'un lead relit. Une PR (pull request) est la demande, sur GitHub, de faire entrer votre branche dans `main`. Vous ferez tout cela en 5.3.

Il reste à savoir où écrire. `NOTES.md` est le carnet de l'équipe. Notez-y ce que vous avez appris, ce qui vous a fait perdre deux heures, le réglage qui a marché. Écrivez-y sans demander la permission. `procédure.md` est la checklist du jour J, écrite par les membres qui vont sur le terrain. Lisez-la pour savoir qu'elle existe, mais vous ne l'appliquerez pas, puisque vous n'avez pas de drone.

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `make build` construit moins de quatre packages | Un submodule est vide : le clone a été fait sans `--recurse-submodules` | `make status` (un `-` en début de ligne), puis `make init` (section 4.2) |
| `Package 'gcs_bringup' not found` alors que le build a réussi | Ce terminal a été ouvert avant le build : le workspace n'existait pas encore quand le shell l'a cherché | Fermer ce terminal et en ouvrir un autre avec `make shell` (section 4.4) |
| `ros2` introuvable, ou le topic du heartbeat invisible dans le second terminal | Le second terminal est resté dans WSL, hors du conteneur | Ouvrir le second terminal avec `make shell` (section 4.5) |
| Des fichiers appartenant à `root` apparaissent après un build | Les conteneurs de ce repo tournent encore en root, pas avec l'utilisateur non root que recommande la formation 2 | `sudo chown -R $USER:$USER .` à la racine du repo (formation 2, section 2.5) |
| `make: command not found` sous WSL | Le package n'est pas installé | `sudo apt install make` |
| `make shell` dit qu'aucun conteneur ne tourne | Aucun conteneur n'est démarré | Lancer d'abord `make dev` dans le premier terminal |
| `make status` affiche un `+` devant un package de `packages/` | Le submodule est sur un autre commit que celui attendu par le repo | Ne rien push et demander à un lead (section 4.2) |
