# Formation 5.1 : le repo vu de haut

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Nommer les trois machines (poste WSL, Jetson, portable GCS), leurs cinq régimes (développement, simulation, test sur véhicule, déploiement, vol) et ce qui tourne sur chacune
- Nommer les sept dossiers du repo de mission et dire en une phrase ce que chacun contient
- Lire `make help` en trois sections et savoir laquelle vous concerne
- Cloner, initialiser et construire un repo de mission, puis lancer un launch file dans le conteneur de développement
- Retrouver les règles du repo, et dire les deux qui comptent avant d'écrire du code

Prérequis : la formation 0 (git, section 3), la formation 1 (le SITL de Mission Planner), et les formations 2 et 3 terminées (WSL, Docker, Compose et Make en place ; une node ROS 2 écrite, lancée par un launch file et une cible make). La formation 4 n'est pas nécessaire : le simulateur utilisé ici est le SITL de Mission Planner.

Les formations 2 et 3 vous ont appris les outils : Docker, Compose, Make, ROS 2. Ce sont les mêmes ici ; ce qui change, c'est l'échelle. Le repo de compétition fait vivre ensemble plusieurs missions, plusieurs conteneurs, plusieurs ordinateurs et plusieurs opérateurs, et chaque dossier existe pour une de ces raisons. Le dossier `docker/` de la formation 2 tenait une seule recette d'image : il en tient maintenant une par rôle. Ses deux fichiers compose sont devenus un fichier par chose à lancer. Son Makefile de huit cibles en compte ici une trentaine, rangées en trois sections. Même boîte à outils, rangée pour une équipe.

> [!NOTE]
> **Avant de commencer**
> - **Durée** : environ 1 h 45, dont une dizaine de minutes de visite du repo et une quinzaine de construction Docker pendant lesquelles on lit la suite.
> - **Prérequis** : formations 2 et 3 faites. Docker démarre sous WSL, `make` est installé, et vous avez un compte GitHub membre de l'organisation `zenith-polymtl`. Si ce n'est pas le cas, demandez à un lead, avant la séance, de vous ajouter à l'organisation et à l'équipe contrôle : sans ça, le push de la formation 5.3 sera refusé.
> - **À la fin** : le conteneur de développement ouvert, le workspace `gcs_ws` construit, et le heartbeat du sol qui défile dans un `ros2 topic echo`.
> - **Aide** : Discord, salon Contrôle, fil « Formations et Questions », avec le message d'erreur exact.
> - **À poster à la fin** : une photo du schéma dessiné à la main (section 1.5) et une capture de `make status` (section 4.2).

Le repo que vous clonez est le repo template, `mission-template`. C'est le squelette dont les repos de compétition sont issus : les mêmes submodules, les mêmes conteneurs, les mêmes packages partagés, sans le code de mission. Votre clone est à vous, vous pouvez le casser. Le repo de compétition `aeac-2027`, lui, n'est jamais touché par la formation.

**D'aeac-2026 au template.** Les formations 2 et 3 vous ont parlé du repo `aeac-2026`. Le template en est le successeur : les mêmes idées, rangées autrement. Si vous croisez l'ancien repo, ou quelqu'un qui en parle, voici les correspondances.

| Dans aeac-2026 | Dans le template (et aeac-2027) |
|---|---|
| un package `bringup` partagé, avec un launch file par mission (`water_mission.launch.py`, ...) | un workspace par mission, avec son package `<mission>_bringup` et son `launch/mission.launch.py` |
| `make mavros-sim` | `make sim C=<mission>` |
| `make mavros-gazebo` | `make sim C=<mission> SITL=gazebo` |
| `nav_stack`, dont la node `init` qui demande les flux de messages à l'autopilote | le même `nav_stack`, submodule partagé dans `packages/nav_stack` |

> [!WARNING]
> **Mêmes noms, autre sens.** Quatre cibles portent le nom d'une cible des formations 2 et 3, mais ne font plus la même chose. Relisez ce tableau la première fois qu'une de ces commandes vous surprend.

| Cible | Dans les formations 2 et 3 | Ici |
|---|---|---|
| `make build` | construit l'image Docker | construit le workspace de `C=` avec colcon, dans un conteneur (l'image se construit au passage la première fois) |
| `make mavros` | démarre mavros vers le SITL | démarre mavros vers le Pixhawk, sur la Jetson ; la simulation passe par `make sim` |
| `make shell` | démarre le conteneur au besoin, puis ouvre un shell | entre dans un conteneur qui tourne déjà, et refuse si aucun ne tourne |
| `make mavros-logs` | les logs du conteneur mavros | les logs du service systemd `mavros` sur la Jetson (`journalctl`) ; en simulation, c'est `make logs IMG=mavros-sim` |

## 1 - Cloner, puis lire ARCHITECTURE.md

### 1.1 - On clone maintenant, on comprend après

La page que vous allez lire est dans le repo. On clone donc avant de comprendre, et le clone lui-même prend une seule commande. Clonez dans votre home WSL, pas sous `/mnt/c` : sur le disque Windows, tout est lent et `colcon build` échoue sur des permissions (formation 2, section 2.7).

```bash
cd ~
```

```bash
git clone --recurse-submodules https://github.com/zenith-polymtl/mission-template
```

```bash
cd mission-template
```

Copiez l'option `--recurse-submodules` telle quelle : elle ramène les packages partagés, et la section 4 explique pourquoi.

### 1.2 - Lire ARCHITECTURE.md

Ouvrez maintenant `ARCHITECTURE.md`, à la racine. C'est une page, et c'est la seule lecture longue de la formation : comptez 20 à 30 minutes.

Elle s'ouvre sur un arbre du repo, puis définit cinq mots en une phrase chacun : systemd, DDS, Zenoh, domaine ROS, namespace de topics. Deux vous servent dès cette formation, le domaine ROS et le namespace de topics. Les trois autres sont le sujet de la formation 6 : lisez-les une fois, sans chercher à les retenir.

Viennent ensuite le schéma « qui tourne où », trois boîtes et une flèche, puis son tableau. Regardez les deux avant de lire le texte. La section « Ce qui traverse la radio » cite des noms que vous ne connaissez pas encore (SIYI, Tailscale, `lo-multicast`, les listes `allow`) : lisez-la sans vous y arrêter. Le plan d'adressage et la section « Pour les leads » ne vous concernent pas encore.

### 1.3 - Qui tourne où

Le tableau qui suit le schéma tient en cinq lignes : trois machines et cinq régimes. Un régime est une façon de faire tourner le code : développement et simulation sur le poste WSL, test sur véhicule et déploiement sur la Jetson, vol sur le portable GCS. Trois choses à en retenir.

Votre poste WSL est la seule machine que vous aurez pendant toute la formation 5 : les deux premières lignes du tableau sont les vôtres, les trois autres se lisent et ne se pratiquent pas. Sur votre poste, tout passe par le conteneur `dev`, le conteneur de développement : on y code, on y construit un workspace et, en 5.2, on y lance la simulation.

La Jetson est l'ordinateur embarqué sur le drone. Le test sur véhicule et le déploiement y lancent exactement les mêmes conteneurs, et la seule différence est qui appuie sur le bouton : vous à la main, ou systemd au démarrage.

Le portable GCS est l'ordinateur au sol le jour de la compétition. Le workspace qu'il fait tourner, `gcs_ws`, est celui que vous allez construire tout à l'heure.

La dernière colonne, le domaine ROS, resservira en section 3.2 : 2 sur la Jetson, 3 au sol et sur votre poste.

### 1.4 - Ce qui traverse la radio

Le drone et le sol sont deux mondes ROS séparés. Ce qui passe de l'un à l'autre passe par la radio, et c'est le nom du topic qui le décide : un topic `/aeac/external/...` traverse, un topic `/aeac/internal/...` reste sur le drone. C'est tout ce dont vous avez besoin ici.

Une dizaine de minutes, sans aucune commande à part celle-ci :

Le même contenu, rangé en arbre, avec ce que chaque ligne contient :

```
mission-template/
├── workspaces/       une mission, un workspace
├── packages/         les packages partagés entre missions
├── config/           les réglages, hors du code
├── compose/          ce qui lance les conteneurs
├── docker/           les recettes des images
├── systemd/          le démarrage automatique sur le drone
├── scripts/          les vérifications du repo
├── Makefile          la porte d'entrée : make help
├── README.md         par où commencer, et les règles du repo

├── procédure.md      la checklist du jour J
└── NOTES.md          le carnet de l'équipe
```

C'est la carte qu'on regarde avant de marcher. Vous n'avez rien à retenir des détails, seulement à savoir où vous êtes quand une commande échouera. Sept dossiers, une ligne chacun ; le détail est dans `ARCHITECTURE.md`, que vous venez de lire. Son arbre montre aussi `models/` et `bags/` : ils sont hors git, et `make init` les crée en section 4.1.

**`docker/`** une image par rôle : `dockerfile.drone`, `dockerfile.gcs`, `dockerfile.mavros`, `dockerfile.vision`.

**`compose/`** un fichier par chose à lancer ; `dev.yml` décrit le conteneur `dev`, le seul que vous utilisez dans cette partie. `sim.yml` s'y ajoute en 5.2.

**`config/`** les réglages sortis du code, rangés selon ce qui les fait changer : la mission, le site, le drone.

**`packages/`** les packages partagés entre plusieurs missions. Cinq vivent chacun dans son propre repo GitHub, et la section 4.2 dit comment. Le sixième, `sim_mocks`, qui remplace le matériel en simulation, vit dans ce repo même.

**`systemd/`** un service par brique sur la Jetson, pour qu'au jour J tout parte à la mise sous tension, sans personne au clavier.

**`workspaces/`** une mission, un workspace ; `gcs_ws` est celui du sol, `vision_ws` ne se construit que sur la Jetson.

Restent les fichiers de la racine. Quatre documents : `README.md` par où commencer, `ARCHITECTURE.md` la carte, `procédure.md` le jour J, `NOTES.md` le carnet. Les deux premiers sont lus dans cette formation, les deux autres vous sont montrés. Et le `Makefile`, qui coordonne tout le reste, comme dans les formations précédentes : c'est la section suivante.

## 3 - Le Makefile en trois sections

### 3.1 - make help

```bash
make help
```

```

1. Développement et simulation (poste WSL)
  help              Affiche cette aide
  print-vars        Affiche les variables résolues (pour déboguer)
  init              Après le clone : submodules, réglages git, dossiers ignorés. Sans risque à relancer.
  status            État de git et des submodules en une page
  check             Vérifie le repo (package.xml, liens, submodules, README). À lancer avant une PR.
  models            Télécharge les modèles de vision dans models/ (hors git)
  build             Construit le workspace de C dans le conteneur IMG (colcon)
  dev               Entre dans le conteneur de développement (tout le repo est monté dans /aeac)
  sim               Simulation de la mission C : mavros vers la source SITL, puis le launch file dans le conteneur dev avec sim:=true et le site SITE
  shell             Ouvre un terminal dans le conteneur en cours (IMG=dev, gcs... pour en choisir un autre)
  down              Arrête tous les conteneurs aeac-* de ce poste (dev, mavros-sim, ...)
  logs              Suit les logs du conteneur en cours (IMG=mavros-sim pour ceux de mavros en simulation)
  takeoff           Arme et fait décoller le drone en simulation (node de test de sim_mocks)
  rc                Simule la manette au clavier (mock de sim_mocks, garde le terminal)
  echo              Affiche un topic : make echo T=/mavros/state
  link              Lie un package partagé au workspace de C : make link C=demo PKG=tools
  bag               Enregistre un rosbag daté dans bags/ (/aeac/* et mavros ; au sol, /aeac/external/* seulement)

2. Test sur véhicule (à la main, en avant-plan, Ctrl-C pour arrêter)
  mavros            mavros vers le Pixhawk (Jetson)
  zed               Caméra ZED (Jetson)
  zenoh-air         Pont Zenoh côté drone (Jetson)
  vision            Conteneur vision GPU (Jetson)
  drone             La mission C sur le drone, sur le terrain SITE de .env (Jetson)
  gcs               Les nodes sol de la mission C + pont Zenoh vers DRONE (portable)

3. Déploiement (Jetson, systemd ; leads)
  deploy            Installe les services systemd depuis systemd/ et fixe la mission C au boot
  undeploy          Arrête et désactive tous les services (pour repasser en test à la main)
  %-status          État d'un service : make mavros-status, make mission-status, ...
  %-logs            Logs d'un service en direct : make mission-logs
  %-restart         Redémarre un service : make zenoh-air-restart
  bump              Avance un submodule sur sa branche (.gitmodules, main par défaut) et prépare le commit : make bump PKG=tools

Variables : C=gcs (mission)  IMG=dev (conteneur)  DRONE=hexa  SITE=sim  SITL=mp (simulation)
Une commande qu'on retape souvent devient une cible d'ici : c'est fait pour.
```

Les trois sections regroupent les cinq régimes du tableau d'`ARCHITECTURE.md` (section 1.3). La première couvre le développement et la simulation, sur le poste WSL : c'est la vôtre, et c'est la seule que vous touchez pendant toute la formation 5. La deuxième couvre le test sur véhicule, à la main et en avant-plan, sur la Jetson, et le vol côté sol avec `make gcs` sur le portable. La troisième est le déploiement par systemd, réservée aux leads ; les cibles avec un `%` dedans s'utilisent en remplaçant le `%` par un nom de service, par exemple `make mission-logs`.

Lisez la dernière ligne de l'aide, elle dit quelque chose d'important. Quand une commande est longue et qu'on la retape dix fois par séance, on en fait une cible make. `takeoff`, `rc` et `echo` sont nées comme ça : elles remplacent trois commandes `ros2` qu'on tapait à la main dans le conteneur. Vous vous en servirez en 5.2.

### 3.2 - Les variables

Cinq variables changent ce que font les cibles, et la fin de `make help` affiche toujours leurs valeurs courantes.

- `C=` est la mission, donc le workspace `workspaces/<C>_ws`. Par défaut `gcs`.
- `IMG=` est le conteneur dans lequel on travaille : `dev`, `drone`, `gcs` ou `vision`. Par défaut `dev`. Pour `make build`, c'est lui qui choisit le fichier de `compose/`.
- `DRONE=` est le fichier de configuration de la radio côté sol, `config/drones/<DRONE>.json5`. Par défaut `hexa`. Vous ne vous en servez pas dans cette formation.
- `SITE=` est le terrain en simulation, `config/sites/<SITE>.yaml`, `sim` par défaut. Vous le rencontrerez en 5.2.
- `SITL=` est la source de la simulation, donc l'endroit où mavros se branche pendant `make sim`. Par défaut `mp`, le SITL de Mission Planner de la formation 1, et c'est le seul que vous utiliserez. Il existe aussi `gazebo`, le SITL de Gazebo (sujet de la formation 4, à venir), et une URL mavros pour un SITL qui tourne sur une autre machine, par exemple `SITL=tcp://192.168.1.50:5760`.

`IMG=` n'est pas nécessaire pour `make shell`, `make echo` ni `make bag`. Sur votre poste, un seul conteneur de travail tourne, `aeac-dev`, et ces cibles le trouvent toutes seules. `IMG=` sert à viser un autre conteneur, et le cas que vous rencontrerez est `make logs IMG=mavros-sim`, en 5.2 : les logs de mavros, là où il dit s'il joint le SITL. Sans `IMG=`, `make logs` suivrait `aeac-dev`, qui n'affiche rien d'utile.

Pour voir ce que ça donne une fois résolu :

```bash
make print-vars
```

```
C=gcs  WS=workspaces/gcs_ws  IMG=dev  COMPOSE=compose/dev.yml  DRONE=hexa  SITE=sim  SITL=mp  FCU_URL=tcp://127.0.0.1:5762
```

`FCU_URL` est l'adresse où mavros joint le SITL, et elle découle de `SITL=`. Avec `SITL=mp`, c'est le port 5762 de `SITL_HOST`, qui vaut `127.0.0.1` : en WSL Mirrored (formation 2, section 1.5), un conteneur en réseau hôte (le mode host de la formation 2) voit Windows, où tourne Mission Planner, à cette adresse. Vous n'avez rien à régler.

Un seul cas demande un réglage : WSL en mode NAT, sous Windows 10, où le mode Mirrored n'existe pas. Il faut alors donner à `SITL_HOST` l'adresse de Windows vue de WSL, que cette commande affiche :

```bash
ip route show default | awk '{print $3}'
```

Copiez le modèle de réglages locaux, puis ouvrez `.env`, retirez le `#` devant `SITL_HOST=` et ajoutez l'adresse affichée :

```bash
cp .env.example .env
```

Le Makefile lit `.env` à chaque commande, et git l'ignore : votre réglage ne part sur le poste de personne. `make print-vars` montre ensuite `FCU_URL` avec votre adresse.

`.env.example` contient aussi `SIM_DOMAIN` : le domaine ROS du conteneur `dev` et de la simulation, 3 par défaut. Il ne sert qu'en séance de groupe, sur un même réseau : chaque poste prend son propre numéro, comme l'explique le commentaire du fichier, sinon les nodes des postes voisins se voient entre elles. Les deux derniers réglages du fichier, `SITE` et `FCU_DEVICE`, ne servent que sur la Jetson.

## 4 - Initialiser et construire

L'ordre est celui du `README.md` du repo. À chaque commande, regardez ce qu'elle affiche : la phrase qui suit dit ce qu'elle a fait.

### 4.1 - make init

```bash
make init
```

```
Submodules initialisés, réglages git posés, dossiers models/ et bags/ créés.
```

Une ligne, trois choses faites. Elle remplit les submodules, et ne trouve rien à faire si vous avez cloné avec `--recurse-submodules`. Elle règle git pour que vos `git pull` et vos `git push` tiennent compte des submodules. Elle crée `models/` et `bags/`, deux dossiers ignorés par git. Elle est sans risque à relancer.

### 4.2 - make status

C'est ici que `packages/` devient concret. Cinq de ses six packages sont des submodules, et `ARCHITECTURE.md` l'a dit (section « Submodules ») : un submodule est un repo dans un repo, dont le vôtre retient seulement le commit voulu. `make status` montre où en est chacun.

```bash
make status
```

Extrait de la sortie, la branche et les submodules :

```
Branche : main
Submodules (espace = à jour, + = commit différent du pointeur, - = non initialisé) :
 792d97ec77f009ee1d6126b2503a46d40a67ad57 packages/custom_interfaces (heads/aeac-2027)
 8f5f96bbcf79346562fea6de708658827eecb3cc packages/nav_stack (heads/main)
 9ab2274ab96d2e2f4829baa2691c71466bf526b1 packages/tools (heads/aeac-2027)
 2c837a1a28b0dca1cb747a039b6e7405ae9f8d09 packages/vision (heads/main)
 ff1bf990d34e271b6a6af23889113e60ae866877 packages/zed-ros2-wrapper (humble-v5.1.0-1-gff1bf99)
```

Seul compte le premier caractère de chaque ligne : un espace, le submodule est sur le commit voulu ; un `-`, il est vide (`make init` le règle) ; un `+`, il est sur un autre commit (demandez à un lead). Le texte entre parenthèses peut différer chez vous, il ne compte pas.

`sim_mocks` n'est pas dans la liste, puisqu'il vit dans ce repo. Ce qu'on vous demande des submodules : savoir qu'un import comme `tools.topics` vit dans `packages/tools/` et pas dans la mission, et que modifier un fichier là-dedans modifie un autre repo, qui sert à d'autres missions. Si un package de `packages/` apparaît comme modifié sous la liste, demandez à un lead avant de continuer.

### 4.3 - make build C=gcs

```bash
make build C=gcs
```

C'est le quart d'heure de construction. Docker fabrique d'abord l'image à partir de `docker/dockerfile.gcs` (la première fois seulement), puis lance `colcon build --symlink-install` dans `workspaces/gcs_ws`. Vous voyez passer quatre packages : `custom_interfaces`, `tools`, `gcs_bringup` et `sim_mocks`.

```
Starting >>> custom_interfaces
Starting >>> sim_mocks
Finished <<< sim_mocks
Finished <<< custom_interfaces
Starting >>> tools
Finished <<< tools
Starting >>> gcs_bringup
Finished <<< gcs_bringup

Summary: 4 packages finished
```

Les durées que colcon affiche entre crochets sont retirées ici, et l'ordre des lignes peut varier chez vous. Une chose ne varie pas : colcon attend qu'un package soit fini avant de construire ceux qui en dépendent, d'après leur `package.xml`. `gcs_bringup` passe donc toujours après `tools`, qui passe après `custom_interfaces`.

Trois d'entre eux viennent de `packages/`. Regardez comment :

```bash
ls -l workspaces/gcs_ws/src
```

La fin de chaque ligne (les colonnes de droits, de propriétaire et de date sont retirées ici) :

```
custom_interfaces -> ../../../packages/custom_interfaces
gcs_bringup
sim_mocks -> ../../../packages/sim_mocks
tools -> ../../../packages/tools
```

La flèche `->` marque un symlink, le raccourci dont parle `ARCHITECTURE.md` : `tools` n'est pas une copie, c'est `packages/tools` vu depuis le workspace. Un workspace contient ainsi ses propres packages, ici `gcs_bringup`, et des liens vers les packages partagés dont il a besoin. Ces liens sont posés une fois par un lead, avec `make link`, et ajoutés au repo par un commit : vous recevez toujours un workspace déjà lié. Un `ls -l` sur le `src/` d'un workspace répond donc à la question « qu'est-ce que cette mission utilise, et qu'est-ce qui est partagé ».

`gcs_ws` est le workspace du sol, et rien d'autre : on n'y met jamais de code spécifique à un drone ou à une mission. Chaque mission a son propre workspace, y compris pendant le développement, et le conteneur `dev` sert à construire n'importe lequel. Si `C=gcs` est la valeur par défaut, c'est seulement parce que c'est le workspace que tout le monde a.

### 4.4 - make dev

```bash
make dev
```

La commande démarre le conteneur de développement s'il ne tourne pas, puis vous y ouvre un shell. Vous êtes maintenant dans `/aeac/workspaces/gcs_ws` :

```bash
pwd
```

```
/aeac/workspaces/gcs_ws
```

Deux endroits de `compose/dev.yml` expliquent cet affichage :

```yaml
    volumes:
      - ..:/aeac
      - /tmp/.X11-unix:/tmp/.X11-unix:rw
    working_dir: /aeac/workspaces/${C:-gcs}_ws
```

La première ligne de `volumes:` monte tout le repo dans `/aeac`, à l'intérieur du conteneur. C'est ce qui vous permet de construire et de lancer n'importe quel workspace depuis ce même conteneur, et c'est aussi pourquoi un fichier que vous modifiez dans VS Code sous WSL est immédiatement modifié dans le conteneur : c'est le même fichier. La seconde ligne passe l'affichage graphique, pour rviz. `working_dir` vous dépose directement dans le workspace de `C`.

Vous n'avez rien à sourcer. Le Dockerfile ajoute trois lignes à `/root/.bashrc`, et chaque terminal que vous ouvrez dans le conteneur `dev` les joue tout seul :

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
[ -f "$PWD/install/setup.bash" ] && source "$PWD/install/setup.bash"
ros2 daemon start > /dev/null 2>&1
```

ROS 2, puis le workspace du dossier courant s'il est construit, puis le daemon `ros2`. Vérifiez-le tout de suite :

```bash
ros2 topic list
```

Il répond, au moins `/parameter_events` et `/rosout`, sans que vous ayez rien tapé avant.

### 4.5 - Le heartbeat du sol

`gcs_bringup` contient un seul launch file pour l'instant, `base.launch.py` : ce que le portable GCS lance quelle que soit la mission. Il démarre une node, le heartbeat du sol, qui publie une fois par seconde pour dire que la station est en vie.

Dans le terminal de `make dev` :

```bash
ros2 launch gcs_bringup base.launch.py
```

```
[INFO] [launch]: All log files can be found below /root/.ros/log/...
[INFO] [gcs_heartbeat-1]: process started with pid [42]
[gcs_heartbeat-1] [INFO] [gcs_heartbeat]: Heartbeat GCS démarré : publication à 1.0 Hz sur /aeac/external/gcs/heartbeat
```

ROS 2 écrit aussi un horodatage après `[INFO]` : il est retiré des sorties de cette formation, pour la lisibilité.

Ouvrez un second terminal WSL, dans le repo, et entrez dans le conteneur qui tourne :

```bash
make shell
```

```bash
ros2 topic echo /aeac/external/gcs/heartbeat
```

```
data: true
---
data: true
---
```

Le nom de ce topic n'est écrit nulle part dans la node : il vient de `packages/tools/tools/topics.py`, où la constante `GCS_HEARTBEAT` le définit une fois pour toutes. C'est la règle des topics du repo, et vous la verrez appliquée dans chaque node que vous lirez. Son deuxième segment, `external`, dit qu'il est destiné à traverser la radio : c'est bien le cas, le sol envoie son heartbeat au drone.

`Ctrl-C` dans les deux terminaux quand vous avez vu défiler quelques messages, puis `exit` pour sortir du conteneur. Deux sorties peuvent surprendre, et aucune n'est une panne : le launch file finit sur une trace `RCLError: failed to shutdown` (la node du heartbeat s'arrête mal, sans conséquence), et `make` écrit une ligne `make: *** ... Error` en rendant la main, parce que le shell du conteneur lui transmet le code du `Ctrl-C`. De retour dans WSL, à la racine du repo, arrêtez le conteneur `dev` :

```bash
make down
```

`make down` arrête tous les conteneurs `aeac-*` de votre poste. Prenez l'habitude de le lancer en fin de séance, après une simulation aussi.

> [!TIP]
> **Jalon** : vous avez réussi si `data: true` défile une fois par seconde dans le second terminal pendant que le launch file tourne dans le premier.

## 5 - Les règles, en une page

Ouvrez le `README.md` du repo, section « Règles du repo », et lisez les sept règles. Elles sont courtes, et elles vous seront opposées en revue de code :

1. `main` est ce qui vole. On travaille sur une branche, on ouvre une PR, un lead merge.
2. Le code de mission n'arme jamais et ne change jamais de mode : c'est le pilote. Les seules nodes qui le font sont les `*_test` de `sim_mocks`, jamais inclus par un launch file de mission.
3. Un nom de topic s'écrit une fois, dans `tools/topics.py`. `/aeac/external/...` traverse la radio, `/aeac/internal/...` reste sur le drone.
4. Ce qui change entre deux drones, deux terrains ou deux essais est dans `config/`, pas dans le code.
5. Chaque mission a son workspace. `gcs_ws` est le workspace du sol : rien de spécifique à un drone ou à une mission n'y entre.
6. Code en anglais ; docs, logs et commentaires de haut niveau en français.
7. Ce qu'on apprend et qu'on n'a pas le temps de ranger va dans `NOTES.md`.

Deux d'entre elles sont à retenir avant d'écrire une seule ligne de code, et ce sont les deux premières. Le code de mission n'arme pas et ne change pas de mode, parce que c'est le pilote qui en est responsable, et vous avez déjà rencontré ce principe en formation 3.4 avec la node `takeoff`. Et `main` est ce qui vole, dans un repo de compétition comme `aeac-2027`. Le `main` du template ne vole pas, puisqu'il n'a pas de mission, mais la discipline y est la même : une branche, `make check`, puis une PR (pull request : la demande, sur GitHub, de faire entrer votre branche dans `main`, relue avant) qu'un lead relit. Vous le ferez en 5.3.

Où écrire, enfin. `NOTES.md` est le carnet : ce que vous avez appris, ce qui vous a fait perdre deux heures, le réglage qui a marché. Écrivez-y sans demander la permission. `procédure.md` est la checklist du jour J, écrite par ceux qui vont sur le terrain ; vous la lisez pour savoir qu'elle existe, vous ne la pratiquez pas, puisque vous n'avez pas de drone.

## 6 - Quand ça casse

| Ce que vous voyez | Pourquoi | Quoi faire |
|---|---|---|
| `make build` construit moins de quatre packages | Un submodule est vide : le clone a été fait sans `--recurse-submodules` | `make status` (un `-` en début de ligne), puis `make init` (section 4.2) |
| `Package 'gcs_bringup' not found` alors que le build a réussi | Ce terminal a été ouvert avant le build : le workspace n'existait pas encore quand le shell l'a cherché | Fermer ce terminal et en ouvrir un autre avec `make shell` (section 4.4) |
| `ros2` introuvable, ou le topic du heartbeat invisible dans le second terminal | Le second terminal est resté dans WSL, hors du conteneur | Ouvrir le second terminal avec `make shell` (section 4.5) |
| Des fichiers appartenant à `root` apparaissent après un build | Les conteneurs de ce repo tournent encore en root, pas avec l'utilisateur non root que recommande la formation 2 | `sudo chown -R $USER:$USER .` à la racine du repo (formation 2, section 2.5) |
| `make: command not found` sous WSL | Le package n'est pas installé | `sudo apt install make` |
| `make shell` dit qu'aucun conteneur ne tourne | Rien n'est démarré | `make dev` d'abord, dans le premier terminal |
| `make status` affiche un `+` devant un package de `packages/` | Le submodule est sur un autre commit que celui attendu par le repo | Ne rien push et demander à un lead (section 4.2) |
